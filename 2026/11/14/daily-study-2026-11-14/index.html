🔧 嵌入式知识：C 对象生命周期、effective type 与未定义行为

嵌入式调试中最危险的一句话是：“地址没变，内存里也还是那个数，所以指针有效。”
C 语言抽象机不只描述字节和地址，还描述对象何时存在、以什么类型访问、表达式计算
是否有定义。编译器可以把这些规则当作优化前提；CPU 偶然读到旧字节，只能说明一次
机器执行的现象，不能证明程序符合 C 语义。

本文把两个经常被混为一谈的故障拆开：第一是对象生命周期结束后仍通过旧别名访问，
第二是把字节地址当成不满足对齐或 effective type 的结构化对象。前者的修复是重新
定义所有权或复制值，后者的修复是逐字段解码或复制到已声明、已对齐的对象；把指针
置空、加 volatile、换优化等级，都不能替代这些因果修复。主机实验验证语言层和
工具诊断，STM32G431/DMA 部分只给出计划验证方法，不能把主机结果升级成板级证据。

1. 先分清存储、对象、指针与所有权

malloc(64) 成功后，程序获得一段 allocated storage；它不是“自动变成任何类型的
结构体”。当程序按某种规则在其中存取值时，生命周期、effective type 和对齐条件
共同决定哪些访问有定义。Frame *p 是一个指针对象，保存的值可以复制到另一个
指针变量；它不是被指向对象的所有权证明。

C11 N1570 6.2.4p2 把生命周期定义为存储保证为该对象保留的执行区间。对象生命周期
外的引用是未定义行为；对象结束生命周期时，指向它或刚好越过它的指针值变为
indeterminate。free(p) 结束 allocated object 的生命周期，不是把对象内容“清空”
成一个仍可读的缓存。把一个别名写成 NULL 只能改变这个变量，不能改变已经复制到
队列、回调、全局变量或另一个线程栈中的别名。

非变长数组类型的普通自动对象，从进入关联代码块起到该块执行结束为止；变长数组
则从执行到声明开始，直到离开声明的作用域。因此，把已结束生命周期的局部数组地址
交给异步回调，不能靠地址仍在栈上来保证有效。下文的 realloc 讨论限定为请求大小
大于零：成功时旧对象生命周期结束，即使返回地址数值相同也只能继续使用新返回的
指针；分配失败时旧对象仍有效，所以应先用临时指针接收结果。零大小请求有独立的
语言版本和实现边界，不应混入这个失败处理模板。
参见 C11 N1570 6.2.4、7.22.3.5。
所有权协议应写成可检查的状态，而不是靠“调用者记得不要再用”：

如果队列接收者负责释放，发送者提交后就不能访问；如果队列传递的是完整值，队列
拥有副本而不是原指针；如果必须复用槽位，就用 slot、generation 和引用计数表达
“谁能写、谁能读、何时归还”。状态图中的箭头是权限变化：它不能由 volatile 自动
产生，也不能由某次运行中地址恰好未变来推断。

4. Effective type、字符数组与 volatile 的边界

带声明的对象有声明类型，声明类型就是该对象访问 stored value 时的 effective type。
无声明类型的 allocated storage 则依赖访问路径：通过非字符类型左值写入，可以为该次
访问和后续不修改 stored value 的访问建立有效类型；用 memcpy/memmove 或字符
数组复制时，源对象若有 effective type，目标后续不修改访问可沿用源类型。这个规则
不是“大小相同所以类型相同”，也不是“调用了 memcpy 就永远变成结构体”。
这些条件来自 N1570 6.5p6–p7。

因此，从已经存在的 Frame 对象完整复制到无声明分配存储，与从文件、网络或 DMA
来的 unsigned char 字节复制到那里，是两条不同路径。后者没有一个源 Frame 对象
可以传递 effective type；直接把字节地址强转成 Frame * 还要同时满足对齐、端序、
padding、边界和对象存活。字符类型可以读取其他对象的表示，这是允许观察字节的
方向；它不反向授权把任意字符数组当作任意结构体解引用。

查看浮点比特表示应复制对象表示，而不是通过不兼容指针解引用：

memcpy 不替协议定义端序；网络/Flash 格式仍应给每个字段定义宽度、字节序和长度，
再显式解码。结构体可能有 padding，直接把它写到线格式会绑定 ABI、泄露未初始化
表示并让接收方误读。即使当前优化下强转读出了期望整数，也只说明这次编译没有暴露
问题；GCC 的 strict-aliasing 选项说明
说明了 -O2/-O3/-Os 等级与类型别名假设，不能把
-fno-strict-aliasing 当作修复错位、越界、生命周期或整数溢出的总开关。

volatile 的限定位置也必须读对：volatile Frame *current 是指向 volatile Frame
的普通指针，Frame * volatile current 才是指针变量本身 volatile。两者都不会建立
线程 happens-before、延长生命周期或让结构体多字段更新原子化。ISR 与主循环交换
对象时，应在短临界区交换已完成对象的句柄，或使用有明确归还规则的单生产者/单消费
者队列；变量是否带 volatile 只是访问优化约束，不是所有权协议。

5. 第二段故障：为什么 raw[9] + 1 不能证明错位

原文使用 uint8_t raw[9] 后读取 *(const uint32_t *)(raw + 1)。raw 的声明只
保证满足 uint8_t 的对齐，通常是 1；C 不要求一个字符数组的起始地址满足
_Alignof(uint32_t)。编译器常把栈帧整体放在更高对齐地址，因此某次运行的 raw+1
可能确实 residue 1，但也可能 array base 恰好是地址模 4 为 3，使 raw+1 反而满足
4 字节对齐。优化、栈布局、ABI 或更换目标都可能改变这个偶合。错位与 effective
type 是两个独立的未定义行为维度：即使一次地址对齐，字符数组反向按 uint32_t
访问仍不能获得类型规则许可。

本次按原文 alignment 片段在 Apple arm64/O2 运行：编译退出 0，实际 raw+1 的
UBSan 地址报告显示需要 4 字节对齐，程序仍打印 bad=12345678 good=12345678 并
退出 0；这正是默认 recover 的陷阱。加入 -fno-sanitize-recover=alignment 后同一
类输入在报告后由 wrapper 映射为 134。bad 数值与 good 相同，不会使强转访问
变成有定义。

一字节偏移，并用静态断言保证本实验实现的 uint32_t 对齐大于 1：

该对齐；程序还打印 alignof_u32=4 residue=1 offset=1，把运行时前提暴露出来。若
另一实现的 uint32_t 对齐不大于 1，静态断言会拒绝把这段代码冒充成错位实验，而不

6. 故障定位闭环：不要把优化现象当因果证明

本次因果链可以压缩为：

-O0 看起来正常、-O2 读到旧值，不代表 -O2 制造了 bug；它只改变了未定义
程序暴露假设的方式。strict aliasing 可能让编译器基于不别名条件保留一次读取，
日志又会改变寄存器压力和布局。-fno-strict-aliasing 只影响一类优化，不能修复
UAF、错位、越界、overflow 或 DMA ownership。LTO 同样不是“更容易正确”，而是更
广的优化视野，所以本次把它作为修复版回归配置，不把某次无告警当作跨编译器证明。

主机回归只覆盖当前 Apple arm64/Apple clang 21、上述输入和支持的 sanitizer。没有
执行 Linux/GCC、不同 ABI、异步线程、真实 DMA、cache maintenance、ISR/NMI 或 RTOS
路径；这些都不能由本次结果代替。

7. STM32G431 DMA：类型正确仍可能生命周期错误

假设 USART DMA 循环接收两个 256 字节槽，DMA 写槽时 CPU 不读，idle ISR 只封存
{slot,generation,len}，解析任务验长度和代数后逐字段解码，任务释放槽后 DMA 才
能复用。这里有两个独立门：类型/对齐门防止把线上的字节当结构体，所有权门防止
解析期间槽被 DMA 覆写。即使 read_le16/read_le32 完全符合 C，DMA 仍可在解析中
改变下一字节，造成跨时间的撕裂帧。

正确的证据链应记录：DMA 当前目标槽、generation、封存时间、解析开始/结束时间、
长度检查结果、CRC 结果以及 release 时的引用计数。若故意让 ISR 每次提交槽 0 又
立即把 DMA 指回槽 0，主机可发送递增序号和 CRC；若观察到头部来自 N、尾部来自 N+1，
并且时间戳显示两个 owner 重叠，故障根因是所有权违反，不是“串口偶尔噪声”。修复
后验收三个不变量：DMA 拥有的槽 CPU 不解析；队列中的 {slot,generation} 在解析
开始和结束仍匹配；重新提交前引用计数为零。

本次未执行 STM32G431 板、DMA、ISR、UNALIGN_TRP 或 cache 实验。计划验证时
应在实际工程中设置 SCB->CCR |= SCB_CCR_UNALIGN_TRP_Msk，配置已知对齐/错位输入，
用 fault status 寄存器、DMA 目标寄存器和 generation 日志建立板级证据；还要按芯片
手册确认缓冲区是否能被 DMA 访问以及数据何时可见。寄存器含义见
Arm Cortex-M4 指南，
实际目标资源见 STM32G431 数据手册。
静态手册阅读不能替代运行。移植到带 D-Cache 的 Cortex-M7 或多核 SoC 时，还要另做
cache line 边界、clean/invalidate、设备屏障和共享域所有权验证；不能把那套缓存步骤
不加区分地写成所有 STM32G431 缓冲区的验收要求。

8. 练习与可判定标准

  1. 生命周期题：函数把栈数组交给异步回调后返回。给出“调用者提供长寿命缓冲”和
    “堆对象由回调释放”两种修复；只加 volatile 判失败。
  2. realloc 题：限定请求大小大于零，使用临时指针接收结果。失败时旧指针仍可释放，成功后所有旧内部
    指针都不得继续使用；测试失败路径和地址改变路径。
  3. effective type 题：分别说明从声明为 Frame 的源对象 memcpy 到无声明存储，
    和从网络 uint8_t 数组复制过去，为什么后续访问依据不同；答案必须提到源对象、
    字符访问、对齐、端序和 padding。
  4. 对齐题：解释为什么 uint8_t raw[9] + 1 不是保证错位；改用 _Alignas 和静态
    断言；运行 alignment_fault.c 时默认 UBSan 的 warning+exit0 不能判 PASS，必须
    查看 stderr 或使用 no-recover 选项。
  5. 工具题：按本文 scripts/labs/c_objects/ 源运行 UAF 的 ASan O0/O2/LTO、UBSan O2，以及修复版
    ASan+UBSan；故障验收为命中对应类别，修复验收为退出 0、业务输出正确、无诊断。
  6. DMA 题：实现双槽 generation 检查，向解析任务注入 100 ms 延迟并发送 10000 个
    递增帧；零撕裂、零 CRC 误报和复用前引用为零才合格，允许按设计计数丢帧但不得
    静默覆写。
