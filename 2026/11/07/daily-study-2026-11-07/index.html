IELTS 每日学习 — 2026-11-07

发表于 2026-11-07 分类于 每日学习 本文字数： 7.3k 阅读时长 ≈ 27 分钟

今日主线：IELTS Academic 周末整合复习与主动输出。

🔧 嵌入式知识：Wi-Fi 连接、漫游、功耗与安全

工程问题：设备显示“Wi‑Fi 已连接”，为什么仍会离线、乱漫游或在省电后漏消息

本文把目标平台固定为 ESP32‑S3‑DevKitC‑1（ESP32‑S3‑WROOM‑1）+ ESP‑IDF v6.0.2 stable 文档接口，2.4 GHz station 模式。ESP32‑S3 的具体安全、漫游与省电能力以该芯片、该 IDF 分支和构建配置为准；不能把经典 ESP32、ESP32‑C6 的 5 GHz/802.11ax 能力或另一个 IDF 版本的默认值移植过来。目标板射频、AP、空口抓包和电流实验在本次没有执行。本文真正执行的是 Darwin 25.5.0 arm64、Python 3.14.0 上的确定性合同模型，它只能证明状态、代次和预算守卫按预期拒绝反例，不能证明某个现场 AP 一定兼容。

真实产品最常见的错误，是把多个证据边界压成一个 connected 布尔值：驱动关联成功便启动 MQTT；收到同名 SSID 就接受；RSSI 瞬时下降就切 AP；把 listen interval 拉长便宣称“低功耗且零丢包”。一旦失败，日志只剩 wifi disconnected，于是射频、密码、DHCP、DNS、证书、漫游和 AP 缓存问题全被误判为“信号差”。正确做法是先建立跨层状态机，再让每个事件只推进它真正证明的那一层。

先分清身份、链路与应用：SSID 不是 AP 身份，关联也不是互联网可达

SSID（service set identifier）是无线网络名称，最长 32 octet；它用于发现与策略匹配，不是密码，也不是可信身份。同名 SSID 可以由同一企业的多台 AP 广播，也可以由攻击者仿造。BSSID（basic service set identifier）通常标识一个 AP 无线接口；漫游时 station 保持 SSID，却把当前 BSSID 换成候选 BSSID。BSSID 有助于描述“连到哪台射频”，但仍不是密码学身份证明，因为地址可被伪造。

扫描是在信道上发现 beacon 或 probe response。被动扫描只接收 beacon；主动扫描发送 probe request 并等待 response，通常更快，却增加发射能量、空口暴露和监管约束。扫描结果是某时刻的观测，不是持续真相：RSSI 会因多径、人体遮挡、天线方向、共信道争用而变动，AP 也可能在结果返回后离线。因此连接 API 必须带扫描结果的寿命和 attempt id，不能永久缓存一个“最佳 AP”。ESP‑IDF 的 Wi‑Fi 驱动把初始化、start、connect、disconnect 和 IP 事件分开，其官方驱动总览也明确要求应用围绕事件建立场景状态，而不是把一次 API 返回值当作最终联网结果。

802.11 authentication、association和密钥建立是相邻但不等价的步骤。WPA2‑Personal 常先做 open-system authentication 与 association，再执行四次握手导出并安装链路密钥；WPA3‑Personal 的 SAE 本身参与认证，顺序和失败码与 WPA2 不同。因此本文状态名 AUTHENTICATED → ASSOCIATED → KEYED 是用于推理的事件边界，不声称与每种 AKM 的每一帧一一对应。AKM（authentication and key management）定义双方如何认证和导出密钥；cipher定义数据帧如何加密与校验。只看 SSID 或 RSSI，无法证明 AKM/cipher 满足策略。

ESP‑IDF 的 WIFI_EVENT_STA_CONNECTED 表示驱动所定义的 station 链路连接完成，却不证明 DHCP 已给地址。IP 层还可能经历 DHCP discover/offer/request/ack、静态地址冲突、IPv6 地址配置和默认路由建立；之后 DNS 解析、可信时间、TLS 证书链/主机名验证、MQTT session 又各有独立失败。IP_EVENT_STA_GOT_IP 也只证明一个地址事件，不证明域名、远端路由或应用认证。MQTT session confirmation是 broker 已接受 CONNECT 并返回成功 CONNACK；TCP/TLS 成功但还没收到成功 CONNACK 时，不能发布业务消息或标为 APP_READY。本文把最小数据流写成：

重连策略：错误分类、deadline 与抖动退避是三件事

“重试”不是固定每秒调用 esp_wifi_connect()。首先按层分类：找不到 SSID、认证密码错误、AP 拒绝关联、四次握手超时、DHCP 无响应、DNS 失败、证书无效和服务器拒绝，不应共享同一处理。错误凭据无限重试既耗电又可能触发网络侧锁定；监管域或安全阈值不匹配应 fail closed；短暂 beacon loss 才适合自动重连。

deadline 是调用者愿意等待该状态的绝对边界，timeout 是超过边界后的结果，二者都不表示无线硬件已静止。停止一次连接尝试后仍可能收到队列中的事件，因此要先提升 generation，再处理迟到回调。指数退避控制反复故障对 AP 和电池的冲击，随机抖动避免成千设备在 AP 恢复时同步扫描。示意公式为：

漫游不是“换到 RSSI 最大值”：11k、11v、11r 分别提供什么

漫游是 station 从一个 BSS 切到同一业务网络的另一个 BSS。普通 station 即使没有 11k/v/r 也可扫描后重新关联；这叫基础漫游，往往要完整发现和密钥流程。三个扩展解决不同成本，不能互换：

  • 802.11k radio resource measurement让 station 请求 neighbor report、beacon measurement 等信息，缩小候选信道和补充测量。它帮助“去哪找”，不会替 station 做安全决定，也不保证邻居更好。
  • 802.11v wireless network management中的 BSS transition management 允许网络建议候选或请求 station 迁移。建议不是命令；终端仍要验证 SSID、安全能力、黑名单、业务预算和本地测量。恶意或错误建议不能绕过策略。
  • 802.11r fast BSS transition（FT）预先/分层派生漫游所需密钥，减少切 BSS 的认证开销。它缩短一部分 L2 交接，不保证扫描为零、IP 不变、TCP 不丢包或应用无抖动。ESP32‑S3 在该固定版本文档下明确支持 WPA2‑PSK 的 FT over-the-air，启用还依赖 CONFIG_ESP_WIFI_11R_SUPPORT 与 ft_enabled；不能把 WPA3、FT over-DS 或跨 mobility domain 当作已支持。Espressif 的安全与漫游指南还明确说示例只展示 API，漫游算法和场景要由应用定义。

mobility domain是 11r 中共享 FT 层级和策略的一组 BSS 标识；相同 SSID 不等于相同 mobility domain。roam trigger是开始考虑漫游的条件，例如当前 RSSI 低于 -70 dBm；hysteresis要求候选至少好若干 dB，防止噪声让两个 AP 反复切换；minimum dwell要求驻留最短时间；三者一起对抗 ping-pong。sticky client则是阈值太低或不扫描，设备抱住差 AP。RSSI 只描述接收功率，不能直接代表 SNR（signal-to-noise ratio，信号相对噪声的强度）、PER（packet error rate，帧/包错误比例）、争用、AP 负载和上行链路；候选评分应同时记录业务丢包/时延，并给安全兼容性硬门禁，而不是让强信号覆盖安全降级。

一个可审计决策顺序是：当前业务是否失去预算 → 当前 RSSI/PER 是否连续越界 → dwell 是否满足 → 获取 11k/本地扫描候选 → 先过滤 SSID/AKM/PMF/mobility domain → 再按信号、负载、历史失败计算本地主评分 → 11v 仅在主评分相等或落入明确容差时作 tie-break → 发起带新 generation 的 roam。容差必须有单位和方向，例如本文窄化 host model 用 RSSI 作主评分，best_rssi - suggested_rssi <= 2 dB 才允许建议胜出；建议 -70 dBm、非建议 -40 dBm 相差 30 dB，必须选择 -40 dBm。不能把“建议优先”写在 sort key 第一项，否则 11v 会覆盖本地证据。阈值成立只允许“尝试”，不保证候选成功；失败需在 deadline 内回退当前 BSS或进入重连。

候选还有一层容易漏掉的对象身份合同：BSSID 只用于从本次 scan table 解析唯一 canonical record，随后 SSID、AKM/security、PMF capability、RSSI、channel、mobility domain、FT eligibility 和最终 connect 全部只能读取该 canonical object。调用方传来的 AccessPoint 副本即使 BSSID 相同，其余字段都不具有权威性；否则它可伪造“好 mobility domain/强安全/支持 PMF”，绕过 scan 中同 BSSID 的坏记录。scan 本身先拒绝重复 BSSID，roam 再按 BSSID lookup；lookup 不到就拒绝，lookup 到后也不能混用 caller target 与 canonical target 的字段。

L2 漫游后 TCP 是否存活，取决于新 AP 是否仍接入同一 VLAN/L3 子网、地址租约和路径状态；TLS session 是否复用又取决于 socket 与服务器。11r 不能修复跨 VLAN 地址变化。验收应分别量 last old-BSSID data → first new-BSSID data 的 L2 gap、IP 可用 gap和应用消息 gap，不能只看 GUI 显示的 roam time。

省电的因果链：beacon、TIM、DTIM、listen interval 与业务延迟

station 持续监听信道会让 RF/PHY/baseband 活跃。modem-sleep允许保持关联而周期关闭这些无线模块；CPU 是否暂停、系统是否进入 light-sleep 是另一个电源层级。ESP32‑S3 的官方 Wi‑Fi 性能与省电说明区分 WIFI_PS_NONE、WIFI_PS_MIN_MODEM 与 WIFI_PS_MAX_MODEM：MIN_MODEM 按 DTIM 唤醒，MAX_MODEM 按 station 配置的 listen interval 唤醒；MAX_MODEM 的间隔可长于 DTIM，因此可能漏广播数据。

beacon interval是 AP 周期发送 beacon 的标称间隔。TIM（traffic indication map）告诉休眠 station AP 是否缓存了面向它的单播；DTIM是在若干 beacon 周期中标识广播/组播交付时机的特殊 TIM。listen interval由 station 在关联配置中表达自己最多隔多少 beacon 监听；它既影响 AP 为该 station 保留单播的预期，也影响最坏下行等待。三者不是毫秒字段的同义词，listen interval/DTIM 通常以 beacon 数计。

TWT（Target Wake Time）是 station 与 AP 协商未来 service period 的机制，双方围绕约定时间唤醒/传输；它不是“把 listen interval 改长”，也不由 DTIM 自动产生。TWT schedule、DTIM broadcast delivery 和 legacy listen interval 分别来自不同协商/缓存合同。TWT常与 802.11ax/Wi‑Fi 6 讨论；ESP32‑S3 v6.0.2 的官方 feature list列出 802.11b/g/n 与 modem-sleep，没有把 TWT 列为本芯片 station 能力或配置 API，因此本文平台必须把 twt_requested 判为 unsupported，不能借别的 ESP32 型号或 AP 支持推断。未来若换支持 TWT 的芯片，也要验证 negotiation result、wake schedule、missed service period 与 teardown，不能复用本文 DTIM 公式。

链路安全、管理帧保护、端到端 TLS 与凭据存储各守一层

WPA2‑Personal用预共享凭据完成认证/密钥管理；WPA3‑Personal用 SAE 改进口令认证与前向安全性质。WPA2/WPA3 transition mode 为旧终端保留兼容路径，也扩大降级面；产品策略应设置最低 authmode，并把降级视为故障，而不是因为同名 SSID 信号强就接受。弱口令在 WPA3 下仍可能遭在线猜测，出厂 provisioning、恢复出厂和所有权转移仍要限制尝试并有审计。

SAE（Simultaneous Authentication of Equals）是 WPA3‑Personal 的口令认证交换，成功后建立可供后续密钥层使用的 PMK（pairwise master key）材料；它不是“数据帧已开始加密”。WPA2‑PSK 则从预共享秘密得到 PMK 语义。两条路径之后仍需要 4-way handshake，用双方 nonce、地址和 PMK 派生 PTK（pairwise transient key），确认双方持有主密钥并安装数据链路所需密钥；AP 还向 station交付/更新 GTK（group temporal key），用于该 BSS 的组播/广播保护。本文 KEYED 要求 PTK 与 GTK 都已安装；SAE success 只推进 AUTHENTICATED，不能跳过 association/4-way 直接推进 IP。

密钥会因重新关联、定时/策略 rekey 或组密钥更新而变化。key epoch是产品给“一组已安装 PTK/GTK”分配的单调生命周期；replay counter是握手/密钥消息用来拒绝旧消息或重发回退的单调证据。新 epoch 必须严格等于旧 epoch+1，接受的新 counter 必须严格大于本 epoch 已接受值；旧 epoch、相同 counter 和倒退 counter都拒绝。counter重复有时是传输层重发的一部分，真实 supplicant必须按 802.11/实现状态机区分可接受重传与已经安装后不可重复安装；本文窄化合同选择在 rekey_complete 完成边界只接受严格前进，防止旧 completion 再次安装。连接 generation解决软件异步对象生命周期，key epoch/replay counter解决加密状态演进；把 generation 当 replay counter会在同一连接 rekey 时失效，把 replay counter当 generation又无法拒绝旧 DHCP/TLS回调。

PMF（protected management frames，802.11w）保护已建立安全关联后的 robust management frame：单播管理帧获得机密性/完整性，广播管理帧获得完整性保护。它减少伪造 deauthentication/disassociation 等攻击，却不能阻止射频干扰、屏蔽、所有未受保护的发现帧，也不能给未关联阶段提供万能认证。ESP32‑S3 的官方 Wi‑Fi Security 页面说明默认 PMF Optional；将 pmf_cfg.required 设为 true 才会拒绝不支持 PMF 的对端。PMF capable只表示 AP 宣告能做 PMF，PMF negotiated才表示本次 association/security exchange 实际选用了它；Required policy 必须检查 negotiated result，不能因 scan record capable=true 就把链路标安全。Optional 是兼容策略，不等于 required。

Enterprise Wi‑Fi通过 802.1X/EAP 与 RADIUS 后端认证。CA certificate 用来验证服务器证书链；server name/subject matching 防止“证书由某 CA 签过但不是目标服务器”；可信时间决定证书有效期判断。把 CA 验证关闭、接受任意服务器，只是把企业口令交给可能的恶意 AP。证书验证是身份边界，不能为了“现场先连上”静默降级。

Wi‑Fi 加密只覆盖 station 到当前 AP/网络设备的链路，不保证 AP 后面的路由、DNS、云端可信。TLS提供应用端到端的服务器身份、机密性与完整性；MQTT authentication/authorization再决定某设备能发布/订阅什么。反过来，TLS 也不保护 deauth 引起的可用性中断。因此产品需同时定义 link policy、TLS trust store、应用凭据与更新生命周期。

SSID/密码、私钥和 CA store 不应出现在普通日志或明文 crash dump。Flash encryption 保护离线读取、NVS encryption 保护存储记录、secure boot 约束可启动固件来源；三者威胁模型不同。即使存储加密，运行时内存仍可能含明文，provisioning 接口仍可能越权。安全验收需覆盖首次配网、凭据轮换、恢复出厂、RMA、OTA 回滚与日志脱敏，而不只是“WPA3 图标亮了”。

实现路径：让事件携带代次，让策略先过滤再评分

下面是针对 ESP‑IDF 的设计骨架，不是本次编译或目标板运行证据。实际 event id、union 字段和 FreeRTOS 同步原语必须以固定 v6.0.2 headers 为准。关键点是每个回调先核对 token，再要求唯一前置 stage；任何提前、重复或迟到事件返回分类错误且不改变状态。连接 generation 与密钥 epoch/counter分字段保存。

event reducer 应只有类似 advance(expected,current_event,next) 的单一入口：current.stage != expected 就拒绝，不做“>= 则也算成功”的宽松判断；完成 TLS 时只进 NET_TLS_READY，收到并验证 MQTT CONNACK/应用协议 ACK 后才进 NET_APP_READY。rekey 不沿主链重复经过 IP/TLS，而是在 stage >= NET_KEYED 时独立要求 new_epoch == old_epoch+1 && new_replay_counter > old_replay_counter，成功后保持当前网络层 stage。

故障注入与完整定位闭环

第一条 fault 把 ASSOC 提前送到 ATTEMPT_STARTED，又把成功 AUTH 重复送一次。现象是宽松状态机可能跳过认证或重复释放/分配资源；证据分别是 WIFI_EVENT_ORDER:ASSOCIATED:ATTEMPT_STARTED 与 duplicate AUTH。修复是 current token匹配后仍要求 stage == exact_expected，并把 event消费设计为一次性。TLS完成后再注入 session_confirmed=false，stage 保持 TLS_READY；只有成功 protocol ACK 才到 APP_READY，重复 APP事件也拒绝。

第二条 fault 在同一 connection generation 内先合法 rekey 到 epoch 2/counter 8，再送旧 epoch 2和不递增 counter 8。现象是旧 completion可能重新安装密钥；证据为 WIFI_KEY_EPOCH:2!=3 与 WIFI_REPLAY_COUNTER:8<=8。修复是 epoch连续、counter严格前进，同时把它们与 generation分开。另一个反例中 scan record pmf_capable=true，实际 pmf_negotiated=false，Required policy得到 WIFI_PMF_NOT_NEGOTIATED，证明 capability不能冒充本次协商结果。

第三条 fault 在漫游后注入旧 connection event。证据显示旧 token generation 1、当前 2，定位异步 ABA；修复是在 disconnect/roam开始时提升 generation，并让所有 auth/assoc/key/IP/TLS回调核对 generation+attempt+BSSID。该修复不替代 replay counter，二者各自回归。

第四条 fault 给 11v 建议候选 -70 dBm，同时存在非建议 -40 dBm，容差仅 2 dB。若把 suggested放 sort key第一项就会选错；模型输出明确选择 -40。修复是先做硬过滤和主评分，只在 best-suggested<=tolerance 时用 11v tie-break。强信号 open evil twin则先被 WPA2/PMF门禁拒绝，说明安全过滤还早于评分。

第五条 fault 传入一个与 scan candidate 同 BSSID 的伪造 AccessPoint：caller副本把 mobility domain写成当前链路的 a1b2，而 canonical scan record实际为 bad0。若 FT检查 caller、connect又按 BSSID取 canonical，就会出现判断与执行对象分裂；修复后第一步按 BSSID解析 canonical，security/PMF/FT/eligibility/connect都只消费它，因此稳定得到 WIFI_FT_MOBILITY_DOMAIN，且 current AP与 generation均未改变。

第六条 fault 把 MAX_MODEM listen interval设 10、beacon 100 ms，却保留 350 ms下行预算，得到 1000>350；修复是缩短 interval、改 MIN_MODEM、提高已获批准的业务 deadline或主动 poll。另一个 fault请求 TWT，模型按 ESP32‑S3 v6.0.2能力边界返回 unsupported，防止把 DTIM/listen interval伪装成协商 TWT。

hostile cases 还拒绝重复 BSSID、bool 冒充 replay counter、NaN指标和 RSSI尚未越 trigger的 ping-pong。它们证明输入/顺序守卫，不能覆盖真实 supplicant对握手重传的全部规范、AP bug或射频攻击。

目标板与多 AP 计划实验（本次未执行）

准备 ESP32‑S3‑DevKitC‑1、固定 ESP‑IDF v6.0.2 构建产物、两到三台可配置 802.11k/v/r/PMF 的 AP、可编程射频衰减器或隔离箱、支持 monitor mode 的独立抓包网卡、功耗分析仪和有线时间参考。所有 AP 锁定配置快照，记录 BSSID/channel/DTIM/AKM/PMF/mobility domain；未固定 AP firmware 的结果不得跨版本推广。

  1. 分层连接：分别重排/重复 auth、assoc、key、IP、DNS+time、TLS、MQTT CONNACK，并注入错密码、DHCP blackhole、错误 CA。通过：只有当前 token+exact stage事件推进；TLS无成功 CONNACK绝不 APP_READY；重复事件无二次 side effect。
  2. 密钥状态：抓 SAE/WPA2 authentication、4-way、group rekey，记录 PTK/GTK安装边界、PMF capability/negotiated、key epoch与 authenticator replay counter。通过：SAE后仍走4-way；Required链路必须 negotiated PMF；旧 epoch、重复/倒退 counter不再次安装。空口敏感密钥不得写日志。
  3. 安全候选：配置同名 open、WPA2 无 PMF、WPA2+PMF 和 WPA3 AP，逐个改变 RSSI。通过：最低 authmode/PMF 永不被信号覆盖；空口协商与驱动记录一致；日志无凭据。
  4. 漫游矩阵：以 1 dB 步进改变 AP 衰减，构造 11v建议比非建议差 0/1/2/3/30 dB，并向 roam API 注入同 BSSID但伪造 AKM/PMF/mobility-domain/RSSI 的副本。通过：只在明示 2 dB容差内 tie-break；所有判断与 connect都使用唯一 scan record；FT仅在 canonical record为 WPA2‑PSK OTA/相同 mobility domain时启用。
  5. 省电矩阵：DTIM为1/3/10，listen interval为1/3/10，MIN/MAX/NONE各测单播、广播/组播、TCP keepalive和100/350/1200 ms deadline。通过：保存电流积分、p99 latency、丢包与重连；ESP32‑S3配置/trace中不得虚构 TWT negotiation，换 TWT-capable平台时另建 schedule验收。
  6. 可用性攻击：在已关联后注入未保护 deauth、合法 PMF 管理帧和纯 RF 干扰。通过：PMF Required拒绝可伪造 robust management frame，但明确 RF jam仍可丢包。
  7. 长稳回归：AP 重启、channel switch、DHCP lease renew、rekey、路由变化、证书轮换、OTA 和断电后连续运行。通过：连接 generation与key epoch各自单调、没有旧回调复活或无限扫描风暴，错误层级可由 trace重建。

练习与可判定答案

  1. WIFI_EVENT_STA_CONNECTED 后能否立即宣称 MQTT 可用？ 不能。至少还要有 IP/route、DNS 或固定地址策略、可信时间与 TLS peer 验证、MQTT session；每层要独立证据。
  2. 11v 建议的 BSSID 信号最强，终端是否必须接受？ 不必须。11v 是 network-assisted suggestion；终端必须先检查 SSID、最低 AKM、PMF、黑名单与业务政策，再评分。
  3. 11r 已启用为何 TCP 仍可能断？ FT 只减少部分 L2 密钥交接；跨 VLAN/IP 改变、扫描 gap、丢包、NAT/path timeout 都不由 11r 保证。
  4. MIN_MODEM 与 MAX_MODEM 的关键差异？ 前者按 DTIM 唤醒以接收相应广播时机；后者按可更长的 listen interval 唤醒，可能进一步省电但增加下行延迟并漏广播。实际取舍必须测 AP。
  5. PMF Required 能否防射频干扰？ 不能。它认证/保护规定的 robust management traffic，不提供抗物理层 jam 的可用性保证。
  6. 为什么 BSSID 和 generation 都要记录？ BSSID描述当前无线接口；generation 描述连接生命周期。地址可能复用、旧事件可能迟到，只有二者与 attempt 一起才能拒绝 ABA。
  7. “WPA3 已连接”为什么仍需要 TLS？ WPA3保护本设备到 AP 的链路，TLS验证远端服务并保护跨 AP/路由的端到端数据；威胁边界不同。
  8. 功耗实验只看最低电流是否合格？ 不合格。必须对固定窗口积分，并把扫描、重连、消息成功数及 p99 latency 纳入；低谷不代表平均能量或业务可用。
  9. SAE 成功是否等于 PTK/GTK 已安装？ 不等于。SAE建立认证/PMK材料，之后仍需 association与4-way；只有 pairwise/group key均安装并满足PMF政策才能到 KEYED。
  10. PMF capable 与 negotiated 有何区别？ 前者是候选宣告能力，后者是本次连接实际选择；Required必须检查 negotiated，不能只看scan capability。
  11. connection generation 能否替代 replay counter？ 不能。同一连接可发生多次 rekey；generation解决软件回调生命周期，epoch/counter约束密钥演进与旧消息。
  12. TWT 与 MAX_MODEM listen interval是否同一机制？ 不是。TWT是与AP协商的service period；listen interval/DTIM是legacy beacon/cache合同。本固定ESP32‑S3平台不宣告TWT支持。
