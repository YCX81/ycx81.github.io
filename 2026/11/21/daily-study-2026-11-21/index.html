🔧 嵌入式知识：RTOS tick、timeout 与绝对 deadline

从“偶尔晚几十毫秒”的现场故障开始

设想一条传感器链：采样任务每 10 ms 读取一次 ADC，处理任务必须在请求进入系统后的 80 ms 内给出控制量。台架连续运行一小时完全正常，设备运行约五十天后却突然把一批请求判成“早已超时”；另一个版本没有突然失效，却会每天比外部基准慢几秒。两种现象通常不是晶振这一项就能解释：前者可能把回绕后的 32 位 tick 当普通整数比较，后者可能在每轮工作结束后重新做相对 delay，把执行时间永久累加到周期里。

本文先冻结适用平台：目标路径是 NUCLEO-H743ZI2（STM32H743ZI）+ CMSIS-RTX 5.9.1 的原生 CMSIS-RTOS2 接口，GNU Arm Embedded 12.3.1，内核 tick 配置为 1000 Hz，osKernelGetTickCount() 为 32 位滚动计数。CMSIS-RTX 5.9.1 Overview给出版本与原生接口定位；CMSIS-RTOS2 的 Generic Wait Functions明确说明 osDelay(1) 的实际等待可能比一个 tick 短，而 osDelayUntil() 处理 32 位溢出但单次未来间隔最多是 2^31-1 tick。目标板实验在本文中标成“计划验证”，没有伪装成已经烧板执行。真正执行过的是 macOS Darwin arm64、Python 3.14.0 上的确定性契约实验。

这里的结论分四层：CMSIS、Zephyr、FreeRTOS 文档写明的是 API 规范或实现文档保证；STM32 定时器频率和低功耗时钟是 芯片/板级配置；本文的 64 位 deadline ledger 是 应用设计；“必须严格早于 deadline 才算成功”是本文控制链的 业务契约，不是所有 RTOS 自动采用的定义。把这四层混写，往往正是时间故障难以闭环的起点。

先把五种“时间”分开

硬件 cycle 是某个计数器的最小递增单位。它可能来自 CPU、通用定时器或低功耗计时器；频率可能固定，也可能随时钟树改变。tick 是内核用于超时和调度记账的离散单位；1 kHz tick 表示一 tick 名义上为 1 ms，却不表示每 1 ms 一定执行一次目标任务。单调时间只承诺不后退，适合衡量持续时间。墙上时间表示日期和时刻，会被 RTC 校准、NTP、时区或人工设置改变，适合日志和日历，不适合判断一段操作是否耗尽预算。CPU 运行时间只累计线程真正占用处理器的时间，也不能替代端到端延迟。

相邻概念必须继续拆开：

  • resolution（分辨率）是最小可表达步长，例如 1 ms；accuracy（准确度）是相对真实时间的误差；precision（精密度）描述重复测量的离散程度。高分辨率计数器仍可能频率错误，准确却低分辨率的 RTC 也测不出微秒级抖动。
  • release time（释放时刻）是一个周期实例允许开始的时刻；deadline（截止时刻）是它必须完成的时刻；period（周期）是相邻释放时刻的间隔。周期等于 deadline 只是常见特例，不是定义。
  • jitter（抖动）是实际释放、开始或完成时刻相对目标时刻的变化；必须注明测的是哪一个点。GPIO 在任务入口翻转得到的是开始抖动，不是 ADC 硬件采样抖动。
  • WCET（最坏情况执行时间）是在写清处理器、cache、输入域、抢占和测量方法后，对一段工作的上界。一次观测到的最大值只是样本最大值，不能自动升级为 WCET 证明。
  • timeout（超时量）常表示“最多再等多久”；absolute deadline（绝对截止点）表示“单调时间到哪里为止”。前者是时长，后者是时刻，量纲虽然都能写 tick，却不能互换。

CMSIS 的 Kernel Information and Control同时提供 kernel tick 与 system timer。system timer 可给出 tick 以下的短时测量，但它仍是滚动计数，频率由 osKernelGetSysTimerFreq() 给出。它不因名字里有 timer 就自动成为 UTC，也不自动具有跨休眠连续性；这些都要由具体 port 与板级时钟证明。

先乘后加会有整数溢出风险；先除又会丢失余数。工程实现应使用内核转换宏，或在足够宽的整数里做 checked arithmetic，再确认 unit_ticks+1 也不碰 forever 保留值和半范围上限。0 tick 不是“等待一个最小单位”：在 CMSIS 中 osDelay(0) 是参数错误；在其他 API 中 0 常表示不等待。调用者必须遵从具体接口，而不是凭经验迁移。

提高 tick rate 只能缩小量化误差，不会自动降低 ISR 阻塞和调度干扰；代价还可能是更多定时中断与功耗。Zephyr 的 Kernel Timing进一步区分 cycle、64 位内部 uptime tick 与 k_timeout_t，并说明 timeout 最终在插入队列时转换成 tick。该文档还指出默认 timeout 表示宽度可配置，长 uptime 与非 tick 单位的回绕语义需要特别处理。这是 Zephyr 的设计，不应倒推成 RTX 或 FreeRTOS 的内部实现。

32 位回绕为什么需要“半范围”前提

1000 Hz 的 32 位 tick 约 2^32 / 1000 / 86400 = 49.71 天回绕一次。若起点为 0xfffffff8，向前 20 tick 的 deadline 投影是 0x0000000c。普通比较 now >= deadline 在起点就得到真，错误地宣告超时。

模 2^32 差值能表达环上的前向距离，但同一对数值存在两个方向。0 到 0x80000000 顺时针、逆时针都是半圈，无法仅凭两端判断谁先谁后。因此 32 位序关系只有在以下不变量同时成立时才有意义：

在这个前提下，可把 distance = (deadline - now) mod 2^32 解释为：0 < distance < 2^31 表示 now 严格早于 deadline；distance == 0 表示相等；distance == 2^31 必须拒绝，因为方向歧义。这里的“半范围”是应用数学前提，不是把 uint32_t 强转 int32_t 的许可证。C 在无符号值超出目标有符号类型范围时的转换结果与实现有关；可移植代码应优先使用 RTOS 已定义的 deadline API，或维护受同步保护的 64 位单调扩展。

CMSIS 文档明确承诺 osDelayUntil() 处理 tick 溢出，并把最大 delay 限为 2^31-1。这意味着下面的周期骨架可以跨一次正常回绕；它不意味着把任意古老的 32 位 tick 存到闪存、几个月后再取出仍能判序，也不意味着任务可以漏掉多次回绕后凭低 32 位恢复 epoch。

这段骨架仍不完整：它需要在工作开始和结束记录时间，定义 overrun 后跳过、追赶还是重新定相；还需要确认 period < 2^31，并确认目标配置确实是 1 kHz。它只展示 API 正确方向，不能把未定义的项目函数冒充可直接编译的完整固件。

执行时间和干扰被永久积累，这叫 drift（漂移）：相位相对理想基准不断偏移。绝对周期以锚点 A 生成 R_k = A + kP，本轮运行多久不会改变未来释放网格。FreeRTOS 的 vTaskDelayUntil()正是以前一唤醒时刻为基准的周期 API；它与 CMSIS osDelayUntil() 名字相近，参数与迟到行为仍必须分别查文档。

绝对周期并没有消灭过载。若一轮在下一个释放点之后才结束，需要显式选策略：

  • catch up（追赶）：立即运行欠下的实例。只适合每个实例都不可丢且系统证明能清空积压，否则会形成 CPU 风暴。
  • skip（跳过）：丢弃已经越过的释放实例，转向“不早于当前完成时刻”的第一个释放点。适合只需要最新样本的控制链，但要记录丢样与数据年龄。
  • rephase（重新定相）：以当前时刻建立新锚点。能停止追赶，却改变与其他任务/外设的相位关系，必须作为受控降级而非静默行为。

本文 host oracle 对 10 tick 周期、执行序列 3,4,15,2 使用 skip：相对开始点为 0,13,27,52；绝对开始点为 0,10,20,40，严格 deadline miss 一次，并跳过释放点 30 一次。这里必须分开两个等号：旧实例的完成判据是 finish < deadline，所以 finish==10 已算旧实例 miss；新实例的 release 判据是 start >= release，所以同一个时刻 10 又允许新实例开始。执行序列 [10,1] 因而从 0,10 开始，记录一次旧实例 strict miss，却不跳过时刻 10 的新释放。把“旧 deadline 等号失败”错误复用成“下一 release 必须严格晚于 finish”，会把新实例误推到 20。如果硬件协议把完成边界包含在合法窗口，则业务应选非严格 deadline 并在一处定义；不能一层用 <、另一层用 <=。

tickless idle、低功耗与墙钟跳变

tickless idle 是没有近期内核事件时停止周期 tick 中断，并安排一次更远的唤醒；它不是冻结逻辑时间。CMSIS 的 osKernelSuspend() 返回可睡 tick 数，osKernelResume(sleep_ticks) 用实际睡眠量推进内核。若低功耗计时器频率不准、宽度不足、唤醒延迟未计入，补偿值就会错。测试必须覆盖最长睡眠、定时器回绕、早醒和晚醒，而不是只测 WFI 一秒。

DVFS（动态电压频率调整）会改变某些硬件 cycle 的频率；tick 是否保持 1 kHz 取决于定时器时钟域和 port 更新逻辑。Zephyr 文档要求运行期系统定时器频率变化时更新内核频率信息，并指出该全局模式不等于每核独立频率支持。因而“读 cycle 差再除以启动时频率”只在频率冻结或记录了每段转换时成立。

目标板计划验证：把 API 保证落到示波器证据

本节是计划，尚未执行。准备 NUCLEO-H743ZI2、CMSIS-RTOS2/RTX5 工程、逻辑分析仪，并固定编译器、优化级别、tick 频率和低功耗时钟源。一个 GPIO 在定时器比较事件处翻转，另一个在采样任务真正进入时翻转；UART 只在低优先级日志任务输出，避免测量路径改变高优先级时序。

步骤与判据：

  1. 启动时打印 osKernelGetInfo()、osKernelGetTickFreq() 与构建哈希。若 tick 不等于 1000 Hz，停止测试，不能把脚本里的 1 tick 当 1 ms。
  2. 让周期任务以 osDelayUntil() 运行十万轮，记录目标释放、GPIO 实际开始与完成。通过条件是相位误差不单调累积，开始/完成 jitter 的最大值落在已批准预算内。
  3. 人工把 tick 初始状态或测试 hook 推到 0xfffffff0 附近，跨回绕执行周期与请求 deadline。通过条件是没有突然提前 timeout，且所有间隔小于 2^31。
  4. 注入一次 15 ms 计算到 10 ms 周期，检查固件按约定跳过并递增 overrun 计数，而不是连续补跑或悄悄重定相；再注入恰好 10 ms，要求旧实例 strict miss，但新实例可在同一时刻 10 开始而不计 skip。
  5. 在等待循环每 30 ms 注入无关通知。通过条件是从请求入口起 100 ms 到期，不得因三次通知延到 190 ms。
  6. 进入最长允许 tickless idle，并用独立示波器/RTC 计量睡眠。通过条件是恢复后的 tick 与外部持续时间误差在晶振和唤醒预算内，过期 timer 不丢失。
  7. 把 wall clock 回拨一小时。通过条件是请求 deadline 与周期相位均不受影响，只有带 UTC 的日志字段变化。

只有这些目标证据完成，才能声称该板级 port 满足项目时序假设。主机实验只能证明应用契约在列出的离散案例中自洽。

故障注入与定位闭环

现象：设备运行约 49.7 天后，一进入请求处理就报 timeout；较短运行中看不到问题。

假设：应用把滚动的 uint32_t now 与 deadline 做普通大小比较，deadline 已跨回绕变小。备选假设包括 tickless 补偿丢 tick、墙钟校时和任务被高优先级线程饿死。

证据：记录请求入口的 64 位扩展时间、now32、deadline32、预算和错误分支。故障时看到 start32=4294967288、deadline32=12，普通表达式在入口已经认为 4294967288 >= 12；同一时刻模前向距离为 20，主机 oracle 也复现 naive_start_expired=true。禁止只看一条“timeout”日志，因为它不能排除调度延迟。

定位：静态搜索所有 now >= deadline、deadline - now、毫秒乘 tick 频率和每轮重置 timeout 的调用点；对每处标注使用的时间域、位宽、最大跨度和等号语义。确认问题发生在应用比较，而不是 RTX 的 osDelayUntil()。

修复：周期任务改用内核绝对周期 API；端到端请求在入口创建 64 位单调 deadline token；所有下游只计算剩余预算，严格相等视为过期；无法证明 epoch 或跨度时拒绝，而不是猜测。取消与硬件 quiescent 另建状态机。

回归：先执行本文主机脚本双跑；再跑目标板回绕、过载、spurious notification、tickless 与 wall-clock-step 测试。持续监控 deadline_miss_total、overrun_total、最大开始/完成 jitter、tickless 补偿误差以及最小剩余预算。若只有错误消失却没有覆盖回绕前后和相等边界，闭环仍未完成。

失效边界与工程收束

  • 32 位半范围比较只覆盖已证明的小于 2^31 的单次窗口；跨多次回绕、掉电保存后的旧 tick、不同设备 epoch 都不成立。
  • 64 位计数器不是自动安全。读取若在 32 位 MCU 上会撕裂，需要内核提供原子快照或短临界区；高字扩展若错过完整回绕仍会别名。
  • timeout 到期说明等待 API 返回失败，不说明被等待硬件停止。资源回收必须等 quiescent 证据。
  • READY 不等于 RUNNING，timer expiry 不等于任务完成。实时验收应测端到端完成点。
  • tickless、DVFS、调试器暂停、深睡复位时钟都可能改变时间连续性；每种电源状态都要列入时钟契约。
  • forever 是特殊策略值，不应参与普通加减；0 是立即尝试、参数错误还是立即到期取决于 API。
  • 绝对 deadline 只能阻止预算被重置，不能凭空制造 CPU、总线或外设容量。准入仍需 WCET、阻塞和干扰上界。

练习与可判定答案

  1. 1 kHz、32 位 tick 多久回绕？为什么安全 horizon 不是 49.7 天？ 回绕约 49.71 天；仅凭两个低 32 位端点判序的无歧义前向范围必须小于半圈，即约 24.85 天，并且不能漏掉完整回绕。
  2. 任务每轮计算 3 ms 后 osDelay(10)，周期是否为 10 ms？ 否。忽略干扰也约为 13 ms，并持续漂移；应以绝对释放基准运行并定义 overrun 策略。
  3. 剩余 5 tick、服务 WCET 5 tick，在本文严格契约下能否准入？ 不能。完成最早只能等于 deadline，而本文要求严格早于。
  4. 等待 100 ms，30/60/90 ms 收到无关通知；每次重新等待 100 ms 会怎样？ 最终可拖到 190 ms。正确做法是入口冻结 deadline，每次只等待 remaining。
  5. wall clock 回拨后是否应延长 SPI 请求 deadline？ 不应。持续时间使用单调域；墙钟只影响日历/显示语义。
  6. 验收任务：修改主机脚本，让 before_u32(0, 2^31) 返回任意布尔而不是拒绝。测试必须失败，因为半圈方向无法由两个投影端点唯一确定。
  7. 目标板验收：在回绕前 16 tick 创建 20 tick deadline，要求入口不超时、回绕后第 13 tick 尚余 7、相等时过期；同时示波器证明周期相位不累计漂移。
  8. 1 kHz 下把 1 µs 向上量化为 1 tick，能否据此调用 osDelay(1) 保证至少 1 µs？ 不能。调用可能紧邻 tick 边界；对任意相位的物理最短保证需 2 tick，或使用高分辨率硬件计时。
  9. 周期实例恰在 t=10 完成，deadline=10，下一实例 release=10，结果是什么？ 旧实例在严格契约下 miss；新实例在 t=10 已可释放，不能因此误跳到 t=20。
