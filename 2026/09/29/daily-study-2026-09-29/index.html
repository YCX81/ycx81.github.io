🔧 嵌入式知识：CMake 交叉编译与可复现构建

CMake 交叉编译与可复现构建：先封闭目标语义，再比较字节

“build、host、target”不是任何构建系统都可随意套用的一组同义标签。GNU 构建约定和 CMake 使用了不同的角色模型：GNU 对普通应用通常只有 build/host，对正在构建的编译器等工具才需要第三个 target；CMake 则把运行本次 CMake 的平台称为 host，把本次生成产物面向的平台称为 target。容器、远程执行器或代码生成器的存在本身都不构成 Canadian cross。若术语一开始就错位，后面很容易把“构建机上要运行的工具”“目标平台库”和“新编译器将产生代码的平台”混成一类，构建可能成功，错误却留到部署阶段。

本文把“交叉配置正确”“输出可复现”“目标功能正确”设为三个独立门。规范资料固定为 CMake 4.1 系列官方文档当前补丁页 4.1.6、SOURCE_DATE_EPOCH 规范和 GNU Binutils 官方文档。实际实验固定为 macOS Darwin arm64、Python 3.14.0、CMake 4.1.2、Ninja /opt/homebrew/bin/ninja 1.13.1、AppleClang 21.0.0.21000101、CMAKE_AR=/usr/bin/ar、CMAKE_RANLIB=/usr/bin/ranlib 与 Apple ld-1267。脚本确实在两个绝对路径不同的树中各执行一次 CMake 配置和静态库构建，并从 verbose 命令证明 ar 与 ranlib 被实际调用；但它使用 /usr/bin/cc 与虚构的 Generic/contract-arm64 目标标识，没有真实交叉编译器、没有真实 sysroot、没有链接可执行文件、没有执行目标程序。ld-1267 只是主机 inventory，输出明确写 linker_executed=false。因此本文可得的结论严格限于这个窄环境中的双路径静态归档样例，不能外推到最终链接或固件正确性。

先把 GNU 三角色与 CMake 两角色分开

GNU Autoconf 官方的 target triplet 说明 给出精确定义：--build 是配置和编译这个包的平台；--host 是这个包构建出的程序或库将运行的平台；--target 只在这个包本身是编译器、汇编器等代码生成工具时表示“该工具将为哪个平台产生输出”。因此：

CMake 没有把 GNU 的这三个配置选项原样复制过来。CMAKE_HOST_SYSTEM_NAME/CMAKE_HOST_SYSTEM_PROCESSOR 描述运行本次 CMake 的平台，CMAKE_SYSTEM_NAME/CMAKE_SYSTEM_PROCESSOR 描述本次构建面向的平台。这里的 CMake target 对普通应用有意义，却不是 GNU --target；它更接近普通 GNU 包的 --host。如果先在机器 B 构建一个将运行在 H、输出 T 代码的编译器，再在 H 上运行 CMake 用它构建应用，第一阶段用 GNU 的 B/H/T 三角色描述，第二阶段用 CMake 的 host=H、target=T 描述。把两阶段画开，Canadian cross 才不会被“远程 runner”或“有一个代码生成器”误触发。

实验为此增加了独立的 GnuPlatformRoles 和 CMakePlatformContext。普通 GNU APPLICATION 若传入 target 会返回 GNU_TARGET_ROLE_NOT_APPLICABLE；只有 COMPILER_TOOL 才读取 target。固定示例分别输出 CROSS_APPLICATION 和 CANADIAN_CROSS，从代码层阻止把两套词汇重新揉在一起。

CMake 交叉状态不是操作系统名比较

CMake 4.1 官方 CMAKE_CROSSCOMPILING 说明：显式设置 CMAKE_SYSTEM_NAME 会令该变量为真，即使它与 CMAKE_HOST_SYSTEM_NAME 相同。由此可见，target_system_name != host_system_name 既不是必要条件，也不能覆盖同 OS 异构架构。Linux/x86_64 host 到 Linux/aarch64 target 的两个 system name 都是 Linux，旧代码若只比较 OS 名会错误返回 NATIVE；本文敌对回归要求显式 cmake_crosscompiling=True 时返回 CROSS。反过来，即使 host 与 target 都写成 Linux/aarch64，只要 CMake 声明为 cross，结果仍是 CROSS，因为该布尔量表达的是 CMake 配置模式，不是对产物 ABI 的测量。

本实验对非 Apple-device 平台以实际 CMAKE_CROSSCOMPILING 布尔值作为声明来源，同时把 host/target 的 system name 与 processor 都纳入审计。布尔为假而完整身份不同会返回 CMAKE_CROSS_STATUS_INCONSISTENT；布尔为真则返回 CROSS，但仍需检查编译器 target triple、对象格式和 ABI，不能从这个字符串推导“产物正确”。这样做不是用处理器差异重新发明 CMake 的布尔量，而是把“CMake 自报模式”与“身份交叉检查”分开。

Apple 设备平台是官方明确列出的边界。CMake 文档指出 iOS、tvOS、watchOS、visionOS 等通常由 CMAKE_OSX_SYSROOT 选择 SDK；Xcode generator 还可在构建时切换 device/simulator，所以不推荐用 CMAKE_CROSSCOMPILING 判断 Apple device 构建。实验遇到 Apple device target 时要求 Darwin host 与显式 SDK，返回 APPLE_SDK_DEPENDENT，而不伪装成可靠的 true/false。正式验收要同时记录 CMAKE_OSX_SYSROOT、CMAKE_OSX_ARCHITECTURES、generator、最终 SDK 路径、实际编译命令与 Mach-O slice；漏 SDK 返回 CMAKE_APPLE_SDK_REQUIRED。macOS 自身不属于这个 device 特例，不能把所有 AppleClang 构建一概标成该状态。

工具链文件可能在 try_compile() 的子构建中再次解释。CMake 官方文档建议在其中用 CMAKE_CURRENT_LIST_DIR 解析相对资源，而不要依赖随上下文改变的 CMAKE_SOURCE_DIR 或 CMAKE_BINARY_DIR。若工具链读取未冻结的环境变量，开发机和 CI 可能悄悄选择不同 SDK；应在 configure 输出和缓存中打印最终解析值，并把 SDK 清单纳入构建指纹。

CMAKE_CROSSCOMPILING=true 也不是“真实目标产物正确”的证明。实验将 CMAKE_SYSTEM_NAME 设为 Generic，因此 CMake 正确报告 cross=true，但编译器仍是本机 AppleClang，产物仍是本机对象格式。这是故意的反例：该布尔量描述 CMake 配置关系，不能替代 file/readelf/objdump 对架构、ABI、动态解释器和依赖的验收。

sysroot 与 find root 解决的是两类问题

CMAKE_SYSROOT 通常传给支持它的编译器，使头文件和链接搜索以目标根为基准，并可能影响安装时路径处理；CMAKE_FIND_ROOT_PATH 则给 CMake 的 find_* 命令提供重根前缀。二者可相关，但不是同义词。一个 SDK 可能把编译器内建 sysroot 与额外包根分开；必须记录编译器实际 --sysroot、CMake 搜索轨迹和找到的包配置文件。

交叉构建所需的可执行程序通常要在 host 上运行，例如 protobuf 编译器、设备树编译器、资源打包器；库、头文件和 CMake package 通常必须来自 target。于是常见策略是：

try_compile、try_run 与模拟器的能力边界

CMake 的编译器/特性检查常通过 try_compile() 生成小项目。默认 EXECUTABLE 会同时测试编译和链接；裸机工具链若需要自定义 linker script、启动文件或无法构造通用可执行文件，配置阶段可能错误失败。CMAKE_TRY_COMPILE_TARGET_TYPE=STATIC_LIBRARY 可让检查只产静态库，避免可执行链接。但代价是它没有证明最终链接器、启动代码、内存映射和运行时库正确；正式构建仍需单独链接最小目标镜像并检查 map。

try_run() 比 try_compile() 多一步执行。交叉编译器产生的程序通常不能直接在 host 运行：无模拟器时应明确失败或预填经过审查的结果，不应把“未运行”当“返回零”。CMAKE_CROSSCOMPILING_EMULATOR 可以指定 host 上能运行目标程序的命令及参数，CMake 4.1 文档说明它可用于 try_run()。模拟器通过只证明该模拟器和输入下的行为；涉及真实内核、动态加载器、SIMD、外设或时序的检查仍要在目标上做。

本实验的契约把 cross=true 且 emulator=None 固定为 CMAKE_TRY_RUN_UNAVAILABLE，给出 tuple 形式模拟器才返回 EMULATED。字符串被拒绝，因为它会把命令和参数边界折叠；空 tuple、布尔成员等也必须在调用前得到稳定域错误。

Generator、build type 与 Preset 必须共同冻结

单配置生成器如 Ninja 和 Unix Makefiles 通常在配置时通过 CMAKE_BUILD_TYPE=Debug/Release/... 选择配置；多配置生成器如 Ninja Multi-Config、Visual Studio、Xcode 则在构建时用 --config Release。对多配置生成器填 CMAKE_BUILD_TYPE=Release 常不会产生团队以为的效果。本文契约只允许三种明确 generator，并要求 Ninja Multi-Config 使用 MULTI_CONFIG 标志，单配置 generator 使用四个标准 build type 之一。

Generator 名称与执行该构建图的程序身份也不同。-G Ninja 选择 CMake 生成 Ninja 语法，CMAKE_MAKE_PROGRAM 才指出之后执行哪个 Ninja 二进制；PATH 上两个不同版本都能叫 ninja。版本号用于判断功能集合，内容摘要用于发现同版本二进制被替换，两者都进入证据。本实验要求路径 /opt/homebrew/bin/ninja、版本 1.13.1、SHA-256 9ad851...4322ab 三者同时匹配；任何一个变化都以专门 mismatch 码中止，而不是继续产生一个“可能可复现”的新基线。成立条件是该路径指向本轮读取与执行的同一字节，失效边界是“检查时文件正确、使用前却被替换”的 time-of-check/time-of-use（TOCTOU）竞争；高保证系统还应在只读容器镜像内按 digest 提供工具，本机探针没有做到这一层。

CMakePresets.json 是把 generator、binaryDir、toolchainFile、cacheVariables、environment 及构建/测试工作流版本化的合适入口。Preset 不是锁文件：它不会自动固定编译器二进制内容、SDK 包或下载依赖。应把用户本地覆盖放入 CMakeUserPresets.json，而把可共享 preset 纳入版本控制；生产 preset 还要明确是否继承环境、warning/error 策略和安装配置。

本文的 PresetContract 保留 cache variable 的有序 tuple，逐项验证键和值后才检查重复。若先把它转成 dict，重复键会被后项静默覆盖，审计无法知道调用方传了冲突配置；因此 preset_duplicate 必须返回 CMAKE_CACHE_VARIABLE_DUPLICATE。

依赖、ABI 与 RPATH 是产物语义的一部分

只锁源码仓库提交仍不够。构建输入包括编译器和 linker、sysroot、libc、C/C++ 标准库、生成器、CMake 模块、代码生成器、环境、依赖源码及补丁。FetchContent 的 URL 应有加密摘要或不可变 commit；包管理器 lockfile、镜像摘要与 license metadata 应进入材料清单。依赖名称不可重复，每个 digest 必须是完整 SHA-256；实验把 list/dict/坏摘要分别映射到稳定错误。

ABI 兼容至少检查 target triple、端序、字长、指令集基线、硬/软浮点 ABI、调用约定、结构体对齐、C++ 标准库、异常/RTTI、符号版本与 libc 最低版本。两个文件 hash 相同当然不能同时是两个不同目标的正确产物；实验故意对“同 hash 但期望 target 不同”返回 BUILD_TARGET_MISMATCH，说明身份检查先于字节比较。

ELF 与 Mach-O 动态产物还需审核加载路径。CMake 的 BUILD_RPATH 与 INSTALL_RPATH 分别描述 build tree 和安装产物的 runtime path；两者阶段不同，清理前者不自动证明后者安全。ELF 的 RPATH/RUNPATH 是动态加载器查找共享对象的目录元数据，两者在与环境变量、直接/间接依赖交互时的优先级并不完全相同；Mach-O 的 install name 标识依赖名称，LC_RPATH 为 @rpath 提供候选根。$ORIGIN 是 ELF loader token，按装载对象所在目录展开；@loader_path 是 Mach-O token，按发起装载的 Mach-O 文件所在目录展开。它们与普通字符串前缀不同：$ORIGIN/../../tmp 虽以可信 token 开头，规范化后仍逃逸到祖先目录，不能因 startswith("$ORIGIN") 而通过。

构建目录或用户目录绝对路径会使产物不可搬移、泄漏主机路径，也可能让攻击者可写目录进入库搜索。相邻但不同的风险是“路径可搬移但目录权限不安全”：即使 $ORIGIN/lib 通过本文语法门，若安装目录可被低权限用户写入，loader 仍可能载入恶意库；因此语法验收不能替代部署后的 owner/mode、签名与真实加载检查。反过来，某个绝对系统路径未必在所有平台都恶意，但它破坏本文面向可搬移产物的窄策略，所以仍拒绝。

运行路径不能只由“字符串出现在总白名单里”决定，还必须绑定产物种类、文件格式和 target。静态 archive 根本没有动态 loader；裸机目标即使可执行文件采用 ELF 容器，通常也由启动代码/linker script 装载，不具有 Linux 动态加载器的 $ORIGIN 语义。相反，Linux ELF 与 Apple Mach-O 的 token 名称和展开规则不同。若把 $ORIGIN/lib 与 @loader_path/lib 放入同一个无上下文集合，Linux 产物会接受 Mach-O token，Mach-O 也会接受 ELF token，字符串虽“可信”，语义却落在错误加载器上。

修复后的 ArtifactContract 同时要求 target_triple、abi、artifact_kind、binary_format、依赖和 runtime_paths。本实验故意采用窄的 fail-closed 矩阵：

family 不能通过“任一 component 等于 none”识别。本文把窄契约明确解析为 arch-vendor-os[-abi...]：至少三个非空 component，只允许小写化后的字母、数字、下划线、加号和点；第三项才是 OS 判决位。先检查 OS=linux，再检查 OS=darwin[版本]/macos，最后才把 OS=none/eabi/elf 归为 bare metal。于是 aarch64-none-linux-gnu 和 arm-none-linux-gnueabihf 的 none 是 vendor，OS 明确是 Linux，两者携带 $ORIGIN/lib 都必须接受；arm-none-eabi 的第三项 eabi 才是本文的 bare-metal 标志。只有一个 component 的 linux 或含空 component 的 aarch64--linux-gnu 返回 BUILD_TARGET_TRIPLE_MALFORMED，不会被猜测补齐。

STATIC_LIBRARY 与 ARCHIVE 必须成对；静态产物出现任何 runtime path 返回 BUILD_STATIC_RPATH_FORBIDDEN。bare-metal target 的任何 runtime path 返回 BUILD_BARE_METAL_RPATH_FORBIDDEN。Linux/ELF 使用 @loader_path/lib、Mach-O 使用 $ORIGIN/lib 均返回 BUILD_RPATH_FORMAT_MISMATCH；Linux target 声称 Mach-O、Apple target 声称 ELF返回 BUILD_FORMAT_TARGET_MISMATCH；x86_64-w64-mingw32 或未知 OS 强行搭配 ELF 返回 BUILD_TARGET_FAMILY_UNSUPPORTED，不会因“不是 Apple”就被当成 Linux。family 只看解析后的第三个 OS component；x86_64-notlinux-gnu 和 arm64-evilapple-unknown 仍是未知 family，不能用 substring 或 vendor 伪装。这个策略明确允许 bare-metal executable/ELF 作为对象容器，但明确禁止给它附加动态运行路径。

在通过上述联合契约后，验证器才按 POSIX 路径语义识别绝对路径，拒绝反斜杠、空段、.、..，并检查该格式自己的精确 token；因此 $ORIGIN/../../tmp 与 @loader_path/../../tmp 返回 BUILD_RPATH_TRAVERSAL，/home/dev/out/lib、/var/tmp/evil、/Users 返回 BUILD_RPATH_HOST_LEAK，无 anchor 的 lib 或更深的 $ORIGIN/lib/plugins 返回 BUILD_RPATH_POLICY。为什么集合如此窄：静态模型没有读取实际 ELF/Mach-O，也没有目标部署权限信息，放宽到任意相对路径会制造无法证实的安全结论。实施时先用 file/readelf 或 file/otool 独立确认真实格式和 target，再从 readelf -d 或 otool -l 提取每个 loader entry，逐项送入匹配策略；最终还要在只含安装内容的只读目录中启动程序并记录 loader trace。本文实际构建的正例是 bare-metal 标识的静态 archive，所以其 RPATH 为空；Linux ELF 与 Mach-O 只是类型化契约正例，没有生成或加载动态产物。

时间是首要噪声源。SOURCE_DATE_EPOCH 规范 给构建工具一个由发行过程确定的 Unix 时间上界，用于替代“当前时间”；它不是要求把所有文件 mtime 随意改成零，也不自动影响所有工具。源码中的 __DATE__/__TIME__、归档成员 timestamp、压缩头、PE/Mach-O 元数据、签名、生成文档日期都需分别治理。签名可能有安全要求的时间戳，通常应把可复现的 unsigned payload 与不可复现但可验证的签名封装分层比较。

路径会进入 __FILE__、DWARF、宏、map 和诊断；GCC/Clang 的 prefix-map 选项用 old=new 把路径前缀替换成稳定名称，但 file、debug、macro 三类选项影响的载体不同，不能设置一个就宣称全部覆盖。old 是要匹配的源前缀，new 是替换值；空映射 = 没有定义任何有意义的来源闭包，若只检查“字符串里含等号”就会被误收。实验策略要求恰好一个 =、old 为非根的规范化绝对 POSIX 路径、new 为非空且无 .. 的相对路径或精确的 .。所以 /workspace=. 通过，而 =、=.、/workspace=、workspace=. 均返回 BUILD_PREFIX_MAP_POLICY。该规则为什么存在：recipe fingerprint 只有在映射本身可解释时才代表语义输入；失败边界是平台允许但超出本实验语法的高级映射会保守拒绝，需要先扩展并回归策略，不能绕过。

locale 影响排序和消息，timezone 影响日期格式，文件系统遍历顺序影响归档顺序，umask 影响权限，用户/组影响归档元数据，并发和随机 seed 可能改变链接布局。环境闭包是传给子进程的键值集合；“覆盖几个变量”与“禁止继承其余变量”不是一回事。若先复制整个 os.environ 再更新 LC_ALL，CPATH、LIBRARY_PATH、SDKROOT、CMAKE_PREFIX_PATH、编译 flags 或包管理器变量仍可成为隐藏输入。本次探针不继承父环境，只传九个键：COPYFILE_DISABLE,HOME,LANG,LC_ALL,PATH,SOURCE_DATE_EPOCH,TMPDIR,TZ,ZERO_AR_DATE；HOME 与 TMPDIR 指向本次临时根，PATH 固定为 /opt/homebrew/bin:/usr/bin:/bin，关键工具又用绝对路径锁定。它仍不是容器级隔离：工具可以读取系统 SDK、系统配置、内核与文件系统状态，因此结论只能覆盖当前 macOS 主机上的小型静态库样例。

实验的 ReproducibilityContract 同时冻结 LC_ALL=C、TZ=UTC、SOURCE_DATE_EPOCH=1700000000、/workspace=. 前缀映射、确定性归档、编译器/linker inventory、Ninja 路径/版本/摘要、CMAKE_AR 与 CMAKE_RANLIB 路径/摘要；这些字段都进入 recipe fingerprint。改变 epoch 会改变 fingerprint，工具摘要变化也会改变 fingerprint。实际 CMake 子项目则把两个真实临时 source 路径分别映射到 .，这是构建命令中的工作路径消除；/workspace=. 是独立 contract 示例，不应误读为本机真的存在 /workspace。

GNU ar 及 objcopy/strip/ranlib 的确定性模式会规范化部分 UID、GID、timestamp 和 mode；Apple 工具链使用不同实现。本次实际探针在 toolchain file 中显式设置 CMAKE_AR=/usr/bin/ar、CMAKE_RANLIB=/usr/bin/ranlib，检查二者完整 SHA-256，使用 Ninja --verbose 证明每个树的 archive 命令确实调用二者，并通过 ZERO_AR_DATE=1 与 COPYFILE_DISABLE=1 获得相同 libprobe.a。Ninja 也由 CMAKE_MAKE_PROGRAM=/opt/homebrew/bin/ninja 固定为 1.13.1 并校验内容摘要。/usr/bin/ld -v 仅做 inventory；由于 try_compile 和目标都是静态库，实际命令没有链接可执行文件，故证据写 linker_executed=false。这只能证明上述工具和九键环境下的两个独立路径静态库样例相同，不可外推到 ELF、固件镜像、签名包或 linker 行为。

故障注入、定位和回归闭环

实验敌意矩阵先覆盖平台语义：CMake context 的 None/dict、host processor 布尔伪装、cross 标志字符串、未知 generator、Linux/x86_64 host 到 Linux/aarch64 target 却声称 cross=false、Apple device 漏 SDK；GNU roles 的 None、未知 package kind、普通应用滥用 target、编译器工具漏 target。之后才覆盖 Toolchain/Preset/Artifact/Repro contract 的 None/dict/list/string 错型，成员 bool/complex/NaN/正负无穷/巨大有限数，未知 find mode、无 emulator 的 try_run、重复 cache key、重复依赖、坏摘要、loader token 后的 ..、任意主机绝对 RPATH、未锚定相对 RPATH、空或相对源 prefix map、坏工具摘要、相对归档器路径、target/ABI 不匹配、非法 epoch、错误 locale/archive 策略、空语义输入与派生乘法溢出。所有容器都先验证精确类型和逐项成员，再做 set/去重/算术，避免原生异常、substring 误接收或先规范化后丢失攻击痕迹。

当双构建不一致时，先确认源码与依赖摘要相同，再 diff 构建命令和环境；然后用 diffoscope 或格式专用工具从归档成员、节区、debug、符号表、时间戳、路径逐层找第一个差异。找到隐藏输入后，把它纳入 manifest 或规范化策略，并增加两个独立目录的回归。若字节一致但目标失败，则转到 ABI/链接/运行诊断，不能继续“修复复现”。若目标正确但构建不可复现，仍需关闭供应链证据缺口。修复必须在干净环境复跑全矩阵、检查产物身份并在目标上验证，最后保存命令、日志、摘要与工具版本。

本次实际注入并修复的完整闭环选用 RPATH 前缀与平台语义绕过。第一组现象是旧黑名单只拒绝若干开头；把 "/Users/"、"/tmp" 与 "/build/" 条件逐项代入可知，$ORIGIN/../../tmp、@loader_path/../../tmp、/home/dev/out/lib、/var/tmp/evil 与精确 /Users 均不命中并会意外接受。其中前两项在 loader 展开 token 后通过 .. 逃逸，后三项则利用未枚举的绝对目录或缺少结尾斜杠。第一假设是“字符串黑名单没有表达 loader 归一化语义，也没有定义允许集合”。本次实际执行的修复后最小探针显示两个 traversal 精确返回 BUILD_RPATH_TRAVERSAL，三个绝对路径返回 BUILD_RPATH_HOST_LEAK，定位到 validate_runtime_path() 的结构门。

第二组现象更隐蔽：把两个合法 token 合并成总 allowlist 后，Linux/ELF 会接受 @loader_path/lib，Mach-O 会接受 $ORIGIN/lib；更早的主正例甚至给 arm-none-eabi 静态 archive 配置 $ORIGIN/lib。这些字符串都在集合里，所以继续增加路径黑名单无法修复。第二假设是“runtime token 没有绑定 artifact kind、binary format 与 target family”。证伪回归分别返回 BUILD_RPATH_FORMAT_MISMATCH、BUILD_STATIC_RPATH_FORBIDDEN 和 BUILD_BARE_METAL_RPATH_FORBIDDEN；Windows/未知 target+ELF 以及 notlinux/evilapple substring 伪装则以 BUILD_TARGET_FAMILY_UNSUPPORTED fail closed，排除“只要不是 Apple 就默认 ELF/Linux”或模糊字符串匹配的旁路。修复初版又暴露第三个反例：把任意 none component 当 bare metal 会误拒 vendor=none 的合法 Linux triple。最终实现改为第三个 OS component 决策，并用上述两个 Linux 正例锁住优先级；这证明拒绝邻域和接受邻域必须同时存在。

修复不是继续添加 /home、/var/tmp 等黑名单，而是先验证联合产物契约，再按 POSIX/loader 结构拒绝绝对路径和任何 ./../空段，最后只允许当前格式自己的唯一 token。主正例改为 arm-none-eabi + STATIC_LIBRARY + ARCHIVE + runtime_paths=()；两个动态正例分别是 Linux/ELF/$ORIGIN/lib 与 Apple/Mach-O/@loader_path/lib，且明确只执行类型化验证。回归覆盖两个合法 anchor、两种 token 交叉误用、bare-metal/static 禁止路径、Linux/Mach-O 格式反配、Windows/未知 target、五个原绕过、无 anchor 的 lib、超出集合的 $ORIGIN/lib/plugins、重复路径、错误成员类型、target/ABI 门以及两树 archive 比较。实际动态目标的后续验收仍是提取 loader metadata、检查安装目录权限并在隔离目标上启动；本文没有执行那一层。若将来产品确需 Windows PE 或另一合法路径，变更流程是先写清目标格式、loader 展开、目录权限和部署布局，增加拒绝邻域与真实加载测试，再扩大矩阵；不能临时把未知 target 归到现有平台或关闭门。

同一轮还闭合了工具身份和环境证据：旧探针只读取 /usr/bin/ld -v，但静态库根本没有执行 linker，且完整继承父环境。修复后 CMake cache 同时观察 CMAKE_MAKE_PROGRAM/CMAKE_AR/CMAKE_RANLIB，verbose 输出证明 archive tools 执行，路径、版本与完整摘要进入证据和 recipe fingerprint；子进程环境改为九键 allowlist。回归要求 archive_tools_executed=YES、environment_narrow=YES 与 linker_executed=false 同时成立。这样不会把“主机有某个 linker”升级为“该 linker 生成了被比较的产物”，也不会把一次双路径静态归档升级为全供应链 hermetic build。

练习与确定答案

  1. CMAKE_CROSSCOMPILING=true 能否证明使用了真实目标编译器？答案：不能；本文探针就是反例。
  2. host 代码生成器通常应由哪类搜索找到？答案：find_program 的 host 搜索，常用 mode NEVER。
  3. target 库通常应使用什么 mode？答案：CMAKE_FIND_ROOT_PATH_MODE_LIBRARY=ONLY。
  4. STATIC_LIBRARY try-compile 证明了最终 linker script 正确吗？答案：没有，它刻意避开可执行链接。
  5. cross try-run 没有 emulator 时本文结果是什么？答案：CMAKE_TRY_RUN_UNAVAILABLE。
  6. Ninja 与 Ninja Multi-Config 的 Release 选择时机相同吗？答案：不同，前者通常配置时，后者构建时 --config。
  7. Preset 能否自动固定 SDK 内容？答案：不能，还需不可变镜像、版本和摘要。
  8. 两个同 hash 文件能否分别满足两个不同 target triple？答案：本文先返回 BUILD_TARGET_MISMATCH。
  9. $ORIGIN/lib 是否表示任意 RPATH 都安全？答案：不是；仍需加载器和目录权限安全审计。
  10. SOURCE_DATE_EPOCH 是否自动消除所有时间来源？答案：不会，各工具和源码宏仍需单独治理。
  11. 为什么双构建必须用独立绝对路径？答案：暴露工作路径和缓存等未声明输入。
  12. 字节相同是否证明固件正确？答案：不证明，只证明当前声明输入下可复现。
  13. 本文是否使用了真实 /opt/contract/sysroot？答案：没有，它只是 find-root 契约值。
  14. 本文是否执行了目标二进制？答案：没有，target_binary_execution=false。
  15. $ORIGIN/../../tmp 为什么不能因 $ORIGIN 前缀而接受？答案：loader 展开并规范化后 .. 会逃逸允许的 lib 子目录；实验返回 BUILD_RPATH_TRAVERSAL。
  16. /home/dev/out/lib 不在旧 /tmp 黑名单中是否即可接受？答案：不能；本文可搬移产物策略拒绝所有绝对 runtime path，返回 BUILD_RPATH_HOST_LEAK。
  17. $ORIGIN/lib 通过语法门能否证明目录安全？答案：不能，还必须在部署后检查 owner/mode、可写性、签名和真实 loader trace。
  18. prefix map = 有什么问题？答案：来源与目标都为空，不能定义可审计的路径替换；当前返回 BUILD_PREFIX_MAP_POLICY。
  19. 为什么要分别冻结 Ninja、CMAKE_AR 和 CMAKE_RANLIB？答案：Ninja 执行构建图，ar 创建 archive，ranlib 写符号索引；它们会影响静态库字节，不能用未执行的 linker 身份代替。
  20. linker_inventory=ld-1267 是否表示本次归档由该 linker 生成？答案：不是；静态库路径没有链接可执行文件，证据明确为 linker_executed=false。
  21. 设置 LC_ALL=C 后继承全部父环境是否已 hermetic？答案：没有，CPATH、SDK 与包搜索变量仍可能成为隐藏输入；本实验改为九键 allowlist，但也不等同容器级隔离。
  22. 两树 libprobe.a 相同的最强结论是什么？答案：在当前 macOS、固定工具摘要、九键环境和该小型静态库输入下字节相同；不能外推到 ELF、固件、签名包或真实目标功能。
  23. GNU 普通应用的部署平台应叫 host 还是 target？答案：叫 host；GNU target 只对正在构建的编译器等代码生成工具有意义。
  24. 远程 runner 是否自动构成 Canadian cross？答案：不是；必须是在交叉构建一个将运行于 host、又为不同 target 产生代码的编译器工具场景。
  25. Linux/x86_64 到 Linux/aarch64 能否因两个 CMAKE_*_SYSTEM_NAME 都是 Linux 而判为 native？答案：不能；处理器不同，且本例实际 CMAKE_CROSSCOMPILING=true，回归结果为 CROSS。
  26. host 与 target identity 完全相同但显式设置 CMAKE_SYSTEM_NAME 时，CMake 的变量可能是什么？答案：仍为 true；实验边界 forced_same_identity_cross=CROSS 锁定这一点。
  27. 为什么 Apple device 返回 APPLE_SDK_DEPENDENT 而不是简单 CROSS？答案：目标平台由 SDK 间接选择，Xcode 还可在构建时切换 device/simulator，CMake 官方不建议用该布尔量判断 Apple device 构建。
  28. APPLE_SDK_DEPENDENT 能否证明最终 slice 正确？答案：不能；还需审核 SDK、architectures、编译命令和实际 Mach-O slice。
  29. bare-metal 静态 archive 的 runtime path 应是什么？答案：空 tuple；它没有动态 loader，主正例不再错误携带 $ORIGIN/lib。
  30. Linux ELF 能否因为 @loader_path/lib 在总白名单里就接受？答案：不能；这是 Mach-O token，联合契约返回 BUILD_RPATH_FORMAT_MISMATCH。
  31. x86_64-w64-mingw32 + ELF 为什么不是当前契约中的合法组合？答案：本文没有实现 Windows PE/loader 策略，也不能把“非 Apple”默认成 Linux；它以 BUILD_TARGET_FAMILY_UNSUPPORTED fail closed。
  32. x86_64-notlinux-gnu 能否因字符串中含 linux 而进入 Linux 策略？答案：不能；family 只按 triple 的精确 component 匹配，该输入返回 BUILD_TARGET_FAMILY_UNSUPPORTED。
  33. aarch64-none-linux-gnu 中的 none 表示什么，为什么允许 $ORIGIN/lib？答案：它位于 vendor 槽；第三个 OS component 是 linux，所以该动态 ELF 正例返回 ACCEPT。
  34. linux 这一个单词能否当作完整 target triple？答案：不能；本文至少要求 arch-vendor-os 三项，返回 BUILD_TARGET_TRIPLE_MALFORMED。

官方一手资料与来源

  • CMake 4.1.6 官方 cmake-toolchains(7) 说明 toolchain file、cross-compiling、sysroot、find-root modes 与 STATIC_LIBRARY try-compile；本文实际工具为 4.1.2，二者版本边界单列。
  • CMake 4.1 官方 CMAKE_CROSSCOMPILING 明确显式设置 CMAKE_SYSTEM_NAME 时即使与 host 名相同也会为真，并说明 Apple device SDK/Xcode 边界；CMAKE_HOST_SYSTEM_NAME 与 CMAKE_HOST_SYSTEM_PROCESSOR 给出 CMake host 身份。
  • CMake 4.1.6 官方 cmake-presets(7) 定义共享/用户 preset、configure/build/test 等结构。
  • CMake 4.1.6 官方 CMAKE_CROSSCOMPILING_EMULATOR 说明 host 上运行目标程序及 try_run() 的适用关系。
  • CMake 4.1 官方 CMAKE_MAKE_PROGRAM、CMAKE_AR、CMAKE_RANLIB 定义本实验实际冻结的生成器执行程序、归档器和索引工具；BUILD_RPATH 与 INSTALL_RPATH 区分构建树和安装产物的加载路径。
  • Reproducible Builds 项目的 SOURCE_DATE_EPOCH specification 定义时间上界变量的语义和采用要求。
  • GNU Binutils 官方 ar 与 objcopy 确定性归档选项 说明归档元数据规范化；本次 macOS 实跑使用 Apple 工具链，不声称执行 GNU Binutils。
  • GNU Autoconf 官方 Specifying Target Triplets 定义 build/host/target；GNU Automake 官方 Cross-Compilation 说明普通交叉应用通常只需 build/host，而为交叉编译器增加 target 才进入 Canadian-cross 三角色语境。
