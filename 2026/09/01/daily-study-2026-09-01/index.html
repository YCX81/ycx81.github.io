🔧 嵌入式知识：消息队列、背压与容量设计

队列长度从 16 改成 64 后，压力测试晚四秒才失败，这不是修复，只是扩大了事故蓄水池。消息队列能解耦执行时刻，却不能改变长期到达率 (\lambda) 与服务率 (\mu)：若 (\lambda>\mu)，任何有限容量最终都会满；若平均速率可承受，突发、调度抖动和最慢服务时间仍决定所需容量。

本文以 NUCLEO-H743ZI2、FreeRTOS 11、ADC DMA 半缓冲 ISR → 处理任务 → Ethernet 上传任务为例，主机用 Python 3 做确定性离散事件实验。FreeRTOS queue 默认按值复制固定大小 item；传指针时队列只复制地址，生命周期由应用负责。FreeRTOS 官方 Queue 文档给出任务/ISR API 与复制语义。

1. 容量从最坏突发推导，不从“常用 16”继承

在长度为 (T) 的最坏窗口内产生 (A(T)) 条，消费者至少完成 (S(T)) 条，忽略初始积压时所需槽位下界为：

[
Q_{min}=\max_T\left(A(T)-S(T)\right)+J+R
]

其中 (J) 吸收调度/中断抖动，(R) 是可解释的工程裕量。例：DMA 每 1 ms 产生一条，Flash 擦除使消费者停 12 ms，恢复后每 0.5 ms 处理一条；停顿窗口至少积压 12 条，再加 ISR 已在途的 1 条和 25% 裕量，容量取 16 是推导结果，不是习惯。

RAM 预算包含 queue_length * aligned_item_size、控制块、指针所指缓冲池与 allocator 元数据。把 2 KiB payload 直接入队会在临界区复制；更合理的是预分配池中存 payload，队列传 {slot,generation,len} 描述符。所有权状态是：

Zephyr message queue 文档同样明确 fixed-size item、复制和 ISR 不等待的约束；API 名不同，所有权推理相同。不能拿 FreeRTOS 的 ISR 函数直接类比 Zephyr timeout 行为。

队列 API 成功不等于业务完成

生产者成功入队，只证明队列接受了副本或指针。消费者可能在处理前被删除、消息过 deadline、网络发送失败或系统复位。需要业务完成语义时，描述符带 message_id，消费者在最终持久化/发送确认后回 completion；生产者超时不能擅自释放仍由消费者拥有的缓冲，而应发送取消请求或通过共享状态机竞争所有权。

一个安全状态可用 CAS 表达：QUEUED -> RUNNING -> DONE，取消只能把 QUEUED -> CANCELLED；若已经 RUNNING，取消者等待完成或把“忽略结果”标志交给消费者。直接让 timeout 任务和消费者都 free() 会形成双重释放。任务被强制删除尤其危险，因为 finally/cleanup 不一定运行；优先采用协作停止，让任务排空或显式归还持有的 slot。

队列 reset 也不是通用恢复。FreeRTOS xQueueReset 清队列控制状态，却不知道指针 item 指向的对象归谁；reset 前必须遍历/撤销所有描述符或重建整个池 generation。否则看似空队列留下永久泄漏，随后旧 callback 又可能释放已复用的 slot。

4. 背压策略要按消息类别分流

安全告警使用独立小队列并预留池；控制命令有 message ID 和 deadline，满时明确 NACK；普通遥测可降采样或合并为最新状态；日志可按严重度丢弃。一个优先级队列虽避免告警被日志阻塞，却可能让低优先级永久饥饿，因此给高优先级设置最大突发并保留最低服务份额。

阻塞生产者会把压力传回上游。任务上下文中这可能正确，但锁内阻塞会造成死锁，控制环阻塞会错过 deadline，高优先级任务等低优先级消费者会形成优先级反转。入队等待上界应小于端到端 deadline 减去最坏后续服务时间，超时必须进入业务可见路径。

队列深度只是快照。至少记录：高水位、每类满队列次数、驻留时间直方图、生产/消费速率、池占用、丢弃原因和端到端完成率。深度低但 P99 驻留高可能是大消息队头阻塞；高水位单调上升说明持续欠载；周期尖峰才适合用容量吸收。

公平性、队头阻塞与合并

将告警、命令和遥测放进三个 FIFO 后，消费者也要有调度合同。严格优先级在持续告警风暴时会饿死命令；简单轮询又可能让 4 KiB 日志块占据网络。可采用每轮最多处理 8 alert, 4 command, 2 telemetry，未使用配额可借用，并给每类定义最大驻留 deadline。调度单位应按预计处理成本或字节，而不只是消息条数。

“合并最新状态”需要原子定义。队列中已有 sensor-7 状态时，新状态可替换旧值，但消费者可能同时取走。更简单的实现是每个 sensor 一个 mailbox 加 dirty bitmap，生产者原子写最新值并置位，消费者交换 dirty 后读取快照；事件日志仍走 FIFO。这样状态频率再高，内存也与传感器数量相关，而非时间相关。

队头阻塞可通过把耗时任务拆成有界 chunk 缓解，但拆分后要保存 continuation 并允许高优先级插入。若底层外设事务不可抢占，最坏阻塞时间就是单次事务 WCET；容量与 deadline 计算必须使用它，而不是平均处理时间。

5. 第二个实跑模型：容量公式与持续过载

确定性模型不替代实测 WCET。把测得的生产到达曲线和消费者最慢服务曲线导入同一计算，包含调度暂停、网络重试和 Flash 操作；再用板级故障注入验证峰值不超过计算。

RAM 满以后不能悄悄转移到 Flash

网络离线时把遥测写 Flash 是第二个有界队列，不是无限容量。需要定义分区大小、写放大、磨损、断电原子性和保留策略。安全事件可保留最近与最严重记录，普通遥测按时间窗降采样；Flash 满时策略必须在规格里可见。若上传端重试不带持久 message ID，设备复位后会重复提交旧记录。

从 RAM 转持久队列的 ownership 是：先写带 CRC 的新 record，提交索引后才能释放 RAM；上传得到业务确认后以 append-only tombstone 或原子游标标记消费。断电测试覆盖 payload 写到一半、索引更新前后和擦除切换，恢复扫描不能把半条记录当有效消息。

6. 从测量回填容量，而不是测试后拍脑袋

在开发板上用 DWT cycle counter 测 ISR 入队、消费者每阶段和最长不可抢占区；用 monotonic timestamp 写入 descriptor，消费时计算驻留。采集至少一个业务最坏周期而非几十秒演示，并保存原始直方图。容量计算采用观测到的最坏突发和保守服务下界，再乘明确裕量；如果结果超过 RAM 预算，必须降低上游速率或改变业务策略，不能偷偷缩小 item 后继续溢出。

每次固件升级都跑同一过载基准，因为日志、TLS 握手或 Flash 驱动变化会改变消费者 WCET。CI 的通过条件同时约束高水位、P99 驻留、丢弃类别和池守恒；只检查“系统没崩”会让静默数据丢失通过。

7. 可复现实验与故障定位链

准备 NUCLEO-H743ZI2、ADC 定时触发 DMA、FreeRTOS runtime stats、可控制速率的 PC TCP server。配置 16 槽 descriptor queue 和 20 个 buffer。先让 server 正常消费，后暂停读取 5 秒，再恢复。记录 queue/pool 高水位、每条消息驻留、ISR WCET、drop 分类和恢复时间。通过标准：RAM 恒定；队列不越界；告警零丢失；遥测按已声明策略丢弃；恢复 10 秒内回到低水位。

真实故障注入：把网络任务在 socket timeout 路径的 pool_release() 删除。现象是队列深度恢复为零，但运行数分钟后 pool_free 降到零，DMA ISR 开始丢消息。假设包括队列容量不足、消费者太慢和缓冲泄漏。证据显示生产/消费率恢复正常、queue 高水位不再上升，但 allocated-released 差值随每次 timeout 增一；generation 日志指出 slot 停在 TX_OWNED。

定位为错误路径所有权未闭合。修复把 success、timeout、cancel、disconnect 汇聚到单一 cleanup，并用状态机断言只释放一次。回归注入 1000 次 timeout、任务删除和网络重连，最终 free==pool_size、重复释放计数为零，再跑消费者暂停确认容量策略仍成立。

8. 练习与判定标准

  1. 生产者 2 kHz，消费者停 8 ms，恢复后 4 kHz。最少吸收 16 条；答案还需加入在途与抖动裕量。
  2. 为命令、告警、温度、调试日志分别选满队列策略，并说明为何；四类全部写成 drop-old 判失败。
  3. 修改两个 Python 模型加入 deadline。过期消息必须在执行前丢弃并按类别计数。
  4. 审计所有权路径。成功、满队列、timeout、取消、任务重启各跑 1000 次，池最终全空闲且无双重释放。
  5. 给出“队列深度低但延迟高”的复现。合格答案包含队头大任务或消费者批处理证据，而非简单扩容。
