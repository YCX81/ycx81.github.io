IELTS 每日学习 — 2026-08-08

发表于 2026-08-08 分类于 每日学习 本文字数： 3.9k 阅读时长 ≈ 14 分钟

今日主线：IELTS Academic 周末整合复习与主动输出。

🔧 嵌入式知识：Ethernet：MAC、PHY、链路协商与 DMA

平台：NUCLEO-H743ZI2（STM32H743 Cortex-M7）+ 板载 Microchip LAN8742A 10/100 PHY，RMII 接口，STM32CubeH7 HAL 与 lwIP，Linux 笔记本作为对端。本文聚焦链路建立到 DMA 收发；IPv6、PTP、VLAN、checksum offload 另行验证。

1. Link LED 亮，只证明四层状态机中的第一层

现场设备显示 100M full-duplex，却拿不到 DHCP 地址。重启 PHY 偶尔“恢复”，于是团队把问题归为线缆；实际可能是 RX descriptor 没归还 DMA，或者 CPU 读到 D-Cache 中的旧 descriptor。要避免这种误诊，先画清四个相连但不同的状态机：

PHY link up 不证明 RMII 数据引脚、MAC 配置、DMA ring 或 IP 层正常；能读 PHY ID 也只证明 MDC/MDIO 管理通道，不证明 50 MHz REF_CLK、TXD/RXD 和磁性器件路径。Arm CMSIS-Driver 明确把 MAC 与 PHY 分成两个接口，PHY 通过管理读写获得 link/speed/duplex，再让 MAC按结果配置（CMSIS Ethernet Interface）。

2. 从 PHY reset 和 strap 开始建立可观测基线

LAN8742A 在复位/上电采样 strap，决定 PHY 地址、模式等默认状态；strap 电阻既要满足逻辑阈值，也不能被 MCU 提前驱动。其自协商只属于物理层，完成后可从 Basic Status 和 Special Control/Status 读取 link 与协商结果（Microchip LAN8742A Datasheet）。

MDIO 诊断第一步扫描 0–31 地址，读取 PHYIDR1/2。读到全 0xFFFF 常见于无响应/上拉，0x0000 可能是复位、总线被拉低或时钟错误；不能把任一值当有效 ID。BMSR 某些状态具有 latch-low 语义，读取两次才能得到当前 link，同时保留第一次读值用于判断曾经掉线。

实际 PHY 地址必须来自 NUCLEO 板卡原理图/strap 与扫描结果，不能因为某个 Cube 示例写 0 就硬编码。复位释放后等待 datasheet 规定时间，再轮询 reset bit 清零与 auto-negotiation complete，并设置总超时。超时日志至少保存 PHY ID、BMCR、两次 BMSR、vendor special status 和时间戳。

自协商双方交换能力并选择共同模式。强制一端 100/full、另一端保持 auto-negotiation，auto 端可能通过 parallel detection只识别速度而不能可靠得知 duplex，形成一端 full、一端 half。小流量 ping 可能通过，满载时 half-duplex 一侧出现碰撞/late collision，full-duplex 一侧表现为 FCS 或丢帧。修复必须让两端都协商或都强制一致，并同时核对交换机端口统计。

3. Link change 不是打印一行日志，而是重新配置 MAC

PHY 从 down 变 up 后，驱动应读取最终 speed/duplex，停止或安全暂停数据路径，更新 MAC configuration，再启用收发；不能只把 netif 标成 up。CMSIS PHY API把 GetLinkState 与 GetLinkInfo 分开，正是为了区分物理状态和协商参数（CMSIS Ethernet PHY Interface）。

link flap 时还要决定协议层语义：停止 DHCP timer 还是保留 lease、清 ARP 邻居还是等待、未完成 TX 如何报错。若直接重建整个 lwIP heap，可能把一个物理抖动扩大为应用连接泄漏。建议 PHY 轮询/中断只发布事件，由网络管理任务串行执行 MAC 与 netif 状态转换。

4. RMII 50 MHz 是数据路径的共同时间基准

RMII 把收发数据压缩到两位总线，MAC 与 PHY共享 50 MHz REF_CLK。MDIO 能工作而 REF_CLK 缺失时，PHY 寄存器完全可读、link LED也可能亮，MAC却收不到有效帧。示波器应在 MCU 引脚测量时钟频率、占空比和启动时序，并根据 NUCLEO 原理图确认时钟由 PHY输出还是外部源提供；不要在 MCU 和 PHY 两端同时驱动。

板级复位时序必须保证 strap采样期间相关 RMII/LED复用脚没有被 MCU强驱。若固件很早配置 GPIO，可能只在暖复位改变 strap结果，造成“断电正常、软件复位失败”。实验要分别覆盖上电复位、NRST和看门狗复位，并在每次保存 PHY ID与 special status。

MAC speed/duplex 配置必须与协商结果一致。100M 时 RMII 仍是 50 MHz，只是每个数据 dibit的有效节奏不同；不能通过测到 50 MHz就宣布速率正确。PHY special status、MAC configuration和交换机端口三方应报告相同参数。

5. 用计数器把线路错误和队列饥饿分开

MAC MMC 统计、DMA channel status和 PHY vendor counter回答不同问题。FCS/alignment error增长而 DMA ring充足，优先查线路、duplex和 RMII时序；RBU/buffer unavailable增长且线上帧正确，说明 CPU没有及时补 RX descriptor；TX underflow 指向 MTL/DMA供数或总线带宽。lwIP memp耗尽又是更上一层，不能用 MAC counter替代。

诊断快照应在故障发生时原子记录：link/speed/duplex、MAC config、MMC delta、DMA status、current descriptor、ring 每个 OWN、pbuf pool余量。只每秒打印累计值会丢失先后关系；用 DWT或统一 tick打时间戳，并在错误后冻结一份 ring镜像。

若抓包看到板端 ARP request但没有 reply进入应用，先确认交换机是否把 reply发回端口；再看 MAC RX frame counter是否增长；再看 DMA descriptor OWN是否清除；最后看 lwIP input是否收到。每一步都有二分价值，比重启整套网络栈更快。

6. Descriptor ring 是 CPU 与 DMA 的所有权协议

STM32H743 Ethernet DMA 使用 normal descriptor。描述符中的 OWN=1 表示 DMA 持有；CPU 只有在 OWN=0 时才能改字段或消费数据。TX 的正确顺序是：填 payload、clean payload cache、填写地址/长度/状态、内存屏障、最后交 OWN、更新 tail pointer。RX 则先确认 DMA 清 OWN，读取状态/长度，invalidate payload，再交协议栈；上层释放 pbuf 后才能把 buffer 归还 DMA。

RM0433 给出 TDES/RDES 与 DMA channel tail pointer 的位级定义；描述符格式不能从旧 STM32F4 示例照搬（ST RM0433 Ethernet DMA）。下面用 non-cacheable descriptor 区和 cacheable、32-byte 独占 line 的 payload，避免 descriptor 自身一致性干扰。位定义按 STM32H743 normal TX descriptor；移植到其他系列必须重查手册。

.eth_desc 必须由 linker 与 MPU 实际配置为 non-cacheable；section 名本身不会改变属性。payload clean 的地址和长度需覆盖完整 cache line，buffer 应独占 line，避免 clean/invalidate 误伤邻居。若 descriptor 仍为 cacheable，则 OWN 与字段也必须按平台规则 clean；只 clean payload 仍会让 DMA 看见旧 descriptor。

三个长度掩码不能合并理解：TX buffer 1 length 在 TDES2 的 B1L 字段，整帧长度在 TDES3 的 FL 字段；DMA 归还 RX normal descriptor 后，接收 packet length 又来自 RDES3 的 PL 字段。本文帧长不超过 1536，因此数值同时落入这些字段范围，但字段位置、位宽与读写方向仍须分别按 RM0433 处理。

RX 最容易被“零拷贝”破坏：协议栈持有 pbuf 时，DMA 不能复用同一 buffer。每个槽位至少有 DMA_OWNED → CPU_READY → STACK_OWNED → FREE → DMA_OWNED 状态。ring 满时应记录 RBU、drop 和高水位；不能悄悄把仍被 TCP 引用的 buffer 重新挂回 descriptor。

示例故意只接受一个 descriptor 内的帧，量产驱动必须处理多 descriptor、错误 summary、FCS stripping 与实际 frame-length 字段。ST AN4839 解释 Cortex-M7 与 DMA 间 clean/invalidate 的方向和按地址维护要求（ST AN4839）。

写 tail pointer不是“把某一个 descriptor地址交给 DMA”的抽象 API，而是告诉 channel可处理范围已经延伸；具体 ring length、tail语义和 resume条件必须按 RM0433。若 DMA因 RBU/TBU暂停，单纯补 OWN却未正确更新 tail/poll demand，ring仍会停。驱动应统计每次暂停原因和恢复动作。

内存屏障也不等于 cache维护：__DMB/__DSB约束访问顺序与完成，不能把脏 payload写回 SRAM；clean执行可见性，仍需在交 OWN前排序。volatile descriptor防止编译器省略字段访问，却不使 cache coherent。三个机制解决不同层级。

7. 从 PHY 到 UDP 的分层实验

准备 NUCLEO、可靠网线、支持端口统计的交换机和 Linux 主机。第一阶段只读 PHY：冷启动 100 次，记录 reset 清零、PHY ID、link、speed、duplex 与协商耗时；通过标准是无错误 ID、双方速率双工一致。第二阶段开 MAC 内部/PHY loopback，发送递增长度帧，区分 RMII 外部路径。第三阶段接真实网络，用 Wireshark 观察板端 ARP request/reply，再运行静态 IP UDP echo，最后启用 DHCP。

Linux 对端用 sudo ethtool -S eth0、ip -s link 和 Wireshark记录 FCS、drop 与包序号；板端每秒保存 PHY snapshot、MAC MMC counters、DMA channel status、RX/TX ring head/tail、OWN 分布、lwIP drop。只有这些时间轴对齐，才能判断“交换机收到了板端 ARP，但板端没把 reply 交给 lwIP”属于 RX DMA，而不是 DHCP server。

压力流量用 64、65、511、512、1514-byte UDP payload 的边界组合，双向各运行一小时；每帧加入 sequence 与 CRC。通过标准：link 不 flap，PHY/MAC error counter不增长，ring 无永久 OWN 卡死，应用序号除明确过载策略外无洞，停止流量后所有 TX descriptor 在规定时间归还。

为验证 backpressure，故意让应用任务停 200 ms，观察 RX ring耗尽、RBU计数与恢复。恢复后所有槽位应重新进入 DMA_OWNED且新包继续到达；若必须整机复位才恢复，说明 ring rearm路径不完整。该实验与线缆拔插分开执行，避免同时引入 link down。

8. 真实故障注入：省略 TX payload clean

在 D-Cache 开启时，先发送全 0x11 帧，再把同一 txbuf 改成全 0x22，注释 SCB_CleanDCache_by_Addr 并立即交 OWN。现象可能是 Wireshark仍收到旧 0x11、头部新而尾部旧，或 CRC/FCS 由 MAC 对旧 payload 正确生成；PHY link、协商与 DMA completion 都显示正常。

假设有应用 memcpy 错、DMA 地址错、cache stale 三种。证据链：检查 TDES buffer address正确、OWN 正常归还；调试器从 CPU 视角看到 0x22，线上却是 0x11；关闭 D-Cache或补回精确 clean 后错误消失；按 32-byte 块比较，旧数据边界与 cache line一致。定位为 CPU 修改未发布到 SRAM，而非 PHY 或 lwIP。修复是让 cache 操作成为 CPU_OWNED→DMA_OWNED 的强制步骤，并把 buffer 对齐/独占 line。

回归运行十万帧，长度与起始偏移覆盖 cache line 边界，线上 payload、sequence、CRC 全部正确；同时验证 descriptor 区 MPU 属性。若只关闭整个 D-Cache通过，不算完成，因为它掩盖协议错误并改变系统性能。

再做 duplex mismatch：交换机端强制 100/full，PHY 端保持 auto。若双方最终信息不一致，满载出现吞吐骤降与 collision/FCS 统计。把双方都恢复 auto 后回归。这个实验训练的是“link up 不是参数一致”的证据链，与 cache 故障的 OWN/线上旧块证据完全不同。

9. 异常恢复与预算

DMA fatal bus error、RX buffer unavailable 和 descriptor ring断裂不能只清中断继续。恢复流程要冻结新提交、保存 channel status与 ring 快照、确认上层 buffer ownership、复位 DMA channel、重新初始化每个 descriptor，再启动 tail pointer。未经确认就重置会让 DMA 写入仍被 lwIP 持有的 buffer。

1536-byte buffer乘 ring 深度很快消耗 SRAM；descriptor、payload、pbuf wrapper 与 cache line padding都要计入。中断合并减少 CPU 开销却增加延迟，NAPI式批处理思想在 MCU 上也适用：一次中断回收有限批次，然后让任务继续，但必须为控制流量设置最坏延迟。checksum offload 开关应做 A/B，尤其确认 RX status 的校验结果与 lwIP 配置一致。

看门狗复位前若 DMA仍运行，复位域和 SRAM保持方式可能让描述符处于旧 OWN状态。启动初始化必须重建整个 ring，而不是只设置 head=0；同时确保 MAC/DMA已停，避免硬件与 CPU同时改同一描述符。持久化故障日志放在独立 non-cacheable区，并带 magic/CRC，不能与 DMA pool重叠。

10. 练习题与判断标准

  1. PHY ID 可读且 link up，为什么仍可能没有 ARP reply？合格标准：至少指出 RMII/MAC filter、RX DMA OWN/cache、协议栈三层，并给对应观测量。
  2. TX 为何先 clean payload 再交 OWN？合格标准：说明 DMA不经过 CPU D-Cache，OWN 是不可逆的所有权边界。
  3. BMSR 为什么读两次？合格标准：指出 latch-low 历史状态与当前 link 的区别，并保留第一次诊断值。
  4. 提交省略 clean 的线上旧数据、descriptor 快照和十万帧回归。合格标准：能以 cache-line 边界和 A/B 修复排除 PHY、DMA地址与应用 memcpy；仅“关 cache 后好了”不合格。
