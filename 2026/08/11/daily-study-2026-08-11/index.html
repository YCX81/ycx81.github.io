🔧 嵌入式知识：TCP：字节流、重连、背压与应用分帧

一台以太网设备发送一次 send()，服务器却分两次 recv()；服务器已经执行“开阀”，响应途中链路断开，设备重连后又开一次；云端变慢时设备发送队列从几 KB 涨到耗尽 RAM。这三个现象不是三个偶然 bug，而是同一个协议模型缺口：TCP 只提供连接内可靠、有序的字节流，消息边界、跨连接语义和应用资源上限都要自己定义。

本文以 NUCLEO-H743ZI2、STM32CubeH7 中的 lwIP 2.1.x raw API、100 Mbps Ethernet 为板端对象，以 CPython 3.11 的本机 socket 为故障夹具。raw API 回调与 TCP/IP 栈在同一执行上下文，不能阻塞；socket/netconn API 的线程规则不同，代码不能直接混用。lwIP 官方 API 说明明确指出 raw API 是事件驱动且应用不得阻塞。

1. 先把字节流还原成有界消息

RFC 9293定义 TCP 为可靠、有序字节流。它不承诺一次 SEND 对应一次 RECEIVE；PSH 也不是应用分帧 API。假设协议采用 8 字节头：magic:u16, version:u8, type:u8, length:u32BE，后接 payload。解析器必须允许头和正文停在任意字节位置，并在分配内存前拒绝超过 MAX_PAYLOAD 的长度。

魔数失配后要断开还是重同步

长度前缀协议一旦读错一个字节，后续 length 会变成任意大数。最安全的默认策略是记录连接代次和偏移、立即关闭连接，不在不可信流中无限扫描 magic；扫描可能把 payload 内的相同字节误当新帧，并消耗不受限 CPU。若产品必须容忍串口桥造成的字节插入，重同步规则也要有上限：最多扫描一个最大帧长度，候选头同时满足 magic、version、type、length 和 header CRC，否则断开。

零长度是合法消息还是协议错误必须事先定义。EOF 到达时，parser 只有在 need is None 且缓冲为空才算干净结束；残留 1–7 字节是截断头，残留不足 length 是截断正文。把二者记成不同指标，才能区分对端实现错误与链路中断。解析失败后不能把旧缓冲带进重连，因为新 TCP 连接没有延续旧流的语义。

3. 背压是“什么时候拥有字节”的合同

lwIP raw TCP 文档说明 tcp_write() 在发送缓冲不足或 segment queue 超限时返回 ERR_MEM，应用应等待 ACK 回调或 poll 后重试；tcp_recved() 只在应用真正取走数据后调用，用来重新扩大接收窗口。过早 tcp_recved() 等于向对端承诺还有空间，实际队列却在涨；永不调用则窗口最终归零。

板端发送状态应保存 message pointer, total_len, queued_offset, acked_offset。每次仅提交 min(remaining, tcp_sndbuf(pcb), UINT16_MAX)，ERR_MEM 不前移 offset；tcp_sent 只增加已 ACK 计数并再次 pump。若不使用 TCP_WRITE_FLAG_COPY，原始缓冲在 ACK 前不得修改或释放，这是官方 tcp_write() 文档明确的生命周期约束。

raw callback 不得等待互斥锁、Flash 擦除或业务消费者。lwIP common pitfalls还要求不要从 ISR 直接调用 lwIP；中断只把事件投入有界队列，由 TCP/IP 线程执行 API。

Partial progress 与优先级不能靠循环硬顶

即使 BSD send() 返回正数，也可能小于请求长度；lwIP raw API 的单次 tcp_write() 则受 u16_t 长度、tcp_sndbuf() 和 queue length 限制。应用发送状态只能在成功提交的字节数上前移。ERR_MEM 后在同一 callback 紧密重试不会凭空产生 pbuf，反而饿死 TCP 定时器；应等 tcp_sent 或低频 tcp_poll。

控制命令与遥测共用一个 FIFO 时，大块日志会造成队头阻塞。可设置两个有界队列并由调度器做加权轮询，但同一消息的字节不能交错，否则接收 parser 无法恢复边界。高优先级也不能无限：给控制队列预留固定字节和最大突发数，保证遥测最终获得服务。记录每类队列等待时间，而不是只看 socket throughput。

接收侧也有两级背压：lwIP pbuf 池和应用消息池。若完整帧尚未复制成功，应保留未消费长度，不调用 tcp_recved；但长期持有 pbuf 会压缩全局池，影响其他连接。设计时比较“每连接复制池”与“共享 pbuf 引用”的最坏占用，并设置业务 deadline，超时后关闭最慢连接释放资源。

4. FIN、RST、keepalive 与业务 deadline

FIN 表示对端不再发送，并不阻止本端继续发送剩余方向；协议若不支持 half-close，应在收到 FIN 且 parser 干净后主动完成关闭。RST 表示连接被复位，未 ACK 与未业务确认操作都要进入未知结果处理。超时则更复杂：没有包不证明对端死亡，可能只是路径拥塞。

TCP keepalive 的默认间隔通常远长于控制业务需求，也不能证明应用线程健康。应用心跳应带连接代次、单调序号与 deadline；收到任意有效业务帧可以更新存活证据，但不能让过期响应确认新请求。重连采用带抖动的指数退避，例如 (d_n=min(d_{max},d_0 2^n)+jitter)，避免成千设备同时冲击服务器。成功稳定运行一段时间后才重置退避，而非 TCP 三次握手一成功就归零。

观测日志至少关联 connection_generation, message_id, parser_state, queued/acked/consumed bytes, close_reason。这样“响应超时”可以进一步判断为未提交、已 TCP ACK、服务端去重命中或响应解析失败。没有这些层次，现场只能反复看到笼统的 reconnect。

5. 板端可复现实验：慢消费者与零窗口

准备 NUCLEO-H743ZI2、STM32CubeH7 lwIP raw TCP echo 工程、PC 上的 Python 客户端、Wireshark。把 TCP_SND_BUF 和应用 TX 队列刻意缩到 4 KiB，消息上限 1 KiB。客户端每 200 ms 才读取一次，同时板端每 10 ms 产生 256 B 遥测。记录 tcp_sndbuf、tcp_sndqueuelen、应用队列高水位、ERR_MEM 次数、窗口和丢弃策略。

通过标准：应用队列不超过配置上限；达到上限后按协议丢弃最旧遥测或拒绝新命令，绝不覆盖尚未 ACK 的命令；客户端恢复读取后 10 秒内队列回落；raw callback 最大执行时间小于 1 ms。Wireshark 应能看到窗口收缩/恢复，但不能以抓包替代板端所有权计数。

6. 真实故障注入与完整定位链

故障：在 recv callback 收到 pbuf 后立即调用 tcp_recved(p->tot_len)，却把 p 指针交给低优先级任务并返回；与此同时为了“省复制”又释放 pbuf。现象是压力小时正常，慢消费者时 payload 偶发 CRC 错、HardFault 或队列上涨。

假设有三类：链路损坏、parser 越界、pbuf 生命周期错误。证据链：抓包中 TCP checksum 与重传正常，线上 payload 正确；parser 的长度门禁未触发；日志显示消费者读取时同一 pbuf 地址已被 RX 路径复用，且 tcp_recved 领先 consumed_bytes。因此定位为应用在承诺消费并释放后仍保留借用指针。

修复：callback 内把有界消息复制到应用自有池，复制成功后才 tcp_recved 并释放 pbuf；池满则返回背压策略，不宣告已消费。回归：随机拆分、连续 30 分钟慢读、池耗尽和重连联合注入，CRC 零错误、队列不越界、窗口能恢复。若选择零复制，则必须让应用持有 pbuf 引用到消费完成，并在同一受控上下文释放，不能混合两种所有权模型。

再注入“服务端执行后立即拔网线”。客户端日志应处于 TCP_ACKED 或 UNKNOWN，而非自动标记失败；重连后相同 message ID 返回原执行结果。把服务器进程也在动作与去重记录之间强杀，能检验二者是否真正原子。如果动作发生而 ID 未持久化，重试仍会重复执行，说明问题在服务端事务边界，而不是 TCP。

7. 练习与判定标准

  1. 为 8 字节头解析器加入 EOF 检查。连接关闭时残留半头或半正文必须报告截断，空缓冲才算正常结束。
  2. 设计队列预算：4 条连接、每条 RX 2 KiB、TX 4 KiB、开销 1 KiB。答案至少为 28 KiB，并额外说明 pbuf 池和并发峰值不能重复漏算。
  3. 将“增量计数器 +1”改成可安全重试协议。合格答案包含 message ID、持久去重、原子结果和窗口过期策略。
  4. 在板上制造至少 20 次 ERR_MEM。合格日志显示 queued offset 未在失败时前移，恢复后消息 SHA-256 与发送端一致。
  5. 区分 FIN、RST、应用超时。合格答案分别记录半关闭、错误回调和业务 deadline，不用一个“网络断开”掩盖所有原因。

官方资料与结论对应

  • RFC 9293：TCP：可靠有序字节流、SEND/RECEIVE 与连接状态语义。
  • lwIP 2.1.x raw TCP API：tcp_write、ERR_MEM、发送缓冲、ACK 回调、tcp_recved 和缓冲生命周期。
  • lwIP APIs：raw、netconn、socket API 模型与 raw callback 不得阻塞。
  • lwIP Common pitfalls：TCP/IP 核心线程与 ISR 调用边界。
