今日主线：IELTS Academic 周末整合复习与主动输出。

🔧 嵌入式知识：CAN/CAN FD：仲裁、错误状态与 Bit Timing

平台：NUCLEO-H743ZI2 的 FDCAN1、外接 MCP2562FD 收发器与一只支持 CAN FD 的 Linux USB-CAN 适配器。总线两端各 120 Ω，标称相位 500 kbit/s、数据相位 2 Mbit/s。本文结论适用于 ISO CAN FD；具体引脚、时钟源与 Message RAM 分配仍以工程和芯片手册为准。

1. 从“偶尔 bus-off”拆成三个不同问题

同一现象可能来自完全不同的因果链：高优先级报文等待，是仲裁和负载问题；错误计数持续增长，是采样、物理层或 ACK 问题；CAN FD 只在 BRS 打开后失败，则重点在数据相位时序、收发器带宽与 transmitter delay compensation。先区分层级，才不会用“调低波特率”掩盖终端或时钟错误。

CAN 的 dominant 位覆盖 recessive 位。节点发送每一位同时监听总线；仲裁字段中发送 recessive 却读到 dominant 的节点退出发送，获胜帧不被破坏。因而“仲裁失败”是正常调度结果，不是 bit error，也不应让错误计数上升。标准 11 位 ID 数值较小通常先出现 dominant 而获胜，但 RTR、IDE 以及扩展格式的后续仲裁位也参与比较，不能把完整规则缩成“ID 小必胜”。Bosch M_CAN 手册给出了仲裁、Protocol Status 与错误状态的控制器实现边界（M_CAN User’s Manual v3.3.1）。

ACK 也常被误读。发送者在 ACK slot 发送 recessive，任何正确接收该帧的节点可拉 dominant。得到 ACK 只证明至少一个节点在链路层正确接收，不证明目标 ECU 的任务已处理、写入 Flash 或执行动作；业务确认仍需序号、超时和响应报文。反过来，单节点总线上帧的位与 CRC 都正确，仍会因无人拉 ACK 而报 AckError。

2. Bit timing 是离散约束，不是只填一个 bitrate

一个 nominal bit 由同步段和若干 time quantum 组成：

[
t_q=\frac{NBRP}{f_{fdcan}},\quad
N_{bit}=1+NTSEG1+NTSEG2,\quad
bitrate=\frac{f_{fdcan}}{NBRP\cdot N_{bit}}
]

采样点为 (1+NTSEG1)/Nbit。本文令 FDCAN kernel clock 为 80 MHz。nominal 取 prescaler 4、TSEG1 31、TSEG2 8，总计 40 tq，得到 500 kbit/s 与 80% 采样点；data 取 prescaler 2、TSEG1 15、TSEG2 4，总计 20 tq，得到 2 Mbit/s 与 80% 采样点。SJW 是每次重同步允许调整的上限，不是任意吸收频偏的“容错预算”。线缆传播、收发器环路延迟、节点时钟误差与支线反射必须共同落在相位裕量内。

STM32H743 的 FDCAN_NBTP 与 FDCAN_DBTP 分别控制 nominal/data timing；字段采用减一编码，但 HAL 初始化结构填写实际数量。RM0433 的 FDCAN 寄存器章节给出字段范围和初始化模式写入规则（ST RM0433）。

初始化后应读取 NBTP/DBTP 反算实际值，而不是相信 CubeMX 文本框。若启用 BRS 后仅发送端失败，要测 TXD 到 RXD 的回环延迟并按控制器规则配置 TDC；M_CAN 的 TDC Offset/Filter 用于补偿数据相位较短时的发射延迟，不应凭经验复制别的板卡值。MCP2562FD 官方手册给出最大传播延迟和 CAN FD 速率边界，但收发器不会修复错误拓扑、缺终端或 MCU 时序（Microchip MCP2561/2FD Datasheet）。

3. 错误状态机：看 TEC/REC 的方向，不只看 bus-off

CAN 节点依据 transmit/receive error counter 在 Error Active、Error Passive、Bus Off 间转换。具体增减取决于检测场景，不能用“每次错误都加一”概括。M_CAN ECR 给出 TEC、REC，PSR 给出 EP、EW、BO、LEC/DLEC；读取 PSR 还会影响 LEC 的后续显示语义，因此诊断代码要保留时间戳与一次性快照。官方手册说明 warning 阈值为 96，并定义 Ack、Bit、Stuff、CRC、Form 等 Last Error Code（M_CAN Protocol Status）。

中断里先把 PSR/ECR/IR 快照压入固定 RAM 环形缓冲，再清已处理的 IR 位；不要在错误中断 printf，否则错误风暴会进一步延迟协议处理。自动重传可保证短暂仲裁后重试，却也可能让一个永久 ACK 故障持续占用控制器。产品应规定 bus-off 后进入何种安全状态、保存何种诊断、由谁批准恢复，而不是检测 BO 就立即重启。

4. 初始化模式和 Message RAM 也是协议正确性的一部分

M_CAN 的配置寄存器并非运行中随时可写。修改 bit timing、模式和 Message RAM 布局前，需要进入 initialization/configuration change 状态，写完后退出并等待控制器同步到总线。若应用在退出初始化前就入队发送，症状是 Tx request 存在却没有总线活动；若两个 FDCAN 实例的 Message RAM offset/数量重叠，接收元素可能被另一实例覆盖，表面上像随机 DLC 或 filter 错误。

Message RAM 元素大小必须匹配计划的最大 payload。过滤器接受 64-byte 帧，并不代表 Rx FIFO element 已配置成 64-byte data field；元素过小不能靠应用截断安全恢复。启动时应把标准/扩展 filter 数、Rx FIFO0/1、Rx buffer、Tx event FIFO、Tx FIFO/Queue 的起点和终点打印成区间，断言互不重叠且不超过 SRAMCAN 边界。此处是 STM32 集成约束，不是 ISO CAN FD 线协议本身。

CCCR.MON 监听模式可用于只收不发，但监听节点不会提供 ACK；若总线上只有发送节点和一个 silent analyzer，发送者仍会 AckError。内部 loopback 又绕过实际收发器、终端和线束，只适合验证 Message RAM/中断软件路径。验收必须明确使用 normal mode 的第二个 active node，不能用 loopback成功替代物理总线成功。

5. 传播与振荡器裕量怎样落到示波器

采样点之前必须容纳本节点 TX 到最远节点、再由总线返回 RX 的往返传播以及收发器延迟；采样点之后的 Phase Segment 2 留给相位修正与处理。线越长、支线越多、边沿越慢，可用时间越少。把采样点推到 90% 可能增加前段传播预算，却压缩后段重同步裕量，并非总是更稳。

振荡器容差是两节点频率误差的组合。每个硬同步/重同步只能在 SJW 范围内移动采样位置；连续同电平位之间依赖 bit stuffing 提供边沿，因而需要按规范允许的最长无边沿序列检查累计漂移。工程上应使用 CAN timing calculator 搜索所有整数解，再按控制器字段范围、目标采样点、SJW 与 oscillator tolerance 筛选，而不是只找到第一个零 bitrate error 的组合。

示波器同时探测 MCU TXD、收发器 RXD 与 CANH-CANL。TXD 到 RXD 的差给出本地环路延迟；差分波形 crossing 相对采样点的位置揭示远端传播和反射。若错误总发生在 data phase 开始后的固定首位，重点查 BRS 切换、DBTP/TDC；若帧末随机 Form/CRC error，重点查振铃、时钟累计误差和地偏移。把波形触发与 PSR.DLEC 时间戳对齐，才能从“有毛刺”走到可重复定位。

6. Linux 对端：让时序和错误可观测

Linux SocketCAN 用同一套 socket 接口承载 Classic CAN 与 CAN FD，但应用必须启用 CAN_RAW_FD_FRAMES；错误消息默认也不自动交给应用，需要设置 error filter。内核文档还明确 CAN FD netdevice 的 MTU 为 72，用户结构中的 len 是 0–64 的实际长度，不等同总线 DLC 编码（Linux SocketCAN）。

-e 显示错误帧，ip -details -statistics 显示状态和 berr-counter。主机配置值必须与板端实际反算值一致。SocketCAN 本地 echo 不是总线 ACK；拔掉 CANH/CANL 后应用仍可能看到本地发送回显，因此要结合错误帧、USB-CAN 统计与示波器判断帧是否真正被另一个节点确认。

7. 可复现实验与通过标准：仲裁、FD 相位和真实故障注入

准备两端 120 Ω、最长计划线束、示波器或 CAN FD 分析仪。Linux 每 2 ms 发 ID 0x123 的 64-byte FD+BRS 帧；H743 同时每 2 ms 发 0x120。捕获两者同起点的轮次，应看到 0x120 获胜、0x123 无错误地稍后重发，TEC/REC 保持稳定。这证明仲裁不是错误。

第二步逐级把 data bitrate 从 1 M 提到 2 M，记录采样点、LEC/DLEC、错误帧与差分波形。若 nominal 帧稳定而 BRS 数据段出现 bit error，测量数据相位边沿、支线反射和 TXD/RXD delay，再调整拓扑或 TDC；不要先改变应用周期。

真实故障注入采用“无 ACK”：保持 H743 正常发送，关闭并拔掉 Linux 节点，使总线上只剩发送者。现象是发送 API 已接受帧但始终无法完成，重复出现 AckError，TEC 上升并最终 bus-off。假设是对端没有确认；证据是示波器上 ACK slot 保持 recessive、PSR.LEC 指向 ACK、REC 不呈同样趋势。定位到缺少 active receiver，而非 ID 冲突。重新连接并启动 Linux 节点后，按产品策略重新初始化/恢复 FDCAN；回归要求连续发送十万帧，TEC/REC 回到稳定、无错误帧、业务序号无洞。

再把远端 120 Ω 暂时移除作为物理层故障。若短线仍“看似可用”，增加线长和温度/负载后会暴露振铃；以 CANH-CANL 差分波形和 error counter 证明，而不是以一次收包成功判定终端正确。断电测量总线两线间约 60 Ω只是两个 120 Ω 并联的初筛，还不能证明终端位置与支线合格。

为避免一次成功的偶然性，仲裁实验应运行十万次同相触发：两个节点先接收同步帧，再由同一硬件定时基准在固定偏移发送。统计两个 ID 的完成时间、arbitration lost 次数、TEC/REC 和应用 sequence。预期 0x120 始终先完成，0x123 随后完成且无 error frame。若两者并未真正重叠，就无法用结果证明仲裁；逻辑分析仪必须显示相同 SOF。

线束实验覆盖最短与最长、节点最少与最多、额定电压温度边界。每个条件保存实际 NBTP/DBTP/TDCR、内核时钟、示波器采样点附近波形和错误计数。只记录 CubeMX 参数而不读回寄存器，无法排除时钟树或初始化覆盖。

8. 资源与实时性边界

64-byte FD 帧减少协议开销，但数据相位更快不等于仲裁等待消失。高优先级周期帧的最坏响应至少包含一个已开始的低优先级帧阻塞、所有更高优先级帧干扰和错误重传。若发送 FIFO 按入队顺序而不是 ID 排序，软件可能先把低优先级长帧送入控制器，造成应用层的优先级反转；应核对 Tx FIFO/Queue 模式并做满载测量。

Message RAM 的 filter、Rx FIFO、Tx element 大小与数量要联合预算。DLC 9–15 映射到 12、16、20、24、32、48、64 等有效长度，不能把 DLC 数字当字节数。接收过滤只能减少 CPU 负载，不能减少总线负载；安全关键消息还需应用层 freshness counter、CRC/认证和 deadline monitor。

9. 练习题与判断标准

  1. 80 MHz 时钟、prescaler 4、TSEG1 31、TSEG2 8，求 bitrate 和采样点。合格标准：总 40 tq，500 kbit/s，采样点 80%。
  2. 两节点同时发送，0x120 获胜而 0x123 延后，TEC 不变。是不是故障？合格标准：不是；指出逐位仲裁与无破坏重发。
  3. 发送得到 ACK 后为何仍保留业务超时？合格标准：ACK 可能来自任意正确接收节点，不证明目标应用执行。
  4. 提交无 ACK 注入的 PSR/ECR 时间序列、ACK slot 波形和恢复后十万帧统计。合格标准：证据同时显示 AckError、TEC 上升、ACK recessive；修复后无错误帧与序号洞。
