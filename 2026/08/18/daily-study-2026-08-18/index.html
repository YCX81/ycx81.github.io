🔧 嵌入式知识：Secure Boot 信任链、镜像签名与 anti-rollback

Secure Boot 回答的是“这份代码是否由被授权的密钥发布且未被篡改”，anti-rollback 回答的是“即使签名有效，这个安全版本是否仍允许执行”。两者缺一不可，但把它们简单相加也不够：如果设备在新镜像第一次启动前就烧高不可逆计数器，而新镜像因驱动错误无法启动，旧槽又被计数器拒绝，安全机制会把可恢复故障升级成永久砖。

本文以 ESP32 芯片修订版 v3.0+、ESP-IDF Secure Boot V2、双 OTA 分区和 eFuse secure_version 为例，设计一条“下载—验证—试运行—确认—推进版本”的协议。Espressif 明确区分 Secure Boot 与 Flash Encryption：前者验证启动代码，后者保护片外 Flash 的机密性；Secure Boot V2 在 ESP32 v3.0+ 使用 RSA-PSS 签名块，详见 官方 Secure Boot V2 文档。

1. 信任链的边界比哈希算法更重要

签名必须覆盖影响执行语义的所有内容：镜像正文、长度、入口、芯片/硬件约束、安全版本和可加载段。验证器还应在验签前检查长度溢出、区间重叠和允许的算法。否则攻击者不必破解 RSA，只需诱导解析器对“验证的字节”和“执行的字节”产生不同理解。

设备保存公钥摘要而非私钥。发布私钥应留在隔离的签名系统；开发、量产和恢复密钥分域。ESP32 Secure Boot V2 支持多个公钥摘要槽及撤销策略，但 eFuse 是一次性资源，烧写和撤销不可当成普通配置更新。官方文档还特别警告启用 Secure Boot 会限制后续更新选择，因此量产前必须在同一芯片修订版上演练恢复与密钥轮换。

2. 安全版本不是产品版本号

v2.7.1 适合人阅读，却不适合作为可信单调状态：分支、地区版本和维修版未必能按字符串排序。镜像头应包含整数 secure_version，设备 eFuse 保存允许的下限 S_device：

[
accept(image) = signature_ok \land product_ok \land
S_{image}\ge S_{device}
]

ESP-IDF 的 OTA anti-rollback 文档 说明 bootloader 会比较应用镜像安全版本与 eFuse；应用完成诊断后调用确认 API，才把运行镜像标记为有效并更新芯片安全版本。经典 ESP32 的安全版本字段按置位位数编码，默认资源有限；官方文档指出其 anti-rollback 次数受 eFuse 位数约束。这意味着安全版本只在修复不可接受漏洞时推进，不应每个普通构建都加一。

4. 可复现的开发板实验

硬件使用 ESP32 rev3 开发板和串口，准备两个固件：A 的 secure_version=1，B 的 secure_version=2；B 增加一个可由 GPIO 拉低触发的自检失败。先在未烧永久安全配置的样片上生成专用测试签名密钥，配置双 OTA 与 rollback，完整保存 esptool.py、idf.py 命令和 eFuse 摘要。生产密钥绝不能用于这个实验。

第一轮从 A OTA 到 B，GPIO 保持高。B 首启状态应为 PENDING_VERIFY，三个自检通过后转为 VALID；断电重启仍进入 B。第二轮重新刷可试运行的 B，首启时拉低 GPIO，使自检失败；设备必须回到 A，并在日志中保留“候选验证通过但运行自检失败”的不同原因。验收不是“最终能启动”，而是每个状态迁移可从串口日志和 OTA 分区元数据同时证明。

随后在下载 10%、写完镜像但未设置 boot partition、设置后未首启、首启未确认四个时点断电。每次恢复只能选择一个完整、签名正确、满足版本下限的槽。ESP-IDF OTA API 要求先结束写入验证，再设置启动分区；遵守 API 顺序比在应用层发明 update_done=true 更可靠。

5. 故障注入与定位：两个“都签过名”的失败

故障一：篡改 Flash 中 B 的一个字节。 用测试夹具在 OTA 写完后翻转应用分区正文，不改签名块。重启应在控制权交给 B 前拒绝。若进入 B 后才 crash，说明执行路径存在未验证入口，或测试篡改了不受签名覆盖的区域。定位时记录 ROM/bootloader 验签错误、分区地址和镜像摘要，不能只依赖应用日志——应用本来就不该运行。

故障二：重新发送合法签名的 A。 它的签名完全有效，但当 eFuse 下限已经是 2 时仍必须被拒绝。若 A 被接受，检查 CONFIG_BOOTLOADER_APP_ANTI_ROLLBACK、镜像 secure_version 字段以及实际 eFuse 值，而不是怀疑 RSA。反过来，若 B 首启失败且 A 也被拒绝，很可能是过早推进下限；这属于发布状态机错误，不是密码算法错误。

还要故意在 eFuse 推进前断电。正常设计会重复确认或保持旧下限，不会出现“半个整数”。但 eFuse 位资源不可恢复，先用 Espressif 的 eFuse 管理器文档 读取编码和保护状态，再在测试板上操作。任何永久烧写都应有工装二次确认、电源裕量和审计记录。

6. 密钥轮换、调试口和恢复镜像属于同一个威胁模型

若量产设备还能从 UART 下载模式执行任意代码，应用签名再严也可能被旁路。是否禁用下载、JTAG 和调试功能取决于维修模型，但必须使用芯片支持的鉴权/永久策略，并验证普通应用不能重新打开。Espressif 的 ESP32 安全概览 将 Secure Boot、Flash Encryption、anti-rollback 与调试/下载模式放在同一配置面中，这是因为攻击者会寻找最弱入口。

根密钥轮换需要旧信任根授权新根，先把新验证材料安全部署到足够多设备，再开始只用新私钥签名，最后按策略撤销旧摘要。恢复镜像也必须签名并满足预先定义的安全版本规则；“紧急时允许未签名”不是恢复策略，而是永久后门。日志可记录密钥槽号、版本与失败类别，但不能泄露密钥、完整敏感摘要或可用于降级的维修口令。

多镜像设备必须验证组合，而非各自签名

真实产品常有主控应用、无线协处理器、文件系统资源和安全元件配置。它们分别验签并不代表组合可运行：主控 v8 可能要求无线协议 v5，而旧无线镜像 v4 虽签名有效也会破坏更新确认。签名保护的 manifest 应声明产品 ID、硬件修订、每个组件摘要、安全版本和依赖下限；bootloader 或更新代理在写入前检查整体约束。

测试时准备一个“每个组件单独合法、组合依赖不满足”的包。合格结果是在切换任何活动槽前拒绝，并指出依赖冲突；如果更新到一半才由应用发现不兼容，说明原子更新边界定义得太晚。跨组件无法同时切换时，应设计兼容窗口：先发布可同时理解旧/新协议的过渡版本，再升级另一端，最后收紧最低版本。这个过程同样需要断电测试和可认证的恢复组合。

7. 练习与可判定标准

  1. 状态机题：补出下载完成、验签完成、首次启动、确认、看门狗复位五个断电点。合格答案要求每点都能落到唯一的可恢复状态，且没有路径执行未验证镜像。
  2. 版本题：设备下限为 7，槽 A/B 的安全版本分别为 6/8，B 未确认并复位。合格答案必须指出不能回到 A；发布前就应保留一个版本不低于 7 的已确认恢复槽，而不是临时绕过检查。
  3. 篡改题：扩展 Python 程序，分别篡改 product、版本、payload 与 tag。四种输入都必须返回 false，并保留至少一个原始合法向量为 true。
  4. 板级题：完成四个断电注入与两个镜像故障。每次给出 bootloader 日志、选中槽、OTA 状态和 eFuse 下限；只展示“板子最后亮灯”不合格。
  5. 运营题：设计 32 个安全版本位的使用政策。合格答案需区分产品版本与安全版本、估算十年漏洞修复次数、定义接近耗尽和维修镜像策略。
  6. 密钥题：画出开发、量产、恢复三类密钥的签名权限和撤销路径。任何“所有环境共用一把私钥”或设备持有发布私钥的方案判定失败。

官方资料与结论对应

  • ESP-IDF Secure Boot V2：ESP32 rev3+ 支持范围、RSA-PSS 签名块、公钥摘要、撤销和量产注意事项。
  • ESP-IDF OTA 与 Anti-rollback：OTA 状态、确认/回滚 API、安全版本比较和 eFuse 更新时机。
  • ESP-IDF eFuse Manager：eFuse 读取、编码、批量写入与写保护接口。
  • ESP32 Security Overview：Secure Boot、Flash Encryption、anti-rollback、UART 下载与调试面的整体关系。
