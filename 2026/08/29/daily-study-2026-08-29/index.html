🔧 嵌入式知识：C11 原子操作与嵌入式内存模型

工程问题：单核 MCU 上稳定的 volatile 标志，为何移到双核就读到旧数据

实验分两层：macOS/Linux 主机使用 GCC/Clang、C11 与 pthread 运行并发压力；目标侧用 STM32F407 Cortex-M4F GCC 检查生成代码和 lock-free 属性。主机用于验证语言层发布关系，MCU 用于确认实现代价。C11 的原子、data race、happens-before 与 memory order 定义以 WG14 N1570 草案为规范依据。

volatile 只要求抽象机保留对该对象的访问，不能把复合读改写变成原子，也不建立线程间同步。C11 原子解决三个不同问题：单次访问不撕裂；操作之间建立可见顺序；实现是否 lock-free。前两者是语义，第三个是目标属性，不能互相替代。

release/acquire 发布关系

生产者先写普通 payload，最后以 release 发布序号；消费者以 acquire 观察到该序号后，生产者在 release 前的写 happens-before 消费者后续读取。

memory_order_relaxed 只保证该原子对象自身修改序列和不可撕裂，适合统计计数，不承担旁边数据的发布。seq_cst 额外要求所有顺序一致操作处于单一总序，但仍不能修复普通变量 data race、对象生命周期或越界。

可运行主机实验：双缓冲发布

下面程序用单生产者/单消费者交接一个 payload。用 C11 原子序号 release/acquire，循环一百万次并验证两个字段的一致性。编译运行：cc -std=c11 -O3 -pthread publish.c && ./a.out。

consumed 的 acquire/release 防止生产者覆盖消费者仍在读的 payload；仅用一个 ready 位且生产者不等待归还会发生生命周期竞争。这个协议仍是假设单生产者单消费者，不可直接扩成多生产者。

原子计数与 compare-exchange

读后再写 counter = counter + 1 包含加载、计算、存储，两个线程可丢更新。atomic_fetch_add 把读改写作为一个原子操作。CAS 用于条件转换；weak 允许伪失败，因此通常循环。失败 memory order 不能是 release/acq_rel，且不能比成功路径更强。

如果允许伪失败就当作丢帧，上面单次 weak CAS 的语义是“竞争或伪失败均放弃”，这是刻意策略；若业务必须最终获得 EMPTY，应在有界循环中重试。CAS 不解决 ABA：状态从 EMPTY 经一圈又回 EMPTY 时，旧观察者无法仅凭枚举值知道对象已换代，需要版本计数或不同所有权设计。

lock-free 必须在目标构建上证明

C11 允许原子由运行库锁实现。GCC 官方说明泛型 __atomic 在目标不支持时可能留下外部运行库调用，并提供 __atomic_is_lock_free，见 GCC __atomic builtins。在 ISR/NMI 中若 fallback 锁被任务持有，中断无法等待任务继续执行，可能死锁。

目标守门应同时做三件事：检查 ATOMIC_*_LOCK_FREE/atomic_is_lock_free；查看反汇编；检查链接 map 是否出现 __atomic_*/libatomic。自然对齐的 32 位对象在 Cortex-M4 常能用独占指令实现 RMW，但具体编译器、选项和对象大小必须实证。64 位原子尤其不能凭 CPU 是 32 位就猜。

ATOMIC_INT_LOCK_FREE 只对应 atomic int，而示例对象是 uint32_t；严格工程还要对所用 typedef 做 atomic_is_lock_free(&irq_flags) 启动断言并检查汇编。静态断言用于暴露工具链不满足先决条件，不是跨所有 C 实现的保证。

单核中断、RTOS 与多核不是同一个并发域

单核任务与 ISR 不会同时执行指令，但 ISR 可在任务的非原子读改写中间抢占。临界区可解决这种单核抢占，却不自动解决双核 cache 可见性。C11 原子可描述 C 执行线程间同步，但 freestanding 实现如何把 ISR 纳入语言模型是实现相关边界，需要工具链/RTOS 文档与实测。

FreeRTOS API 自身已有临界区和调度契约，不能在不了解端口时混用原子与 ISR API。若原子 fallback 使用锁，它也未必遵守 RTOS 中断屏蔽阈值。对简单单核 ISR 标志，经过证明的 lock-free 原子或短临界区都可选；选择依据是最坏延迟、可移植性和实现证据。

MMIO、DMA 与 cache：C 原子不负责设备

MMIO 寄存器通常通过 volatile 设备映射访问，其读写副作用和总线顺序由芯片架构定义。把寄存器指针强转 _Atomic 不会自动满足外设手册，反而可能生成不允许的独占访问。CPU 与 DMA 共享缓冲时，DMA 不是 C 线程；release 标志不能替代 cache clean/invalidate、所有权切换和设备屏障。

在带 cache 的 Cortex-M7/多核 SoC 上，正确流程常是：CPU 填缓冲；clean cache 到共享域；设备屏障确保描述符可见；写 doorbell；完成后读取状态并 invalidate。C 原子用于 CPU 线程之间的发布，设备步骤由平台 API完成。Arm 对屏障与内存类型的解释见官方 memory ordering 文章。

可复现实验与通过标准

主机准备 GCC 或 Clang。运行发布程序，输出必须 errors=0；再用 -fsanitize=thread -O1 构建。故障版本把原子 flag 改为普通/volatile，ThreadSanitizer 应报告 payload/flag data race，不能因为一次运行零错误就判正确。分别将循环提高到一千万并绑定不同 CPU 核。

目标侧用 arm-none-eabi-gcc -std=c11 -O2 -mcpu=cortex-m4 -mthumb -S 编译 ISR 例程，检查 32 位 RMW 是否内联、是否有 DMB、是否引用 libatomic；再测试对齐的 64 位对象，记录差异。运行 atomic_is_lock_free 并与 map/汇编交叉验证。

通过标准：正确主机版无 sanitizer data race；故障版产生可解释告警；目标中所有 ISR 使用原子都证明 always lock-free 且无运行库锁；每条共享数据都有发布者、获取者和生命周期说明；MMIO/DMA 路径另列屏障/cache 协议。

真实故障注入与完整证据链

注入：把 published 的 release store 和 acquire load 都改为 relaxed，并删除 consumed 归还协议，让生产者连续覆盖 payload。现象可能是消费者看到序号更新却读到字段不匹配；在 x86 上不一定复现，但 ThreadSanitizer 会指出普通 payload 的并发访问。假设包括整数撕裂、发布顺序不足、缓冲生命周期重叠。

证据是序号原子本身不撕裂，错误集中在 payload；sanitizer 报生产者写与消费者读竞争；恢复 acquire/release 但仍不等待 consumed 时错误尚存，说明可见顺序和所有权是两个问题。定位为缺少发布同步加单缓冲被过早复用。修复为匹配 release/acquire，并增加 consumed 归还或改为双缓冲序号协议。

回归在不同优化、百万到千万循环、不同核亲和与 sanitizer 下运行，错误和 data race 均为零；目标汇编仍满足 lock-free 守门。完整链为：字段不一致 → 三个假设 → 原子序号/竞争报告/分步恢复证据 → 同步与生命周期双根因 → 发布和归还修复 → 多配置回归。

data race 是未定义行为

两个 C 线程并发访问同一普通对象、至少一方写且没有 happens-before，就形成 data race，程序行为未定义。后果不限于读到旧值；编译器可基于“合法程序无 data race”外提、合并或删除访问。改成 volatile 仍没有同步关系。

同一共享对象不能一边原子访问、一边通过普通别名访问。对象生命周期结束后，即便地址被新对象复用，旧原子指针也不能继续使用。ThreadSanitizer 是动态证据，只覆盖执行路径，也可能不理解 RTOS 同步；无报告不构成全局证明。

如何选择 memory order

从同步需求而非性能猜测开始。单纯统计且不发布其他数据时用 relaxed；发布已初始化对象用 release；取得后读取对象用 acquire；原子读改写既取得旧状态又发布新状态时常用 acq_rel；确需跨多个原子的统一全序才选 seq_cst。

失败 CAS 只执行读取，不能使用 release 或 acq_rel。fence 只有与相应原子操作组成正确模式才有意义；随手插一个 fence 不能给普通 flag 建立同步。

lock-free 不等于 wait-free

lock-free 表示系统整体持续前进，不保证某线程不会长期饥饿；wait-free 才要求每个操作在有限自身步骤完成。CAS 高竞争循环可能让低优先级任务反复失败，实时上界很差。ISR 抢占任务时，两者争同一独占监视器会增加任务重试。

对硬实时 MCU，短临界区有时比复杂无锁算法更容易给上界。选择要比较最坏关中断时间、CAS 重试、优先级反转和 fallback 锁。原子多字段也不是事务；分别更新 head 和 count，读者可能看到不一致组合。

消息传递 litmus 的推理

初始 x=0, flag=0。生产者普通写 x=1 后 release 写 flag；消费者 acquire 读到 flag=1 后读 x。规范保证 x=1。若 flag 两端 relaxed，C11 不提供 happens-before，即使某 CPU 碰巧通过，也不能发布。

消费者 acquire 若读到旧值 0，没有同步发生，不能推断 payload。同步关系取决于读取到 release 序列中的值，不是只因源码使用 acquire。环形序号还要考虑回绕，避免旧值与新一圈相同造成 ABA。

三类屏障不能混为一谈

编译器屏障只限制编译期重排；DMB 约束内存访问顺序；DSB 还等待相关访问完成。C11 acquire/release 由编译器按目标映射，但面向 C 抽象机同步；设备寄存器完成语义仍看架构。

在 Cortex-M4 单核无 cache SRAM 上，release/acquire 可能不需要显式 DMB，只靠编译器顺序即可；换到多核/cache 系统可能生成屏障。不能因反汇编没有 DMB 就断言错误，也不能把 M4 结果推广到 M7/A 核。

检查汇编时同时看 payload 是否移到发布之后、原子宽度与对齐、是否调用库函数。只看到 ldrex/strex 不能证明整个协议。

资源回收与 ABA

无锁栈中指针从 A 变 B 又变 A，CAS 只比较地址会误以为未变化；期间 A 可能已释放复用。方案包括带版本标签、hazard pointer、epoch 回收或禁止并发释放。固定池可简化生命周期，但版本计数仍会回绕。

引用计数原子减到零也不自动安全：另一个线程若能从无保护位置重新取得指针，可能在释放后递增。必须保证获得引用本身与对象存活同步。复杂回收算法不能只靠压力测试批准。

练习题与判断标准

  1. _Atomic int 是否必然 lock-free？不必然，必须查宏、运行检查、汇编和链接。
  2. relaxed 计数器何时合适？仅当不承担其他数据发布关系且回绕语义已定义。
  3. release flag + acquire load 是否允许生产者立即覆写 payload？不允许；还需要所有权归还或多缓冲协议。
  4. C11 fence 能否替 DMA 做 cache clean？不能，DMA/设备一致性是平台协议。
  5. 实操提交正确/故障版 sanitizer 输出、目标汇编、lock-free 结果和 map；仅声称“在板上没出错”不合格。
