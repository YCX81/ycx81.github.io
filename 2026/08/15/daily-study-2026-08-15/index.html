🔧 嵌入式知识：嵌入式 TLS：证书验证、熵与会话

设备日志出现“TLS handshake success”，并不能推出“连接的是生产服务器”。若客户端信任任意证书、跳过 hostname、时钟停在 1970 年或 DRBG 每次从相同 seed 启动，握手仍可能成功，却把加密通道交给攻击者。会话恢复进一步容易被误解：它减少握手成本，不会恢复旧 TCP 连接，也不会替业务提供恰好一次。

本文以 ESP32-S3-DevKitC-1、ESP-IDF 5.x/ESP-TLS（底层 Mbed TLS）、Wi-Fi 已启动为例；主机实验使用 OpenSSL 3 与 Python 3。ESP32-S3 的硬件 RNG 只有在 RF、SAR ADC 内部熵源或 bootloader 特定阶段满足条件时才保证真随机；ESP-IDF RNG 文档明确说条件都不满足时输出应视为伪随机。

1. “验证证书”其实是两条独立证明

第一条是路径验证：叶证书由中间 CA 签发，最终到设备信任锚，且签名、有效期、Basic Constraints、Key Usage/EKU 等成立。第二条是服务身份：应用期望的 api.example.com 必须匹配叶证书 subjectAltName 的 dNSName。SNI 只是告诉服务器选择哪张证书，不等于客户端完成身份验证。

RFC 9525要求服务身份来自 SAN，不再把 Common Name 当服务标识；IP 连接应与 iPAddress SAN 逐字节匹配。因而正确条件是：

[
authenticated = path_valid \land time_valid \land identity_match
]

任何一项被“调试开关”跳过，结果都不是较弱的认证，而是没有证明对端身份。ESP-TLS 官方文档警告跳过 common-name 配置会同时禁用 hostname matching 和 SNI；字段名的历史命名不能成为误用理由。

3. 没有可信时间时不能假装证书永不过期

无电池 RTC 的设备首次上电可能没有可信 UTC。直接关闭 notBefore/notAfter 检查，会让泄露且已过期的证书永久有效。可行方案是保存受防回滚保护的“已知时间下界”：制造时写入，成功完成受认证时间同步后只向前推进；首次连接只允许访问内置根与固定身份的 bootstrap 服务，再取得签名时间。威胁模型必须说明攻击者能否回滚 Flash、控制 DNS/NTP、长期断电。

信任锚与证书轮换是掉电事务

把一张叶证书永久 pin 在固件里，会在正常续期时制造现场故障；信任整个公共根集合又扩大信任面。产品私有 PKI 通常 pin 一个或两个受控根，并让叶证书短期轮换。根轮换需要重叠期：旧固件先收到“旧根签名授权的新根”，保存到非活动槽并校验；新服务器链在足够设备支持后上线；最后才撤销旧根。

信任存储采用 A/B manifest，每份包含 generation、根摘要集合、有效策略和整体签名。写完非活动槽、读回校验、原子切换 active marker；任一点断电都应至少保留一份可验证集合。OTA 固件版本、可信时间下界和 trust-store generation 要定义兼容矩阵，防止固件回滚后不理解新证书，也防止旧根随配置回滚重新有效。

证书撤销在离线设备上尤其困难。若实现不获取 CRL/OCSP，就不能声称能实时撤销叶证书；可用短有效期、快速根/中间轮换和固件 denylist 降低窗口，并明确最坏暴露期。这个结论是部署策略，不是 TLS 协议自动提供的保证。

4. 熵、DRBG 与启动阶段的因果链

TLS 临时密钥和 nonce 通常从 DRBG 获取；DRBG 的安全性来自初始熵、personalization 与适当 reseed，而不是算法名字。ESP32-S3 在 Wi-Fi/Bluetooth 运行时有主熵源；若早期应用尚未启用 RF，需按官方约束临时调用 bootloader entropy API，并在 ADC/RF 使用前关闭。不要高频直接抽取“随机流”替代 DRBG。

把熵故障变成可诊断的失败

平台适配层应返回“获取了多少字节、来源当前是否满足强熵条件、健康检查状态”，而不是永远返回成功。若早期启动需要生成设备长期密钥，先显式启用内部熵源，采样完成后关闭并清理缓冲；若 ADC 或 RF 已被别的子系统占用，则延后生成，不能并发抢用。长期密钥只生成一次并存入受保护存储，不能每次启动重新生成。

故障注入可在测试构建中把 entropy callback 固定返回 32 个零且仍报告成功。现象可能是多台设备生成相同 ephemeral/key material；假设包括随机源固定、持久 seed 被克隆或 DRBG personalization 缺失。证据是两次冷启动的 DRBG 首段摘要完全相同，同时硬件 RNG 路径计数为零。定位到回调错误后，修复为错误向握手传播并 fail closed；回归要求固定零源使握手/密钥生成明确失败，真实源下 1000 次冷启动摘要无重复。摘要只能用于实验，生产不要记录随机输出。

CTR-DRBG 的内存小不等于可以跨任务无锁共享。若多个 TLS 连接共用 context，需要按 Mbed TLS 线程模型串行化；更清晰的设计是平台 entropy context 受控共享，每连接 DRBG 有独立 personalization。复位、deep sleep 与 session ticket 恢复后仍要判断 reseed 条件。

5. 会话恢复改变成本，不改变业务语义

TLS 1.3 RFC 8446定义 ticket/PSK resumption；恢复出的连接仍有新的 record sequence 和应用状态。ticket 是敏感凭据，需要保密、过期和服务器密钥轮换；恢复失败必须能回到完整握手并重新验证策略。

0-RTT 更特殊：RFC 8446 第 8 节明确说明 TLS 本身不提供固有的 early-data 防重放，客户端不得发送不愿在多个 1-RTT 连接上重试的操作。因此 GET-like 遥测查询可评估 0-RTT，“开锁”“扣款”“推进固件计数器”不得直接放入 early data。即使不用 0-RTT，TCP 响应丢失后的业务重试仍要 message ID 去重。

资源预算要实测：全握手与恢复分别记录峰值 heap、任务栈、握手耗时、发送/接收字节和失败标志。恢复快不代表证书永不更新；服务器拒绝 ticket、ticket 过期和根证书轮换都必须回归。

ESP32-S3 的峰值 RAM 常出现在证书链解析与握手消息并存阶段。证书 bundle、最大 TLS fragment、并发连接数和任务栈共同决定是否 OOM。若内存不足，不能把 verify mode 降级；应减少并发、裁剪受信根、使用合理 fragment 或串行握手。记录 minimum_free_heap 与最大栈水位，并在服务端发送最长合法证书链时测量，而不是只测最短自签证书。

ticket 存入 NVS 前应视为凭据：加密/完整性保护、绑定服务器身份和配置 generation，并设置寿命。恢复连接仍要校验应用目标没有变化。设备从生产域切到测试域时必须清除旧 ticket，不能让缓存 PSK 绕过环境切换的预期路径。

6. ESP32-S3 开发板实验与故障定位

准备 ESP32-S3-DevKitC-1、ESP-IDF、受控 Wi-Fi、本地 TLS 服务器和抓包。固件显式配置服务器 hostname 与 CA，打印 Mbed TLS verify flags、握手耗时和 free heap，但不打印密钥。依次测试：正确链、未知 CA、错误 SAN、过期、缺中间证书、时间未初始化、完整握手与恢复。通过标准是所有身份/时间错误 fail closed，恢复失败可回完整握手，连续 100 次握手无 heap 下降。

真实故障注入：把配置中的 hostname 从 device.test 改为 evil.test，同时保留由同一 CA 签发的证书。现象：若误设 skip-hostname，握手成功；假设可能是 CA 配错、SNI 错或身份校验被关闭。证据：OpenSSL 显示链有效但 SAN 仅有 device.test；ESP-TLS 配置日志显示跳过字段为 true；抓包只能看到加密握手，不能证明 hostname。

定位为应用禁用了身份匹配。修复是恢复 hostname 验证并传入参考身份，禁止生产构建覆盖；回归运行正确 hostname 成功、错误 DNS/IP/CN-only 证书全部失败，并在 CI 搜索 skip 选项。再关闭 Wi-Fi、在 RF 初始化前连续生成启动材料，验证固件按 RNG 文档启用/关闭内部熵源；若无法保证强熵就拒绝生成长期密钥，而非静默继续。

为了避免“错误码被统一成连接失败”，保存 Mbed TLS verify flags 和最内层错误，但对远端只返回一般失败。路径未知、时间无效、hostname 不符、熵不足与 socket timeout 要有不同本地指标。诊断信息不得包含私钥、PSK、ticket 或原始随机数。

7. 练习与判定标准

  1. 解释 CA 验证与 hostname 验证的差别。答案必须给出“同一可信 CA 给错误域名签证书”仍应失败的例子。
  2. 为无 RTC 设备画首次启动状态机。合格答案包含不可回退时间下界、受限 bootstrap 身份、失败关闭与 OTA 回滚关系。
  3. 在本地证书实验增加 IP SAN。以 127.0.0.1 连接时只有 iPAddress SAN 匹配才通过，DNS 字符串不算。
  4. 测 100 次完整/恢复握手。报告中必须有中位数、最大 heap/栈、恢复接受率和 ticket 过期回退，不只写“更快”。
  5. 重放同一 0-RTT “开阀”消息两次。合格设计要么禁用该 early data，要么证明应用级 nonce/ID 去重和持久化原子性。

官方资料与结论对应

  • RFC 9525：TLS 服务身份：SAN、DNS/IP 身份匹配和废弃 CN-ID。
  • RFC 8446：TLS 1.3：握手、PSK/session resumption、0-RTT 与重放边界。
  • ESP-TLS 官方文档：证书配置、hostname/SNI、session ticket 接口。
  • ESP32-S3 Random Number Generation：硬件 RNG 的主熵条件、启动阶段和 DRBG 建议。
  • ESP-IDF Mbed TLS：X.509、证书 bundle、SNI 和 session ticket 构建选项。
