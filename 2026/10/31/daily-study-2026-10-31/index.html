今日主线：IELTS Academic 周末整合复习与主动输出。

🔧 嵌入式知识：QSPI/OSPI XIP、协议模式与缓存一致性

工程问题：Flash 已写对，为什么 CPU 仍执行旧代码，甚至下一次复位就再也读不到

本文固定平台为 STM32H735G‑DK（STM32H735IGK6）+ 板载 Macronix MX25LM51245G 512 Mbit OctaFlash + STM32CubeH7 v1.12.1 的 Applications/ExtMem_CodeExecution/ExtMem_Boot build target。板级器件与连线边界来自 UM2679 Rev.7，控制器语义固定到 RM0468 Rev.3 的 OCTOSPI 章节。根仓固定 commit f5c0b7a2b1f6eb26fde150f72edb2d7deb647066，其中 STM32H735G‑DK BSP gitlink 固定为 4d2e91db442e525b8b879fba260fc3c6369a87d5、MX25LM51245G component 固定为 e7f45cee910535311a590890d0fffe9eded935fe、HAL driver 固定为 57ed86b4c358e2333a71fd895b17f1ccdb68739e。本次主机证据环境为 macOS Darwin arm64、Python 3.14.0。

本次未连接 STM32H735G‑DK、示波器、逻辑分析仪或调试器，也未在 Cortex‑M7 上执行外部 Flash 代码。因此 WIP 时长、DQS 眼图、ABORT 完成条件、I-cache 失效效果和实际 XIP 指令流全部属于计划验证。正文中的 transcript 只来自确定性主机合同模型。

真实事故常有两个阶段：OTA（over-the-air update，在线远程更新）先从 SRAM 驱动擦写外部 NOR，indirect read 校验新镜像正确；跳转后 CPU 却继续运行旧函数。工程师再按 reset，bootloader 甚至读不到 JEDEC ID——由串行 NOR 标准命令返回的制造商/器件识别 byte。ID 可确认当前总线能读到哪类器件，却不是防伪认证。第一个现象通常被归咎于“Flash 写坏”，第二个被归咎于“板子偶发死机”。更有解释力的因果模型要同时区分：

  1. Flash 阵列里真正存的 bit；
  2. Flash 此刻解释的串行协议模式；
  3. OCTOSPI 控制器此刻生成的 transaction 格式；
  4. 控制器 memory-mapped prefetch/buffer 的旧副本；
  5. Cortex‑M7 I-cache/D-cache 与流水线已经取得的旧指令或数据；
  6. 正在执行 update 的代码、vector、ISR 和常量位于哪种存储器；这里 vector table 把异常号映射到 handler 地址，ISR（interrupt service routine）是异步中断到来时执行的 handler；
  7. 哪个 generation 拥有更新窗口，以及是否还有其他 bus master 访问映射区。

只验证第 1 项不能推出其余六项一致。

QSPI、OSPI、协议宽度和 DTR 分别是什么

SPI 的经典事务用一根数据输出和一根数据输入；Dual/Quad/Octal SPI 允许某些 phase 使用 2/4/8 根双向 I/O。这里的 QSPI/OSPI 常同时指控制器类别与总线宽度，命名容易误导。一个 read transaction 通常由以下 phase 组成：

opcode 是选择 Flash 操作的命令编码；instruction phase 是把该编码送出的总线阶段。两者相关但不是一个概念：控制器还需知道该 phase 用几根线、每边沿是否传数据。1-1-4 表示 instruction/address/data 分别用 1/1/4 线；1-4-4 不是“所有阶段四线”；八线 DTR 常写成 8D-8D-8D。具体记法不是寄存器值，最终要映射到 IMODE/ADMODE/DMODE、DTR enable、DQS 等控制字段。

STR（single transfer rate）每个时钟周期只在一个有效边沿传输；DTR（double transfer rate）在两个边沿都传输。DTR 提高单位频率的 bit rate，也缩小采样裕量。DQS（data strobe）是 Flash 随数据提供或用于对齐的采样参考；它不是普通 data line，也不等于 MCU 内部 delay block。本文不是抽象地挑一个 OPI_DTR_6，而是把 operational tuple 锁到一个可静态复核的 build：

固定 build 的 mx25lm51245g_conf.h把 CONF_OSPI_DUMMY_CYCLES 设为 MX25LM51245G_CR2_DC_6_CYCLES；固定 BSP driver生成 200 MHz kernel clock 并使用 prescaler 2；固定 component driver把 DTR read 的 DummyCycles 设为 6、DQS enable。HAL 字段的“一周期”含义来自 固定 stm32h7xx_hal_ospi.h：它是 data phase 前插入的 dummy clock cycles，不是 DTR edge 数，也不是 byte 数。目标实物仍必须 read back CR2/OCTOSPI registers 并测眼图；源码闭合只证明配置意图一致。

Macronix 官方 OctaFlash 产品页列出 MX25LM51245G 的 8 I/O、DTR、hardware reset、suspend/resume 与频率能力。产品页说明“器件有什么能力”，不证明本板在最高频率、全部温压下有 margin，也不证明 boot ROM 理解运行时留下的 octal mode。

dummy cycle 不是可随意调的延迟，mode 也不是控制器单方面属性

dummy cycle 是没有有效 payload 的完整时钟间隔。Flash 利用它完成阵列访问，接收端利用它安排方向转换和采样；所需数值随 opcode、频率、STR/DTR、配置寄存器和器件 speed grade 变化。DTR 每个 full cycle 有两个 data edge，但 HAL ... DummyCycles=6 仍表示六个 clock cycle；若把它误算成六个 edge、十二个 cycle 或六个 byte，controller 与 CR2 会分裂。少一个周期可能把 mode bit 或无效 bit 当作数据，多一个周期可能整体错位。低频“读起来正确”不能证明 100 MHz 设置正确，因为内部访问时间相对时钟周期的预算改变了。

Flash 的 protocol mode 可来自 volatile configuration register、nonvolatile configuration register、特殊 enter/exit 命令、reset pin 或 power cycle。volatile 表示掉电后不保证保持；nonvolatile 表示器件把设置保存到非易失单元，但写入次数、保护和复位语义要看 datasheet。控制器寄存器通常是 MCU reset domain 的状态。两边 reset source 不同，就可能产生：Flash 回到 1-1-1 SPI，OCTOSPI 仍按 8D-8D-8D 发；或者 watchdog 只复位 CPU/控制器，而 Flash 仍留在 octal mode。这个错误不是“频率不稳”，而是双方从第一 bit 就采用不同语法。

可靠 recovery 不能直接重发 operational read，也不能在 WIP timeout 后把 payload 标成失败：timeout 只说明 host 的等待预算耗尽，器件可能尚未写、写完、随后写完，甚至留下部分/失败状态，结果是 UNKNOWN。恢复必须先作废旧 generation，把 controller 与 Flash 都带回已知 reset-state SPI，满足 tRST（复位后重新接受命令所需时间），再在一个总 deadline内依次验证：

  1. RDID 0x9F 返回 C2 85 3A。这三个 byte 分别是 Macronix manufacturer、memory type、density，来自 MX25LM51245G Rev.1.1 数据手册的 ID Definitions；ID 证明 decode path/器件类别，不证明镜像可信。
  2. status/security readback 显示 WIP=0，且 program/erase failure 位没有宣告错误；仍 busy 或 failure 必须保持 recovery，不得重开 XIP。
  3. 对被冻结的 update span 做 indirect readback，并与 old/new payload 分类：全 new 才是 VERIFIED_NEW，全 old 是 VERIFIED_OLD，混合结果进入镜像校验/擦除恢复而非猜测。
  4. 累计 reset + tRST + ID + status + readback + reconfigure 时间未超过 recovery deadline，最后才写 CR2 与 OCTOSPI tuple、重开 memory map。

主机 lab 的 hardware_reset_flash_only() 故意只改 Flash，随后 fetch 得到 XIP_PROTOCOL_DECODE_MISMATCH。完整恢复 fixture 在 1000 us deadline 内用 500 us 验证 C2853A/status-ready/readback；另一用例让 WIP 在 timeout 后晚完成，host 仍保持 UNKNOWN，直到 readback 把它分类为 VERIFIED_NEW。101 us 超过 100 us 总 deadline 会在读 ID 阶段 fail。模型没有真的读取 JEDEC 电平，不能升级成板级证据。

indirect、automatic-polling、memory-mapped 与 XIP 的边界

ST AN5050 Rev.14把 OCTOSPI/HSPI/XSPI 操作分为 indirect、automatic status-polling 与 memory-mapped 等模式：

  • indirect mode 由软件明确配置一次 command，通过 data register/DMA 发送或接收有限长度数据。它适合读 ID、写 enable、page program、erase 等离散操作。
  • automatic status-polling 让控制器反复读取 status register，按 mask/match 判断 WIP（write in progress，内部 program/erase 尚忙）等状态并置 flag。它减少 CPU 轮询开销，但 mask、match、interval 与 timeout 配错仍会误判。
  • memory-mapped mode 把一段 AHB/AXI 地址请求转换为串行 transaction，使 CPU、DMA 或其他 master 像访问内存一样发 read。AHB/AXI 是 Arm 系统互连协议；master 是能主动发起地址事务的总线参与者，OCTOSPI 在这条路径上表现为被访问的 slave/target。memory mapping 是地址转换与事务生成机制，不会把 NOR 变成 SRAM。
  • XIP（execute in place）是 CPU 直接从该映射区取指执行。memory-mapped data read 不等于 XIP；XIP 额外依赖 executable MPU attribute、vector、I-cache、异常路径和最坏延迟。

NOR 的 program/erase 仍受介质语义约束。erase 把一个 erase sector 的 bit 恢复到 1；page program 只能把 bit 从 1 写成 0，不能不擦除就把 0 变回 1。page 是一次 program 不能跨越的边界，典型为 256 byte；sector 是最小 erase 单位，通常远大于 page。实际值必须来自 MX25LM51245G 数据手册/BSP component，不能只凭“常见值”。本文 host model 为了构造可判定反例固定 page=256, sector=4096，并明确这是模型参数，不声称 sector 取值覆盖该器件所有 erase opcode。

若向 page 尾地址 255 写两个 byte，很多器件会在 page 内 wrap 或只写部分，而不是自然进入下一 page。安全 API 应在提交前证明 start/page == (end-1)/page，然后由上层拆分。若旧 bit 为 0、新 bit 为 1，应返回 ERASE_REQUIRED，而不是把 readback mismatch 当传输噪声。

XIP 更新为何会自锁：代码、vector、常量和并发 master 都是读者

当 Flash 忙于 program/erase 时，同一 bank/器件的普通 read 可能不可用或返回受限状态。MX25LM51245G 的 suspend/resume 是明确命令状态，不意味着任意 read-while-write；是否可在另一 bank 并发读要以器件架构为准。若 update 函数从外部 Flash 取下一条指令，CPU 为了完成“让 Flash 恢复可读”的代码反而需要先读 Flash，形成循环等待。

把一个函数标记到 SRAM 仍可能不够：

  • vector table 若仍指向 OSPI，任何中断入口都会读 Flash；
  • ISR 在 SRAM，但它引用的 literal pool、const table、logging format string 在 OSPI；
  • veneer/trampoline 或库函数仍由 linker 放在 OSPI；
  • DMA2D、LTDC、另一个 bus master 仍从 memory-mapped 窗口取资源；
  • speculative fetch、prefetch 或 debugger memory window 仍有 outstanding read；
  • MPU 属性和 linker symbol 与运行时地址不一致。

因此 quiescent 要定义成“所有可能访问该映射区的 master 都已停在可证明边界，且 OCTOSPI ABORT/disable 已完成”，不是“主任务决定不读”。这里 ABORT request 只是要求控制器终止当前 functional mode/transaction；提交请求后 BUSY 仍可为 1，完成 flag/callback 也尚未来。本文合同要求三项同时成立：active_readers==0、OCTOSPI BUSY==0、ABORT completion flag/callback 已观察到；次序是阻止新 reader、排空已有 reader、发 ABORT、带 deadline 等 BUSY/complete，再关闭 memory map。只写 ABORT bit 或只看到 reader count 为零都不能进入 indirect mode。owner 是谁被允许改变 Flash/controller 状态；update generation 活跃时，其他模块不能重新开启 memory mapping。host lab 分别让“request 后立刻 confirm”返回 busy=1, abort_complete=0，以及让一个 active reader 阻止 ABORT completion，最后只有 BUSY0+ABORT_COMPLETE1 才通过。

三层“旧代码”问题：Flash、控制器和 CPU 各自可能正确

假设 external NOR 地址 A 原来是指令字节 10 20 30 40，program 后阵列为 00 20 30 40。indirect read 绕开或刷新了 memory-mapped buffer，所以校验新值正确；但 OCTOSPI prefetch 仍保存含 A 的旧 burst，CPU I-cache 又保存旧 instruction line。此时每一层都在兑现自己的缓存语义，并没有一个神秘“缓存错乱”。错的是软件没有定义更新后的统一观察点。

prefetch 是控制器提前抓取后续串行数据以隐藏 latency；I-cache 缓存 CPU 指令；D-cache 缓存 data load/store；branch predictor可能保存分支方向或目标信息；DSB（data synchronization barrier）等待先前显式内存事务达到要求的完成点；ISB（instruction synchronization barrier）清空流水线，使后续指令在新 context 下重新取。它们解决不同问题，不能互换：volatile 只影响编译器对特定访问的优化，不清任何硬件 cache；只清 D-cache 也不能让旧 I-cache 指令消失。

CMSIS‑Core Cortex‑M7 D-cache API与 I-cache API提供按地址/全局维护接口。按地址操作必须扩大到完整 cache line，并避免把邻居对象的 dirty data 一起丢失。若更新的是将执行代码，安全顺序通常需要：program/erase WIP 完成 → 停止/清控制器 memory-mapped buffer → 使目标 data view 一致 → invalidate 对应 I-cache → DSB → ISB → 再跳转。精确 helper 是否已经包含 barrier、OCTOSPI buffer 如何清，必须审查固定 RM/HAL/BSP 源码，不能复制一条跨芯片“万能顺序”。

这里有两个容易混为一谈的 span。frozen update span 是 token 中不可变的半开区间 [start,end)；每个 controller/I-cache/barrier confirmation API 都必须收到完全相同的逻辑 span，不能 program 16 byte 却只同步前 4 byte。maintenance span 是实现内部按 cache-line 边界向下/向上扩大的物理范围，可以比 frozen span 大，但不得缩小。

三个完成 bit 还不够：bitmask controller=1, icache=1, barrier=1不能证明发生顺序，调用者可以先 barrier、再 I-cache、最后 controller，仍拼出全 1；重复某一步也可能被当作幂等成功。本文改用 ordinal phase：WIP completion 只进入 CONTROLLER_PREFETCH，成功后唯一下一态是 CPU_ICACHE，再到 DSB_ISB，最后 COMPLETE。每个 API 先核对完整 span 和当前 phase；乱序或重复不产生状态推进。token 从 WIP 到 COMPLETE 全程活跃，只有 confirm_update_synced() 才释放。hostile 序列依次尝试 barrier→I-cache→controller：前两步都因 actual=CONTROLLER_PREFETCH失败；controller成功后再重复 controller，又因 actual=CPU_ICACHE失败。partial span 与 early release 仍分别失败，构成“范围、顺序、唯一完成”三个独立不变量。

地址、容量、alignment 与 MPU 属性必须在进入硬件前证明

memory-mapped window 往往大于实际 Flash 容量。DEVSIZE、address byte 数和 Flash density 任一错误，都可能让高地址 alias 到低地址。安全 span 检查应使用半开区间 [address,address+length)，先证明 address <= 2^32-length，再证明 end <= actual_capacity；不能先用 32 位算 end 再比较，因为它可能 wrap。host lab 用 2^32-128 + 256 验证 overflow 被拒绝，也拒绝 Python 的 True 冒充地址 1。

alignment 是地址满足访问宽度/cache line/page/sector边界；这些边界不是一个数。CPU 32-bit load 可能要求 4-byte 对齐，cache maintenance 按 32-byte line 扩展，page program 按 256-byte 拆分，sector erase 又要求 erase-size 对齐。API 应分别命名 cpu_access_alignment、cache_line、page_size、erase_size，不能共用一个 FLASH_ALIGNMENT。

MPU（memory protection unit）为地址区间设置 memory type、cacheability、shareability、executable 与访问权限。把 XIP window 标成 Device memory 可能禁止正常取指；把 update region 永久 executable 又增加攻击面。产品通常把 active image 映射为 read-only executable，把 inactive slot 映射为 non-executable data，在校验签名并原子切换 boot metadata 后才改变角色。secure boot验证镜像来源与完整性；cache coherency保证 CPU 观察到刚写入的 byte。前者不能替代后者，后者也不判断代码是否可信。

更新实现骨架：把更新器的依赖闭包放进 SRAM

下面是目标 C 设计骨架，不是本次编译或板级运行 transcript。RAMFUNC 必须通过 linker map file（链接器给出的 symbol 到地址清单）和运行时地址检查证明生效；所有被调用函数、常量和异常路径都属于依赖闭包。BSP（board support package）是把 HAL/driver 与具体开发板连线、器件和初始化绑定的支持层。本文只以固定 ExtMem_CodeExecution/ExtMem_Boot、BSP/component/HAL gitlink 组合为 tuple 来源；同仓库的 standalone OSPI_NOR_MemoryMapped_DTR 示例使用不同 prescaler/dummy 常量，不能混成同一个配置证据。

dependency closure 是从 update entry 可达的一切代码和只读数据集合。验收不能只 nm 看 entry symbol；还要审查 linker map、relocation/call graph，并在 OSPI 禁读期间触发允许的中断。若无法证明 ISR 全部在 SRAM，安全选择是只保留 SRAM 中的最小 watchdog/power-fail 路径并屏蔽其他中断，但屏蔽时长又必须满足系统 real-time 与 watchdog 约束。

同一命令随后在独立进程双跑，要求 exit 0、stderr 为空、stdout byte-identical；冻结检查还会逐字节比较正文 transcript。host model 不模拟 instruction pipeline、真实 cache line size、DQS、OCTOSPI flag 或器件 program time。

故障注入与定位闭环

第一条故障先 fetch 10203040，完成合法 1→0 program 后通过 test-only backdoor 跳过 view sync。现象是 Flash array=00203040，CPU fetch=10203040。初始假设“program 失败”被 array 证据否定；证据又指出 stale layers=prefetch+icache，定位到映射读取路径。修复是 token 冻结完整 update span，WIP 完成后按 ordinal phase依次确认 controller prefetch、I-cache、DSB/ISB；任何 partial span、提前 release、乱序或重复都失败，到 COMPLETE 才恢复 memory map。敌意序列 barrier→I-cache→controller 的前两步没有推进 phase，controller完成后重复 controller 也被拒绝；正确序列回归得到 fetch=00203040。

第二条故障只 reset Flash，不 reset controller。现象是下一次 fetch 无法解码；证据显示双方 protocol tuple 不相等，定位到 reset domain/模式交接，而非信号随机错误。修复是 fail closed 回到双方已知 SPI，在总 deadline 中核对 C2853A、WIP/failure status和冻结 span readback，再共同进入固定 100 MHz + CR2 0x07 + HAL DummyCycles 6 tuple。回归记录 500/1000 us；101/100 us 的敌意恢复在 ID 阶段超时。

第三条故障令 WIP busy 1001 us、deadline 1000 us。timeout 后 outcome 明确是 UNKNOWN，模型再注入“器件在 host timeout 后完成 program”；只有 reset-state readback=00 才把结果分类为 VERIFIED_NEW。generation 从 0 升到 1，迟到 completion 得到 XIP_STALE_GENERATION:0:1。这闭合了“超时 → 未知结果 → 作废生命周期 → 双方复位 → ID/status/readback → 重新配置”的路径，避免把 timeout 误记为失败或旧 ISR 把新 update 标完成。

第四条故障在发出 ABORT request 后立刻检查 quiescent。BUSY=1, ABORT_COMPLETE=0 直接否定“写 ABORT bit 即已退出”；另一个 active reader 又否定“controller flag 足够”。修复链必须同时排空 reader 并等待硬件 BUSY/complete。第五条故障把 controller dummy 改成 8，既得到 protocol split，又由 build tuple validator 证明该数值与 100 MHz/CR2 0x07/HAL 6-cycle 固定来源不一致。

其余敌意案例覆盖跨 page、未擦除的 0→1、同 Flash 执行器/vector、32 位 span wrap、bool 地址和无限时间。每个错误在硬件副作用前被分类；这只证明软件 guard，不证明真实硬件没有其他 fault。

目标板计划实验与通过标准（本次未执行）

准备 STM32H735G‑DK、STM32CubeH7 v1.12.1 固定 root/BSP/component/HAL commits、ST‑LINK、8 通道逻辑分析仪/高速示波器、可恢复的 A/B 测试镜像。先构建固定 ExtMem_CodeExecution/ExtMem_Boot，保存 map file、编译选项和 binary hash，再加入 fault variants；不把使用不同 dummy/prescaler 的 standalone example 混入证据。

  1. 抓 CS#/CLK/DQS/IO0..7，对照 0xEE11、32-bit address、6 个 full dummy clocks 与 data phase；同时 dump OCTOSPI clock/prescaler、CR2 0x300 与 status。通过：SCK 实测 100 MHz，controller dummy=6、CR2 code=0x07、DQS enable；冷启动、watchdog/software reset 后先在 reset-state SPI 读到 C2 85 3A，再进入同一 tuple。
  2. 在 25/50/100% 目标频率、最低/最高供电与温度边界扫 delay tap。用固定种子的 PRBS（pseudo-random binary sequence）产生 address/data，便于复跑并比全零更容易暴露粘连。通过：indirect 与 mapped read 全一致，记录连续通过窗口和中心 margin；单点 PASS 不算调谐证据。
  3. 把 update entry、全部 callee、vector 和常量链接到 SRAM，由 map-file 自动审计；更新时让 debugger 不打开 OSPI memory window。通过：退出 mmap 时先阻止 reader，ABORT request 后观察 BUSY→0 与 completion flag/callback；program/erase WIP 期间无外部 Flash read transaction，未迁移依赖会确定性触发 fault variant。
  4. 先 populate I-cache/controller prefetch，再更新 4 KiB 函数区。分别传 partial span、缺 controller 清理、缺 I-cache invalidate、缺 DSB/ISB、提前释放 token，以及 barrier→I-cache→controller、重复 controller/I-cache/barrier 的乱序。通过：所有 maintenance API 的逻辑 span 与 update token 完全一致，内部才按 cache line 扩大；phase 只允许 controller→I-cache→DSB/ISB→complete，任何乱序/重复均不推进；fault variants 稳定拒绝或读到旧 generation，完整序列十万次都取到新 generation；保存 ETM（Embedded Trace Macrocell，处理器指令流硬件跟踪）或 logic-analyzer trace。
  5. 在 update 的 WREN、program、WIP timeout、cache sync、metadata commit 各阶段 reset，并分别注入 late-complete/未完成/混合 readback。通过：timeout 初始只报告 unknown；在总 deadline 内验证 ID、WIP/P_FAIL/E_FAIL 与整个 update span，分类 old/new 后才选择 A/B 已签名镜像；任何 mode split、status failure、mixed readback 或 deadline miss 都保持安全恢复，而不是无限 HardFault（Cortex‑M 对无法归入更具体异常的严重 fault） reset loop。

练习与可判定答案

  1. 8-8-8 与 DTR 是同一属性吗？本文固定 tuple 还缺哪些字段？ 答：不是。前者描述各 transaction phase 的 I/O 线宽，DTR 描述每时钟两个边沿传输；本文还绑定 build target、100 MHz、opcode 0xEE11、32-bit address、DQS、CR2 code 0x07 与 HAL 6 个 full clock cycles。
  2. indirect read 新值正确为何不能证明 XIP 新值？ 答：两条路径可能经过不同 controller buffer，且 XIP 还会命中 I-cache/流水线；必须验证 Flash、controller mapped view 与 CPU instruction view。
  3. 为什么 volatile 指针不能修复旧代码？ 答：它约束编译器执行访问，不会失效 OCTOSPI prefetch 或 I-cache，也不会执行 DSB/ISB。
  4. update 函数已在 SRAM，仍可能死锁的三个原因是什么？ 答案至少包含：vector/ISR 或 callee/const 仍在 OSPI、其他 bus master 在读 mapped window、退出 mmap 尚未 quiescent。只答“cache”不合格。
  5. 跨 256-byte page 的 300-byte payload 应如何处理？ 答：先做无回绕 span 检查，按当前 page 剩余空间拆分为多个 page program，每次 WREN/program/WIP/错误检查；不能假设器件自动跨页。
  6. secure boot 与 cache coherency 的关系？ 答：secure boot回答“镜像是否可信/完整”，coherency 回答“处理器看到哪一版 byte”；两者互不替代，必须都闭合。
  7. 发出 ABORT request 后为何不能马上 program？ 答：request 不是 completion；还需所有 reader 归零，并看到 OCTOSPI BUSY=0 与 ABORT completion，三项共同证明 mapped transaction 静止。
  8. program 16 byte 后只 invalidate 命中的 4-byte instruction 是否足够？ 答：不足。token 冻结整个 16-byte逻辑 span，controller/I-cache/barrier confirmation都必须绑定完整 span；实现内部可扩大到 cache line，不能缩小。
  9. WIP timeout 能否直接选择旧镜像？ 答：不能，结果是 unknown。必须 reset 到已知 SPI，在总 deadline 内验证 JEDEC ID、status 与完整 span readback，再分类 VERIFIED_OLD/NEW；混合结果保持 fail closed。
  10. 三个 sync-done bit 最终都是 1，为什么仍不足？ 答：bitmask只证明集合，不证明次序或唯一执行；barrier先执行、controller后清理也能得到全 1，却没有建立正确观察点。要用 ordinal phase强制 controller→I-cache→DSB/ISB→complete，并让每步乱序/重复都失败且不推进。
