IELTS 每日学习 — 2026-10-03

发表于 2026-10-03 分类于 每日学习 本文字数： 9.7k 阅读时长 ≈ 35 分钟

今日主线：IELTS Academic 周末整合复习与主动输出。

🔧 嵌入式知识：嵌入式单元、集成与 HIL 测试分层

嵌入式测试金字塔：按可证明的主张分层，而不是按固定比例堆用例

“单元测试多、HIL 测试少”只是成本直觉，不是测试充分性的证明。纯函数的边界可在 host 上每次提交枚举，真实 ADC 饱和、复位毛刺、总线电气和闭环截止期却只能在具有相应现象的载体上观察。如果一条安全需求只有一百个 mock 用例而没有任何真实 I/O 证据，金字塔再漂亮也没有闭包；反过来，把所有逻辑错误都留到稀缺 HIL 台架上发现，又会让反馈过慢、定位困难且不可规模化。

本文用“需求主张—层能力—oracle—证据”闭包设计测试组合。平台基线固定为 Zephyr 4.2.0 的 Ztest/Twister 文档、Renode tag v1.15.3 的完整 commit 03756cb5a3112fb94aeffef227ddec48db531cad 及其官方 Robot 测试工作流。固定 tag 的 tests/requirements.txt 明确要求 robotframework==6.1，所以计划使用精确 6.1，而不是从滚动文档或发布页文字猜依赖。实际只在 macOS Darwin arm64、Python 3.14.0 执行 scripts/labs/embedded_test_pyramid_hil_fault_lab.py 的确定性契约模型；没有安装或运行 Zephyr、Renode，没有连接 HIL 或目标板。zephyr_execution=false、renode_execution=false、hil_hardware=false、target_hardware=false 是机器可读边界；脚本新增的 ExternalExecutionPlan 只验证未来命令前提，不把计划升级成运行证据。

七个层的边界要用“真实参与者”定义

层名不是统一标准，团队必须先写自己的定义。本文固定如下：

  • UNIT：只编译被测纯逻辑及必要 stub/mock，直接调用函数；不启动完整 RTOS，不含真实驱动模型。适合状态转换、编码器、校验、限幅、错误分支和大量确定性故障枚举。
  • COMPONENT：把一个可部署组件连同其公开 API、适配层或寄存器契约测试；外部依赖可控。它能证明组件边界和局部协议，但未证明多个真实组件协作。
  • INTEGRATION：连接两个或更多真实软件组件、进程或子系统，例如任务、队列、存储服务和协议栈，观察接口、生命周期与并发。外围仍可能是 fake，故不自动证明物理 I/O。
  • SIL：software-in-the-loop，执行固件构建产物或接近目标的软件镜像，但被控对象和 I/O 仍由软件提供。它擅长长回归、算法和镜像级启动路径，不等于真实 MCU 时序。
  • VIRTUAL_PLATFORM：在 QEMU、Renode 等指令/设备模型上运行固件二进制，能观察模型实现的寄存器、中断、协议和故障。模型未实现的电气、模拟、竞争和时序现象仍不存在。
  • HIL：hardware-in-the-loop，把真实控制器或真实 I/O 的一部分接到实时被控对象/台架，形成闭环，测量端到端时序并注入物理或协议故障。HIL 的对象模型和功率级仍可能与真实产品不同。
  • TARGET：在实际目标处理器/板卡上运行，覆盖真实编译、启动、电源复位、物理 I/O 和目标时序；若没有外部闭环对象，它仍不自动具备 HIL 的闭环故障能力。

这些层可以重叠。例如 HIL 中通常包含目标板，SIL 可以运行与目标相同的固件二进制，virtual platform 也可被组织成 integration test。判定依据是本次证据真正包含哪些参与者和可观察现象，而不是测试目录名称。Zephyr 4.2.0 Ztest 文档 特别区分 unit_testing 伪板与 native_sim：前者不构建内核、调度器和驱动模型，后者运行完整 Zephyr host 二进制。把二者都叫“host test”会丢失关键边界。

“host test”还不等于“可在任意 host OS 原生运行”。unit_testing 生成由 host 工具链编译的普通进程，但 Zephyr 4.2.0 文档把它的运行支持限制为 Linux；macOS 或 Windows 必须提供 Linux 环境。这里必须把三层内核关系说准确：在原生 Linux Engine 上，Linux container 与 Linux host 共享内核；但 Docker Desktop for Mac 不是让 Linux container 共享 Darwin/XNU 内核。Docker 官方 Mac 权限与架构说明 明确写明 Docker daemon 与 containers 运行在 Docker 管理的轻量 Linux VM 中，Mac VMM 文档 也把各 VMM 描述为驱动“运行 containers 的 Linux VM”。所以本文拓扑是：

这个区分直接影响证据语义。容器里的 uname、syscall、线程与 Zephyr unit_testing 观察的是 Linux VM 内核行为；bind mount、网络、时钟和 CPU 调度仍经过 Docker Desktop 虚拟化边界。它既不是 macOS 原生进程，也不证明目标 MCU 的调度、驱动或硬件时序。本机是 Darwin，因此计划字段固定 unit_guest=Linux、isolation=CONTAINER、kernel_provider=DOCKER_DESKTOP_LINUX_VM；把 guest 写成 Darwin 返回 TEST_ZEPHYR_UNIT_LINUX_GUEST_REQUIRED，把隔离写成 NATIVE 返回 TEST_ZEPHYR_UNIT_ISOLATION_REQUIRED，把 provider 伪写成 MACOS_HOST_KERNEL 返回 TEST_DOCKER_DESKTOP_LINUX_VM_REQUIRED。这些字段只验证未来执行拓扑的声明，没有检查 Docker daemon、镜像或 VM，本轮证据仍为 zephyr_execution=false。

金字塔不是固定配额，而是风险和经济性的结果

“70% unit、20% integration、10% HIL”不能跨项目复制。无外设的数学库可能接近这个形状；传感器融合板、功率变换器或安全执行器的物理故障很多，HIL/target 证据比例会更高；协议网关可能需要大量 virtual platform 和 integration。合理分配至少考虑：

这个式子不是精确财务模型，而是强迫评审问五件事：失败后果多大、该缺陷多可能、该层是否真能看见、反馈有多慢、失败能否定位。低层测试便宜且快，应承接所有可下沉主张；高层测试保留无法替代的模型差异、真实时序、物理 I/O 和端到端闭环。测试组合可能是蜂巢或菱形，只要需求闭包、反馈速度和残余风险明确。

本文实验把五项必需主张 pure_logic/virtual_device/physical_io/closed_loop_real_time/power_reset 分配到 UNIT,VIRTUAL_PLATFORM,HIL,TARGET，返回 COVERED。删除 TARGET 会留下 power_reset 缺口；仅增加更多 UNIT 用例不会补上，因为层能力不支持该主张。layer_substring=TEST_LAYER_UNKNOWN 还锁定了精确层名，防止用 "HIL" in "NOT_HIL" 一类 substring 误接收。

Oracle 决定测试是否真正可判定

刺激和日志不是 oracle。oracle 是把观察转为通过/失败的明确规则。本文固定六类：

  • EXACT_VALUE：纯函数、编码字节或状态的精确值；要考虑浮点/平台是否允许精确比较。
  • RANGE：电压、温度、延迟、误差位于经过依据批准的区间；区间边界必须固定。
  • TEMPORAL：事件先后、最大响应时间、持续时间与 deadline；需要定义时钟源和采样误差。
  • TRACE：协议事务序列、寄存器访问或状态轨迹与允许语言匹配；不能只搜索“PASS”子串。
  • SAFETY_STATE：故障后在截止期内进入确定安全状态，并保持或受控恢复。
  • STATISTICAL：通过样本分布、置信水平与效应阈值判定，而不是单次均值。

每条链必须包含五个不可跳过的节点：requirement_id -> claim -> selected layer capability -> oracle -> evidence_id。需求描述“断线后 50 ms 安全停机”时，claim 不能只写成泛化的“测试过”，而应拆成 physical_io、closed_loop_real_time 和 SAFETY_STATE/TEMPORAL 等可判定主张；链接选 HIL 后，门还要证明 HIL 的能力集中确实包含相应 claim。REQ-001 一类 ID 必须匹配固定模式，相同 (requirement,claim,layer,oracle) 的重复链接被拒绝，层必须在本计划的 selected layers 中，每个 (requirement,claim) 都要有链接，oracle 必须属于固定集合，evidence ID 必须非空。

为什么 aggregate coverage 和结构性 traceability 仍然不够？考虑敌对输入：必需 claim 是 physical_io，selected layers 是 (UNIT,HIL)，因此能力并集含 HIL 的 physical_io，aggregate plan_coverage 返回 COVERED；再把需求链接到 UNIT，并填上合法 oracle/evidence，结构门只看“需求有链接”也会返回 TRACEABLE。两个绿灯同时存在，但实际承担该链接的 UNIT 不具备 physical_io。本实验把这个输入固定为 hostile_prechecks=COVERED+TRACEABLE，最终端到端门沿链接调用 layer_claim_gate("UNIT","physical_io")，稳定返回 TEST_LAYER_UNMODELED_CLAIM。这正是“所选集合中有人能做”和“这条证据由能做的那一层产生”的区别。

正常矩阵有五条明确链：REQ-101/pure_logic/UNIT/EXACT_VALUE/unit-report-101，REQ-102/virtual_device/VIRTUAL_PLATFORM/TRACE/virtual-trace-102，REQ-103/physical_io/HIL/RANGE/scope-trace-103，REQ-104/closed_loop_real_time/HIL/TEMPORAL/scope-deadline-104，以及 REQ-105/power_reset/TARGET/SAFETY_STATE/powercut-105。脚本输出 links=5 ... VERIFIED 只证明这些结构与能力映射一致；“有链接”仍不等于证据真实。CI 还需验证 evidence 文件存在、hash 与本次固件对应、测试实际运行而非 build-only、结果不是 skip/quarantine、oracle 版本与需求版本匹配，并校验原始观测确实支持 verdict。

Zephyr 4.2.0 Twister 官方说明 明确区分 buildable 与 runnable，并会在 twister.json 报告执行方式；build_only、缺 harness、未连接设备等都可能只构建不运行。因此“Twister 绿了”不能自动解释为目标测试通过，验收脚本必须检查每个实例的 platform、handler、status 和 reason。

Coverage 是多张地图，不能互相替代

代码行/分支覆盖回答哪些实现被执行；MC/DC 回答条件中每个原子是否能独立影响决策；功能覆盖回答规范场景和边界是否出现；需求覆盖回答需求是否有合格证据；故障覆盖回答故障集合是否被注入并观察到预期反应；时间覆盖回答 deadline、抖动、负载和持续窗口是否命中。

100% 代码覆盖可能没有断言，100% 需求链接可能只链接到跳过用例，全部功能 bin 命中也不能证明状态空间无错误。覆盖门必须声明 numerator、denominator、排除和 waiver。Zephyr 的 coverage 文档 也说明目标/QEMU/host 收集方式和 RAM 限制。实验的 coverage_gate 要求 required/hit 都是 set/frozenset，先逐项验证非空字符串，再做 subset；缺项返回 COVERAGE_GAP。它刻意不接受 list 或裸字符串，避免重复、substring 和字符迭代改变语义。

保真度、吞吐量和成本要同时量化

UNIT 每秒可运行成千上万例、控制最强、定位最短，但物理保真度低。Virtual platform 可跑完整固件并做精确快照/故障注入，速度通常高于真实时间或可并行，但真实性以设备模型实现为上限。HIL/target 看见真实 I/O、编译与部分实时行为，却受台架数量、刷写、热稳定、机械动作和安全人工限制。

因此每个测试应记录预计/实测 runtime、并行度、台架占用、setup/teardown、模型版本、可观察信号和未覆盖现象。高层失败后，应提取最小 trace 下沉到 component/virtual/unit；低层发现的边界故障若涉及模型差异，应向上增加目标回归。分层的价值不是把同一个 happy path 复制七次，而是用最低成本层穷举逻辑，再在高保真层验证差异假设。

Renode 1.15.3 官方发布 给出人类可读版本入口，完整 commit 03756cb5a3112fb94aeffef227ddec48db531cad 才把源码树固定到一个对象；tag 名与 commit 相邻但不等价，因为 tag 引用理论上可以移动。该 commit 的 tests/requirements.txt SHA-256 为 fefef7299387c7d4bce7e9159810d44708332404f8bdfe0a546c46e2897b044d，首项是精确的 robotframework==6.1。依赖 manifest 是实际 pip install -r 的机器输入，优先于发布页概述；若二者文字冲突，不能挑更方便的版本。脚本把 tag、完整 commit 和精确 requirement 作为同一个计划门，latest、短 commit 或范围依赖都会失败。

Renode 测试工作流 用 renode-test 启动模拟器与 Robot Framework，可并行和重复；但这个链接是滚动文档，不能覆盖固定 tag 的源码语义。Renode v1.15.3 commit 03756cb... 的 tests/renode-keywords.robot 第 21 行 把 ${CREATE_SNAPSHOT_ON_FAIL} 默认设为 True；同文件的 Test Teardown 第 158–174 行 在测试失败时调用 Create Snapshot Of Failed Test。因此，对这个固定版本而言，失败 snapshot 的触发链是“默认变量为真 + Robot Test Teardown 检测失败”，RENODE_CI_MODE=YES 不是必需触发条件。把滚动文档中的环境变量要求倒灌到 v1.15.3，是版本来源错配。

这段源码还有三个必须保留的边界。第一，teardown 在检测到 timeout 后会提前 RETURN，所以“任何非通过结果一定有 snapshot”并不成立；预期失败探针必须选择普通 assertion failure，并单独覆盖 timeout 证据。第二，默认值可以被 Robot 变量覆盖，因此运行记录仍应保存最终 ${CREATE_SNAPSHOT_ON_FAIL} 值、完整命令和 suite 变量。第三，runner 只会在测试没有自定义 teardown 时注入资源里的 Test Teardown；如果 probe 自己声明了 [Teardown]，不能再假设 runner 的 snapshot 分支会自动执行。可选闭包只有两种：本文选择 probe 不定义自定义 teardown，让 runner 注入固定的 TEST_TEARDOWN；若产品必须自定义清理，则该 teardown 要显式调用对应 snapshot keyword，并另写失败回归证明调用发生，不能只在文档中声称“仍会注入”。

失败 snapshot 是模拟器在失败点的可装载状态，便于复现寄存器、内存与设备模型；日志记录观察序列但不能恢复状态。snapshot 还依赖 Renode/模型/固件版本兼容，并可能漏掉外部不可序列化资源。实验计划门据 tagged source 固定 snapshot_default=true、snapshot_hook=TEST_TEARDOWN 和 snapshot_probe_custom_teardown=false，明确输出 runner_injects_teardown=true、ci_mode_required=false；把 custom-teardown 标志改成字符串先得到类型错误，改成真则得到 TEST_RENODE_SNAPSHOT_PROBE_CUSTOM_TEARDOWN。本轮没有运行失败 suite，因此这仍是源码对齐的计划契约，不是 snapshot 已生成的证据。

可重复随机与 flake 治理

随机顺序和故障参数可暴露共享状态、竞争和顺序依赖，但每次失败必须打印 seed、用例集合、固件/模型 hash 和调度参数。实验以 0x12345678 对固定 case tuple 做确定性排列，摘要 fb5ba3dd5a05，重复调用必须一致。容器必须是 tuple 且成员逐项为非空字符串；list、bool、重复 ID 都返回稳定域错误。

flake 是相同声明输入下结论不稳定。常见根因包括未复位全局状态、后台线程、墙钟等待、串口旧日志、共享端口、未独占台架、电源余热、USB 重枚举、无线干扰和过窄 timeout。重试可以收集统计，不能把“第二次通过”改写成通过。应保存每次 attempt，按 test/rig/firmware 分层统计 flake rate，给 quarantine 责任人和到期时间，并用故障预算阻止无限增长。

timeout 必须基于协议或实时预算，而非把 CI 慢简单乘十。等待应以单调时钟和目标事件结束，失败时输出最后状态。setup/teardown 要幂等；即使测试失败，也必须复位输出、关闭电源、释放端口和台架租约。共享资源冲突应归类 infrastructure error，而不是 DUT failure。

故障注入必须定义注入点、oracle 和恢复

好的故障用例至少包含 fault ID、层、注入方式、开始条件、持续/次数、预期安全状态、截止期、清除与恢复。UNIT 可注入函数返回错误、边界值和内存分配失败；virtual platform 可注入寄存器延迟、中断丢失、包损坏；HIL 可断线、过压保护范围内调幅、模拟传感器冻结和总线错误；target 可做真实复位/掉电。不是所有层都支持每个故障，本文只允许具有 fault_injection 能力的 VIRTUAL_PLATFORM 和 HIL 创建 FaultCase，在 UNIT 标成同一物理故障会返回 FAULT_LAYER_UNSUPPORTED。

故障后只看到“程序未崩溃”不是充分 oracle。安全需求应写“在 50 ms 内关闭驱动，输出低于阈值，记录诊断码，未收到授权不得自动恢复”。测试还要验证注入确实发生，否则断线继电器未动作会产生假通过。现实台架应有独立测量通道和注入确认信号，证据包保存电源/总线波形、控制日志和统一时间基准。

跑 n 次零失败不代表失效率为零。在独立同分布 Bernoulli 且检测可靠的简化假设下，置信度 C 的单侧上界为：

log1p(y) 在 y 接近零时保留 log(1+y) 的有效位，expm1(x) 则直接计算 exp(x)-1，避免再从两个接近 1 的浮点数相减。实验加入两个会击穿朴素写法的边界：n=1,C=1e-20 必须严格大于零并约等于 1e-20；n=1e9,C=1e-10 必须严格大于零并约等于 1.00000000005e-19。每项都用 Python Decimal 80 位精度独立计算 -(exp(ln(1-C)/n)-1) 作为 oracle，相对误差必须小于 1e-15。高精度 oracle 只是验证浮点实现，仍不放宽独立 Bernoulli、代表性样本和可靠检测这些统计前提。

统计 oracle 必须预先固定样本单位、总体、置信度、通过阈值、丢失样本和停止规则。测试后才挑窗口或只报告最好台架属于选择偏差。本文公式只是确定性数值边界，不是产品失效率证明。

失败定位与跨层闭环

失败先分类为 DUT、oracle、模型、harness、台架或基础设施。保存 requirement ID、测试层、镜像/模型/台架身份、seed、输入、时间线和原始日志；确认测试确实运行且注入发生。然后从第一个状态分叉定位：若 unit 已失败，先修纯逻辑；若只在 virtual 失败，比较设备模型与协议规范；若 virtual 通过而 target 失败，检查寄存器副作用、时序、电源和未建模并发；若仅 HIL 失败，检查闭环延迟、模型/真实接口和安全限制。

修复后把现场 trace 最小化：能下沉的故障加入 UNIT/COMPONENT 以获得快速回归，模型差异加入 virtual 差分，真实物理差异保留 target/HIL 门。全量重跑时检查 requirement closure、oracle、coverage、deadline、flake、统计和台架 cleanup。只有原层复现消失、低层防回归加入、高层相邻验证通过且 evidence 可追溯，问题才关闭。用加 timeout、无限重试或 quarantine 永久化来“变绿”都不是修复。

本次实际注入的完整闭环是同一台架预约重叠。现象是 rig-A 的 [0,10) 与 [9,14) 返回 overlap=HIL_SCHEDULE_CONFLICT，第二项没有被静默排队。第一假设是共享台架被两个作业同时占用，会让串口、电源和固件身份互相污染。证据是两个 HilReservation 均先通过类型、范围和 SAFETY- token 检查，排序后区间交叠条件成立；因此定位在调度资源而非 DUT。修复是让第二预约从 slot 10 开始或换独立 rig，并在真实系统增加租约/cleanup。回归锁定 [0,10) 与 [10,15) 返回 SCHEDULED、重复/越界/坏 token 仍失败、过流仍触发安全门。这里执行的是离散调度模型，没有真的抢占 HIL 硬件，故不能升级为台架联锁已验证。

数值审查另闭合了零失败上界的消减缺陷。现象是数学结果严格为正，但朴素 1-exp(...) 在 n=1,C=1e-20 和 n=1e9,C=1e-10 上都可能因 exp(x) 舍入到 1 而返回 0。第一假设是两个接近 1 的浮点数相减丢失全部有效位；证据是 80 位 Decimal oracle 分别给出约 1e-20 与 1.00000000005e-19，而不是零。定位在最后的 1-exp(x)，不是统计公式或输入范围。修复为 -expm1(log1p(-C)/n)，回归同时要求两个结果严格正、相对高精度 oracle 误差小于 1e-15，并保留常用 1000/0.95 -> 0.002991。若平台数学库不能满足该数值门，应停止签核并使用经过验证的高精度/专用实现，不能用绝对 epsilon 把零改成一个猜测值。

本轮还完成了外部计划漂移的闭环。现象是原计划从发布说明文字推导 Robot 依赖，把 macOS 上 Docker container 笼统描述成“共享宿主内核”，又用滚动 Renode 文档给 v1.15.3 推导 snapshot 触发器；这些步骤无法由固定源码和实际运行拓扑共同复现。第一假设是来源版本与内核层级没有进入机器门。证据有三组：v1.15.3 完整 commit 的 tests/requirements.txt 首项为 robotframework==6.1、文件摘要为 fefef...044d；Docker 官方文档说明 Mac 上 daemon/container 位于 Docker Linux VM；同一 Renode commit 的 renode-keywords.robot 把 ${CREATE_SNAPSHOT_ON_FAIL} 默认设为 True，并在 Test Teardown 的失败分支创建 snapshot。定位同时落在依赖 pin、Docker VM kernel 语义和 tagged-source teardown 三处，而不是测试用例逻辑。

修复后的 ExternalExecutionPlan 明确记录 host、Linux guest、isolation、kernel provider、精确 Renode tag/commit/requirement、tagged source 的 snapshot default/hook，以及 probe 是否自定义 teardown。回归中有效计划返回 VALIDATED_NOT_EXECUTED，Darwin guest、NATIVE isolation、伪造 macOS container kernel、latest tag、短 commit、范围依赖、关闭 snapshot、错误 hook、自定义 teardown 错型和自定义 teardown 启用各自返回不同错误；独立最小探针也锁住 custom-teardown 前提。若产品选择“显式调用 snapshot keyword”的另一条路径，应新增独立计划类型与运行证据，不能把本门的 false 偷改成 true。若将来 tag 或 runner 真正更新，必须先审核新 commit、依赖文件、runner 注入条件和 teardown 实现，重建带 hash 的 lock、复跑 virtual/target 差分，再改期望常量；不能从 latest 文档直接修改旧 tag 语义。因为本次没有安装外部工具，闭环证明的是“计划与固定源码及拓扑不再自相矛盾且可被拒绝”，不是 Zephyr/Renode 测试已通过。

需求链的闭环也单独注入过反例。旧结构先分别计算能力并集与 requirement ID 链接，因此敌对输入同时得到 COVERED 和 TRACEABLE；第一假设是链接对象漏掉 claim，导致能力检查无法绑定到实际产证层。证据是同一 physical_io 链接放在 UNIT 时，UNIT capability set 明确不含该项。修复给 RequirementClaim 与 TraceLink 都加入 claim，端到端门再按顺序检查 selected layer、声明 pair、层能力、oracle 和 evidence；原输入现在返回 TEST_LAYER_UNMODELED_CLAIM。回归同时锁定未选择层、未声明 claim、claim 缺口和正常五链，防止未来又退化成两个互不相干的绿灯。

练习与确定答案

  1. unit_testing 与 native_sim 都在 host 执行，是否是同一层？答案：不是；前者隔离模块且不构建完整 Zephyr，后者运行完整系统。
  2. 一百个 mock 驱动测试能否证明真实 ADC 饱和？答案：不能，所选层没有物理 I/O 能力。
  3. HIL 一定等于最终产品环境吗？答案：不等于，被控对象、功率级和环境仍可能是模型。
  4. TARGET 测试一定有闭环对象吗？答案：不一定，因此不能自动替代 HIL。
  5. 测试打印日志但没有判定规则，是否有 oracle？答案：没有明确可审核 oracle。
  6. 100% 行覆盖能否证明需求闭包？答案：不能，覆盖维度不同。
  7. Twister 绿灯能否不看报告就声称目标已执行？答案：不能，可能 build-only、skip 或模拟执行。
  8. 本文 7.5+2.5=10 ms 是否通过？答案：通过，等号是 DEADLINE_MET。
  9. 重试后通过能否抹掉第一次失败？答案：不能，每次 attempt 都要保留并计入 flake。
  10. 1000 次零失败、95% 置信度的上界是多少？答案：约 0.002991。
  11. 同一台架连续一千周期一定是独立 Bernoulli 试验吗？答案：不一定，温度和共同根因会相关。
  12. 两个相邻 HIL 时段是否冲突？答案：不冲突，本文返回 SCHEDULED；重叠才失败。
  13. 软件 safety token 能否替代硬件急停？答案：不能。
  14. 本文是否执行了 Zephyr、Renode 或 HIL？答案：都没有，证据行全部为 false。
  15. macOS 能否原生执行 Zephyr 4.2.0 的 unit_testing？答案：官方只支持 Linux；在 macOS 必须使用 Linux container 或 VM，并冻结 guest 环境。
  16. unit_testing 放进 Linux container 后是否变成 native_sim？答案：不会；前者仍只链接被测模块与 Ztest，后者构建并运行完整 Zephyr host 系统。
  17. 本文为 Renode 1.15.3 固定的 Robot requirement 是什么？答案：tag commit 的 tests/requirements.txt 明确为 robotframework==6.1。
  18. 为什么同时记录 tag 与完整 commit？答案：tag 便于人读但引用可移动，完整 commit 固定源码对象；两者一致才能兼顾版本语义和不可变身份。
  19. Renode v1.15.3 保存普通失败 snapshot 是否必须设置 RENODE_CI_MODE=YES？答案：不必须；tagged source 默认 CREATE_SNAPSHOT_ON_FAIL=True，并由 Test Teardown 的失败分支触发。计划仍显式传该 Robot 变量并验证 .save，用于冻结运行输入而不是开启一个默认关闭的功能。
  20. snapshot 是否能证明真实 ADC、电源或 ISR 时序？答案：不能，它保存 Renode 模型状态；真实物理现象仍需 target/HIL。
  21. VALIDATED_NOT_EXECUTED 表示什么？答案：外部计划的版本、host/guest/kernel provider、isolation、依赖和 tagged-source snapshot 字段通过静态门，不表示任一外部工具已经运行。
  22. Docker Desktop for Mac 的 Linux container 共享哪一个内核？答案：共享 Docker Desktop Linux VM 的 Linux kernel，不共享 macOS 的 Darwin/XNU kernel。
  23. plan_coverage=COVERED 且 requirement ID 都有链接，是否已证明每条链选对层？答案：没有；还必须把 requirement 的 claim 绑定到具体链接层，并确认该层 capability set 支持它。
  24. 敌对示例为何能同时预检为 COVERED+TRACEABLE？答案：HIL 在所选层并集中提供 physical_io，而结构链接又让需求有证据 ID；但链接实际指向 UNIT，端到端门因此拒绝。
  25. v1.15.3 的 timeout failure 是否由当前 teardown 路径保证 snapshot？答案：不保证；源码在 snapshot 分支前对 timeout 提前返回，应单独验证并保存 timeout 证据。
  26. snapshot probe 自己定义 [Teardown] 后，能否仍假定 runner 注入资源 Test Teardown？答案：不能；本文选择 probe 不自定义 teardown，若必须自定义则要显式调用 snapshot keyword 并提供运行证据。
  27. 为什么 1-exp(log1p(-C)/n) 在小概率下会错误返回零？答案：exp(x) 可能舍入为精确 1，再与 1 相减丢失全部有效位；应使用 -expm1(log1p(-C)/n)。
  28. n=1e9,C=1e-10 的上界能否写成 0？答案：不能；稳定双精度与 80 位 oracle 都给出约 1.00000000005e-19，且严格为正。
