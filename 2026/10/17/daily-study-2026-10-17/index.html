🔧 嵌入式知识：DMA Descriptor、Scatter-Gather 与 Ownership

工程问题：DMA 偶发搬到旧数据，真正坏掉的是哪一层

本文锁定目标平台为 MIMXRT1060-EVKB（MIMXRT1062，Arm Cortex‑M7）+ MCUXpresso SDK 26.06.00 的 eDMA 驱动；主机证据环境是 macOS Darwin arm64、Python 3.14.0 标准库。目标板尚未在本次执行中连接，所以所有“cache 已到达一致点”“eDMA 已取走某个 TCD”“外设已经真正发完”的说法都列为计划验证，绝不由主机模型代证。

真实故障常长这样：CPU 构造两段网络包，把两个 Transfer Control Descriptor（TCD，传输控制描述符）串起来，启动 eDMA；一万次中有几次，第二段还是上一包内容，或链尾长度突变。关掉 D‑cache 后故障消失，于是团队把结论写成“DMA 不可靠”。这个结论混淆了四个不同对象：

  1. CPU 的 cache 视图：CPU 最近写过、可能仍只存在于 cache line 中的字节；
  2. 系统内存视图：eDMA 作为另一个总线主设备实际能读到的字节；
  3. TCD 执行状态：源、目的、步长、循环计数和下一 TCD 是否已经被硬件装载；
  4. 软件所有权状态：此刻谁被允许修改 TCD 和 buffer。

DMA 不是“CPU 之外的一条 memcpy 指令”。它是独立的请求响应状态机。CPU 只负责准备内存和寄存器；一旦发布，硬件会在将来的某个总线时隙读取它们。若没有先定义可见性、生命周期与交接点，数值偶尔正确只是调度碰巧有利。

适用边界与证据分层

NXP 当前产品页列出的基准手册是 IMXRT1060RM Rev. 4.0，2026‑01，Chapter 6 “Enhanced Direct Memory Access (eDMA)”；本文谈到的 TCD 字段与 major/minor loop 以该章为芯片语义入口，NXP i.MX RT1060 官方产品与文档页给出了固定文档号和版本。SDK 侧固定到 MCUXpresso SDK 26.06.00 的 eDMA 示例目录，构建分支为 release/26.06.00、revision 02c9635c。

本文不把以下结论外推：

  • 不同 SoC 的 DMA 可能使用环形描述符、固定通道寄存器、IOMMU 映射或硬件 OWN 位。IOMMU 是位于 DMA 主设备一侧的地址翻译与访问控制单元，可把设备地址映射到被授权的物理页并拒绝越权访问；硬件 OWN 位则是某些描述符格式中由 CPU/设备交接的所有权标志。i.MX RT1062 eDMA TCD 没有被本文虚构成这两种机制；本文的 FREE → CPU_PREPARED → DMA → CPU_DONE 是软件合同。
  • “32 字节对齐”在本文中特指 eDMA scatter/gather TCD 的 SDK 要求；数据 buffer 的对齐还取决于传输宽度、cache line 和项目隔离策略，三者不是同一概念。
  • D‑cache 操作只适用于 cacheable 区域。若 MPU 把 DMA arena 配成 non-cacheable，数据 cache 维护路径会不同，但内存顺序与生命周期仍然存在。
  • 本文主机 lab 是离散合同模型，不模拟 AXI 仲裁、cache 控制器、总线错误、eDMA 寄存器副作用或外围 FIFO。

scatter、gather、linked list 和 ring 不是同义词

scatter 表示连续输入被分散写入多个不连续目的区；gather 表示多个不连续源区被顺序读成一条输出。硬件实现常用“完成当前 TCD 后装载下一 TCD”同时支持两者。linked list 描述控制结构的连接方式；ring 则额外要求尾部回到头部并长期循环。一个两节点有限链可以 scatter/gather，却不是 ring；一个固定地址循环 DMA 可以是 ring 行为，却不一定使用链表。

MCUXpresso SDK 26.06.00 scatter/gather 官方示例展示 TCD0 major loop 完成后装载 TCD1；同版本 ping‑pong 示例则把两个 TCD 互链形成循环。两者的差别直接改变停止合同：有限链以链尾完成为自然终点；循环链没有自然终点，必须另设“禁止新请求、确认当前请求静止、撤链、代次作废”的停止协议。

scatter/gather 不提供跨 TCD 原子性。TCD0 已经写完而 TCD1 因总线错误失败，是合法的部分完成状态。恢复逻辑必须知道：

  • 哪个 TCD 最后确认完成；
  • 当前 TCD 的残余迭代数是否可信；
  • 外设是否还在产生请求；
  • 目的数据的哪一段可以发布给消费者；
  • 重试是否会重复已经产生副作用的外设写。

“收到一个完成中断”也不自动等于“整条链完成”。SDK 的回调语义会给出自上次回调完成的 TCD 数；scatter/gather 时一次回调可以只代表一个或若干 TCD 完成。软件 API 因而必须把硬件回调展开成有序事件 (submission_token, tcd_index, result)：token 标识本次发布，index 标识链中哪一段，result 区分成功与错误；只有 index == next_expected_tcd 且 token 匹配当前发布，才允许把这一段从 DMA 交还 CPU。一个布尔 dma_done 会同时丢失段号、代次和部分失败信息。

ownership 是许可，不是地址属于谁

所有权在这里是并发许可：某个状态下谁可以读、谁可以写、谁负责推进状态。它不改变物理内存归属，也不等于 C 指针“属于”某模块。一个可审计的 TX 状态机是：

RX 的方向相反：CPU 先提供容量，DMA 写入，完成后 CPU 才解析。状态名相同不代表 cache 动作相同：TX 要把 CPU 新数据 clean 到硬件可见点；RX 要防止旧的 CPU dirty line 以后写回覆盖 DMA 新数据，并在完成后 invalidate 掉可能陈旧的 CPU cache 副本。

generation（代次） 用于解决 ring wrap 后的 ABA：slot 0 第一次使用、释放、再次使用时地址仍是 slot 0；只比较索引会把第一次的迟到回调误认成第二次完成。本文 oracle 的 SubmissionToken 同时携带单调递增的 channel generation，以及链内每个 (slot, slot_generation)；完成 API 再接收 tcd_index 和 result。旧 token 即使地址与 index 都重新相同，也会被 DMA_STALE_GENERATION 拒绝。代次不是加密随机数，只是生命周期标识；位宽必须按最大迟到窗口证明不会回绕混淆。

两段链的逐段状态不是“一起完成”：TCD0 的匹配 OK 事件只把 slot 0 变成 CPU_DONE，slot 1 仍由 DMA 持有；随后 TCD1 的 BUS_ERROR 只能证明 TCD0 已确认的 32 byte。oracle 先把当前段置为 DMA_ERROR 并保持 quiescent=false，此时回收会被拒绝；下层另取得通道 inactive/静止证据并调用 confirm_error_quiescent() 后，它才变成 CPU_ERROR。因此既不能把 64 byte 整链发布，也不能把“发生 error”本身误当硬件已静止。错误记录必须保存 confirmed_tcds、出错 index、残余计数和通道静止证据，不能用最终 buffer 中“看起来像新数据”的字节猜完成范围。

cache clean、invalidate、barrier 和 volatile 分别解决什么

clean 把 dirty cache line 写到一致点而通常保留 cache line；这里的一致点是 CPU cache 路径与 eDMA 可观察的内存路径会合的位置，究竟落在片上 RAM、互连还是外部存储控制器一侧必须由 SoC 手册确认。invalidate 丢弃 cache line，使后续 CPU 读重新取内存；clean+invalidate 先写回再失效。它们处理的是“同一地址有多个可见副本”。memory barrier 处理观察顺序；compiler barrier 只约束编译器重排；volatile 只要求相应 C 访问真正发生，既不清 cache，也不延长 buffer 生命周期，更不让复合字段更新原子化。

Arm CMSIS‑Core 6.2.0 的 M7 D‑cache API 明确提供 SCB_CleanDCache_by_Addr、SCB_InvalidateDCache_by_Addr 与 SCB_CleanInvalidateDCache_by_Addr，并把地址参数约束为 32 字节边界，见 CMSIS‑Core 6.2.0 D‑Cache Functions。NXP 的 MCUXpresso SDK 26.06.00 cache 示例也明确区分：CPU 写后、DMA 读前 clean；DMA 写后、CPU 读前 invalidate。

对本文平台，安全窄化策略是把 DMA buffer/TCD 放进专用、32 字节对齐、整 cache line 独占的 arena：由链接脚本划出的固定内存池，只允许受控 DMA 分配器放置对象，并有明确起止边界。原因不是“eDMA 所有数据必须 32 字节对齐”，而是按地址维护 cache 时通常覆盖整条 line。若 17 字节 RX buffer 与旁边一个 CPU dirty 变量共享 line，完成后 invalidate 这条 line 可能丢掉旁边变量；DMA 前 clean+invalidate 又可能让并发 CPU 写产生新的 dirty 副本。cache line 是一致性所有权的最小粒度，因此 buffer 的软件所有权最好也按 line 隔离。

地址可达性、宽度与边界检查

地址可达性表示特定总线主设备能否访问该地址，不等于 CPU 能解引用。SoC 可能含 TCM（tightly coupled memory，紧耦合存储器），它以低且确定的延迟直接连接 CPU 核，却未必挂在 eDMA 所在总线；还可能有受保护区域或外设别名。链接成功与 CPU 单步读写成功都不能证明 eDMA 可达。计划实验必须覆盖实际 linker map，并在目标板读取 eDMA bus error，而不是只比较最后 buffer。

访问宽度是每次总线访问的字节数。SDK 文档要求源/目的地址与所选宽度一致，否则产生 source/destination address error。宽度也不等于 NBYTES：可以每次 4 字节访问、一个 minor loop 搬 16 字节。配置前至少检查：

取消、超时、错误与复位的闭环

取消请求只是软件意图；quiescent（静止）才表示硬件不会再读写被取消对象。本文 oracle 在 request_abort(token) 后仍允许一次 device_access_after_abort()，并拒绝 release()；只有 confirm_abort_quiescent(token) 才把仍在 DMA 的 slot 标成 CPU_ABORTED 并允许回收。这不是声称真实 eDMA 必然恰好迟到一次，而是构造反例证明“请求已经发出”不能推出“访问已经停止”。目标安全停止通常需要：阻止新外设请求、禁用通道、等待当前读写结束或按手册执行 reset、读取/清除错误、使迟到回调代次失效，最后才归还内存。仅清中断 pending 不等于总线主设备静止。

错误恢复不能一律从链头重放。幂等表示同一操作重复一次或多次，外部可观察结果仍与执行一次相同；覆盖同一普通内存区可能幂等，向 FIFO、闪存控制器或设备命令寄存器重放却可能产生重复副作用。恢复策略必须按 destination 类型分类，并保存 last_confirmed_tcd、残余计数与外设状态。若这些证据不足，就 fail closed：不猜测部分结果可用，而是丢弃这一 generation、复位通道/外设并由上层重建事务。

ring 的生产者/消费者容量也要形式化。容量为 N 的 ring 若仅用相等的 head/tail 同时表示空和满，会有歧义；可保留一个空槽，或用单调 sequence。若 producer 在 consumer 尚未释放前追上一圈，旧 buffer 被覆盖。通过标准不是“平均吞吐足够”，而是：

第一项是消费者来不及介入前可能瞬时到达的突发字节，第二项是消费者最坏额外延迟期间继续到达的字节；量纲统一为 byte。若生产速率本身也会突发，应直接用到达曲线或测得的最坏窗口，不得把“平均速率 × 平均延迟”代入。

同时记录 high‑water mark、queue full、DMA error、取消时长和迟到回调；否则现场只剩一条 CRC mismatch，无法区分容量、cache 和所有权。

目标板可复现实验与通过标准（计划验证，本次未执行）

准备 MIMXRT1060‑EVKB、MCUXpresso SDK 26.06.00 固定 revision 02c9635c、J‑Link 或 MCU‑Link、逻辑分析仪；构建官方 edma_scatter_gather 和项目 fault variant。把 TCD/buffer 链接到已核对 eDMA 可达的 cacheable OCRAM 区，每个对象独占 cache line；另建 non-cacheable MPU arena 作为对照。

步骤与观测量：

  1. 两 TCD 各搬 4096 字节 PRBS（pseudo-random binary sequence，伪随机二进制序列），它由固定种子确定地产生、便于重放且比全零更容易暴露地址/数据粘连；连续十万链。每次记录 generation、TCD index、CITER、eDMA error status、源/目的 CRC（循环冗余校验）、ISR cycle 与 queue high‑water（观测窗口内队列占用峰值）。CRC 用来高概率发现内容差异，不是密码学真实性证明，也不能单独证明没有越界写。
  2. 正常版执行完整 clean/barrier/invalidate；故障版分别省略 TX clean、TCD clean、RX invalidate，在 D‑cache 开/关与 cacheable/non-cacheable arena 四种配置下运行。
  3. 故意让第二 TCD 指向未对齐地址、不可达区、0xffffffe0+64 式 32 位 wrap span，并让两个逻辑 slot alias 同一 TCD 地址；提交前软件检查应拒绝可静态证明的问题，目标 eDMA source/destination/scatter-gather error 则要被捕获并按手册复位。
  4. 在 DMA_ACTIVE 时由低优先级任务试写 buffer；软件 ownership 守门必须拒绝。完成并复用同一 slot 后注入旧 token 的迟到 ISR，即使 index/address 相同，generation 不匹配也必须丢弃。
  5. 用 GPIO 分别标记发布、DMA ISR 与消费者可读；若 destination 是 UART，再同时采 TX，证明 DMA complete 与线路 complete 是两个时间点。
  6. 让 TCD0 正常完成、TCD1 触发可控 bus error，证明消费者只收到 TCD0；另在请求 abort 后、硬件确认 inactive 前尝试回收并观测总线访问，前者必须拒绝，直到寄存器/请求源证据证明 quiescent 才允许释放。

硬件通过标准：正常矩阵零数据 mismatch、零越界访问；事件 trace 中 token/index/result 严格单调匹配，部分错误绝不发布未确认段；abort request 到 quiescent 之间没有内存回收；每个注入都产生预期错误而不是静默错误；错误后通道可重新提交；cacheable 正常版与 non-cacheable 对照结果一致；省略维护只可作为故障证据，不能进入交付；所有 buffer 的发布—逐段完成—回收代次闭合。任何仅“最终 CRC 正确”、但没有状态/错误寄存器/波形的结果都不通过。

真实故障注入：旧 payload 偶发上链

注入是删除 TX payload 的 clean，只保留 TCD clean 和启动写。现象：大多数包正确，CPU 高负载或相同 cache set 竞争后第二段偶尔保留上一 generation；关闭 D‑cache 消失。假设包括 eDMA 链接错误、buffer 被提前复用、payload 未到内存。

证据计划：TCD snapshot 的地址/长度/next 全正确；ownership trace 无提前回收；CPU cacheable 地址读回新 payload，而 non-cacheable observer/目的 CRC 对应旧 payload；补回 clean 后故障消失。由此排除 descriptor 与生命周期，定位为数据可见性。修复不是全局关闭 cache，而是专用 arena、完整 line clean、屏障后启动，并让 owner 在完成前保持 DMA。回归覆盖 cache 开关、不同内存区、链长 1/2/8、ring wrap、最大总线争用和取消错误。

闭环可写成：旧数据 → 链/复用/cache 三假设 → TCD snapshot + generation + 双视图 CRC → payload 未 clean → 对齐 arena 与发布封装 → 全矩阵零静默错误。若目标板没有获得这些证据，本节仍只是可执行调查方案，不能标成“已复现”。

资源、实时性与安全边界

描述符越多，中断摊销越低，却增加不可撤销的在途数据和错误恢复范围。大 burst 提升带宽，却可能长期占用总线，拖慢 CPU、显示、网络或实时 ADC。eDMA bandwidth/throttling 与通道优先级必须按最坏延迟测量，不能用平均 MB/s 替代 deadline。

DMA 能写任意被配置的可达地址，因此长度/地址错误是内存安全问题。本文平台没有为 eDMA 提供本文可依赖的 IOMMU 隔离：核心 MPU（Memory Protection Unit）可约束 CPU 软件访问并设置 cache 属性，却不能被误当成拦截 eDMA 越界总线事务的防火墙。因此直接防线是提交前的软件地址轨迹验证、静态且边界明确的 DMA arena、受控 API 与最小权限驱动；MPU 只作为约束 CPU 调用方和内存属性的补充。来自外部包的 length 不能直接乘 stride 填入 TCD；先做精确整数溢出检查，再验证完整地址轨迹。故障日志也不能直接遍历可能被 DMA 篡改的 next pointer；先停止通道并把有限字段复制到可信区。

低功耗/复位会打断所有权。进入睡眠前要证明通道 quiescent；醒来后不能假设 TCD 寄存器、DMAMUX（把某个外设请求源路由到某个 eDMA 通道的请求复用器）映射和 cache 状态保持。系统复位后，保留 RAM 中的旧 owner 也不能直接恢复链，应增加 boot generation 并重新初始化。

练习题与可判定答案

  1. 为什么 volatile uint8_t buffer[] 不能修复旧 DMA 数据？ 答案必须同时指出：volatile 只约束 CPU 访问；不执行 cache clean；不建立跨主设备顺序；不保护生命周期。
  2. TX 和 RX 的 cache 动作为什么不对称？ TX 是 CPU 生产、DMA 消费，DMA 前 clean；RX 是 DMA 生产、CPU 消费，要防前置 dirty writeback，并在完成后 invalidate。未提共享 cache line 风险不满分。
  3. TCD0 完成是否等于 scatter/gather 链完成？ 否；须结合完成 TCD 数、当前/残余状态和链尾定义。
  4. 为什么完成 API 同时需要 token、TCD index 和 result？ token 拒绝旧生命周期，index 只推进下一已确认段，result 区分成功与部分错误；缺任何一项都可能把迟到/跳段/失败事件误当整链成功。
  5. 调用 abort 后为何还不能 free()？ abort 是请求，DMA 仍可能有在途或迟到访问；必须取得 quiescent 证据并使旧 token 失效。只答“因为有中断”不完整。
  6. 为什么本 lab 拒绝 0→1→0，而 SDK 示例允许 ping‑pong？ lab 只证明有限链终止；循环链必须额外有取消、代次和静止证明。把拒绝解释为硬件不支持判错。
  7. DMA TC 后能否立即释放 UART 的 RS‑485 DE？ 不能；DMA 完成只到 USART 数据路径，须等待 USART 线路 transmission complete。
  8. 实操验收必须提交：linker map、TCD/buffer 对齐、cacheable/non-cacheable 矩阵、eDMA 错误寄存器、token/index/result generation trace、CRC 与 GPIO/线路波形。只提交“跑了十万次没错”不通过。
